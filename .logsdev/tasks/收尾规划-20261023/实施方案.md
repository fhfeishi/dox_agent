## 1. R1 项目索引：请求只读、后台单一写入方、跨进程互斥

### 1.1 现状与根因

`ProjectIndex.library(info, knowledge)`（`src/project_index.py:112`）在每个请求里：读全部缓存行 → 逐份文档算签名 → 签名不符的文档重新解析，并**每份单独开连接、单独提交**一行 `INSERT OR REPLACE` → 聚合返回。调用方 7 处：`api/structure.py`（41、88、199、210 行）、`api/reports.py:307`、`intelligence.py:265`、`api/domains.py`（全景，一次请求聚合 11 库）。

缓存一旦失效（升级改 `INDEX_VERSION`、新导入、四维提取改写 `target/*.json`），并发请求各自重建同一批文档：N 个写者逐条抢 SQLite 写锁（回滚日志模式下每次提交都要独占），Windows 上每次提交还有一次落盘同步，排队超过 30 s 即 `database is locked`，已写的行保留但请求失败，前端重试又带来新一轮并发。实测 2026-10-23：6 个线程同时卡在第 160 行，服务日志 12 次锁超时；顺序预热后 510 份的库首轮 70 s、次轮 1.3 s。

另一个隐患：缓存命中时，每次请求仍对全部行做 JSON 解析与聚合（517 份约 1 s，全景 11 库约 3 s）。千人并发下这是纯 CPU 浪费。

### 1.2 设计

| 层 | 做法 | 对应约束 |
|---|---|---|
| 写入 | 新增 `ProjectIndex.refresh(info, knowledge) -> int`：算全部签名、只重算不符的文档、**一个事务**写入全部变化行并删除已不存在的行，事务内把该库的 `revision` 加 1；返回新 revision | 成批写入 |
| 互斥 | 新增表 `index_state(corpus PK, revision INT, built_at TEXT, lease_owner TEXT, lease_until TEXT)`（`SCHEMA` 追加一步，迁移器只增不改）。`refresh` 先取租约：`UPDATE index_state SET lease_owner=?, lease_until=? WHERE corpus=? AND (lease_until IS NULL OR lease_until < ?)`，受影响行数为 1 才算拿到；不存在的行先 `INSERT … ON CONFLICT DO NOTHING`。租约 10 分钟，重建中每处理 50 份续一次；结束或异常时清空。持有者标识 `主机名:进程号:uuid` | 跨进程互斥；崩溃后租约过期自动接管 |
| 触发 | 后台重建由 `src/jobs.py` 运行器执行（新 kind `index`）：① 启动后对每个库检查一次；② 导入（`import`）与四维提取（`target`）完成时对该库触发。同一库已有租约时不再启动 | 请求路径不写 |
| 读取 | `library()` 改为只读：读 `index_state.revision` 与缓存行，**不在请求里重算**。签名与当前文档不符时照常返回缓存行，并附 `index: {"state": "refreshing", "revision": n, "stale_docs": k}`，同时触发后台重建。首次建库同样只调度后台任务，等待最多60 s轮询已发布修订，超时返回503“资料正在整理，请稍后刷新”，带 `Retry-After`。用户在执行时确认采用此口径，取代原“冷缓存请求内refresh”例外 | 并发请求不再重复重建；首次建库只建一次 |
| 聚合缓存 | 聚合结果按 `(corpus, revision, topic_merges 修订)` 缓存在进程内（LRU，每库 1 份）；revision 每次从 `index_state` 读（一次主键查询），因此多实例下任一实例重建后，其他实例下次请求即发现并重算 | 计算重的读按修订号缓存，修订号在共享存储 |
| 可移植 | SQL 只用 SQLite 与 PostgreSQL 都支持的写法（`ON CONFLICT … DO UPDATE/NOTHING`、普通 `UPDATE … WHERE`），不新增 `INSERT OR REPLACE`，原有两处随本卡改掉 | 存储可替换 |

`topic_merges`（人工整理）的读写不变；合并或撤销时同样把该库 revision 加 1，使聚合缓存失效。`project_vectors` 与相似度（`project_similarity.py`）的请求内写入属于同类问题，但涉及嵌入模型的调度，本卡不改，列入 §8 已知债务。

### 1.3 前端

`index.state === "refreshing"` 时，在用到项目索引的页面（首页概览、领域分析、资料库四维）顶部显示一行“资料正在更新，当前显示的是上次整理的结果”，不阻塞页面；503 时显示“资料正在整理”与重试按钮。文字进 `copy.ts`。

## 2. R2 直接打开 `/library/<资料库>` 返回 404

- 现状：`src/main.py` 前端兜底（`frontend()`，约第 192 行）的正则只放行 `library/<id>/documents…` 与 `library/<id>/targets/four-facets`；`tests/test_app.py:228` 同时要求 `/library/no-such-page` 返回 404。两条要求都有效，不能只放宽正则（那样就改了断言）。
- 做法：正则改为 `library(?:/(?P<corpus>[^/.]+)(?:/(?:documents(?:/[^/.]+)?|targets/four-facets))?)?`；匹配到 `corpus` 时用已有的 `find_corpus(id)` 确认资料库存在且未缺失，存在才返回 `index.html`，否则 404。路由表 `frontend/src/router.tsx` 与这里的正则在文件中互相注明，改一处须改另一处。
- 千人并发：`find_corpus` 目前每次扫描目录（见 R5），R5 做成登记表后这里自然变快，不另做缓存。
- 测试：`test_app` 同一用例增加 `/library/{corpus_id}` 返回壳页面；`/library/no-such-page`、`/library/{corpus_id}/no-such` 仍 404。浏览器：直接打开并刷新 `/library/<id>`，截图。

## 4. R4 模型连接状态只保留一份（用户选 b）

- 现状：三处各管各的。① 启动检查 `src/launcher.py model` → `agent/models.py:check_model`，结果只打印；② 运维抽屉 `POST /api/model/check`，结果只返回给页面；③ 审查模块 `POST /api/review/model/test` 把结果写进审查库的 `model_connection` 记录（`review/routes.py:157–188`），审查页读它显示“最近一次模型连接测试失败”。`/api/health` 的 `model_verified` 恒为 `False`（`api/system.py:36`），是无用字段。
- 做法：
  1. 新建一份共享的模型状态：应用级 `workspace.sqlite3` 增表 `model_checks(connection PK, status, latency_ms, error, checked_at, source)`，`connection` 为 `sha256(base_url, model, key)`（不存密钥）。审查使用独立模型（`REVIEW_MODEL_*`）时它就是另一个 connection，各自一行。写入函数放 `agent/models.py`，`check_model` 每次检测后写入。
  2. 三个入口都写这一份：启动检查（launcher 进程直接写同一文件）、`/api/model/check`、审查页“重新测试”（保留它额外的 JSON 输出检查，结果同样写这一份）。
  3. 读：`/api/health` 用 `model_status: {status, checked_at, latency_ms}` 取代 `model_verified`；`/api/review/health` 返回审查所用 connection 的同一结构。删除审查库的 `model_connection` 记录类型及 `connection_state`，加一次迁移清掉旧记录；前端审查页与顶栏“模型”标记都改读新字段，不保留旧字段（新旧冲突整体替换）。
  4. 审查页文案：失败时写“上次检测（时间）失败：原因”，成功不提示。
- 千人并发：状态在共享存储，任一实例写入后所有实例读到同一结果；不放进程内存。
- 测试：先写失败再写成功，`/api/review/health` 为 connected；启动检查写入后 `/api/health` 显示 connected 与时间；审查独立模型时两行互不覆盖；`model_verified` 字段不再出现。浏览器：审查页在模型正常时无红色提示，截图。

## 8. 已知债务（不在本轮做，记录以免遗忘）

以下现有实现依赖单进程，多实例部署（B5）前须处理，届时各自立卡：

| 位置 | 单进程假设 | 多实例下的后果 |
|---|---|---|
| `src/jobs.py` | 任务占用（`keys`、`tasks`）只在进程内存；启动时 `recover()` 把所有未完成的运行标为中断 | 实例 B 启动会把实例 A 正在跑的任务标为中断；两个实例可同时对同一库导入 |

| `review/routes.py` | 审查用进程内线程池与自己的运行记录 | 同上，且不受统一运行器管理 |
| `project_similarity.py` | 请求内计算嵌入并写 `project_vectors` | 与 R1 同类的并发重建；嵌入在 CPU 上更慢 |
| 各状态库 | 回滚日志模式，未启用 WAL（[系统.md §3](../../design/系统.md#3-存储现状--目标)） | 读写互斥更重；迁到 PostgreSQL 或启用 WAL 前须确认所有连接经 `core/db.connect` |
| `launch.sh`、`launch.cmd` | 单个 uvicorn 进程，默认只监听 127.0.0.1 | 部署方案（B5）另定 |
