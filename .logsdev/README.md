# .logsdev — 项目记录与维护约定

本目录保存 dox_agent 的开发文档与工作记录。**按任务需要组织，不强制模板**：先用已有等价文档，缺什么再采用什么；模板占位不代表已完成或已采用的事实。同一结论只在一个地方维护，其他场景只补差异与链接。

## 记录入口

| 文件 | 用途 | 何时更新 |
|---|---|---|
| [PROJECT.md](PROJECT.md) | 长期稳定说明：目标、范围、结构、契约、质量约束、当前限制 | 目标/需求/契约/现状实质变化时 |
| [ITERATION.md](ITERATION.md) | 当前工作：目标、已完成与依据、未决与下一步 | 有意义的进展、阻碍或接续点变化时 |
| [DECISIONS.md](DECISIONS.md) | 关键取舍：选择、理由、代价、替代关系 | 决策采用或被替代时 |
| [demand.md](archive/demand.md) | 需求基线（分期实施；§9/§10 为追加项） | 需求变更时 |
| [status.md](archive/status.md) | 现状摘要：接口、能力、限制 | 每次开发后 |
| [design/](archive/design/README.md) | 接口与实现契约（HLD / API / LLD） | 接口、数据、状态变更时 |
| [plan/](archive/plan/plan.md) | 分期计划、任务状态、完成记录、专项设计 | 推进任务时 |
| [archive/](archive/README.md) | 只读历史快照 | 仅确有需要时 |

## 模板选择

| 模板 | 何时采用 | 主要内容 |
|---|---|---|
| [PROJECT.md](PROJECT.md) | 长期项目需要独立的稳定说明时 | 目标、有效要求、现状与重要限制 |
| [ITERATION.md](ITERATION.md) | 工作需要跨会话接续时 | 当前目标、完成内容及依据、未决问题与下一步 |
| [DECISIONS.md](DECISIONS.md) | 出现值得长期追溯且需独立维护的取舍时 | 选择、理由、代价与替代关系 |

无需按表格顺序填写，也无需先创建空决策文件。单次修改、审查或知识总结可以直接完成并交付。

## 填写与更新

替换所需占位，删去不适用内容。当前工作默认用简短自然语言；只有任务、验收或证据确实需要对应时才展开表格和编号。不默认指定角色、维护者或完整审查链。

长期结论引用可定位的提交及检查结果、固定报告或带版本的记录，不能只指向下一次会被覆盖的工作文件。更新当前工作前保留必要历史依据，并带入仍有效的约束和问题。

[archive](archive/README.md) 仅用于确有需要的只读快照；目标项目无需默认创建或按轮归档。保留本目录现有路径与文件名，不要求目标项目采用相同命名。

# 项目工作与文档维护约定

默认按任务需要组织工作和证据。保留足以理解、执行、核查与接续的信息，优先更新已有文档；不为使用模板而增加角色、审查阶段或状态表。

## 1. 需要多少记录

| 场景 | 默认需要 | 何时增加结构 |
|---|---|---|
| 小修改、一次审查、短篇知识总结 | 明确目标，完成工作，说明结果和限制 | 有接续需求时记录当前状态 |
| 跨会话开发、持续调研 | 当前目标、重要进展、依据、未决问题、下一步 | 多项任务或验收需要对应时增加计划与表格 |
| 长期项目 | 稳定说明、当前工作、重要取舍 | 信息有独立维护需求时拆分 |
| 多人或多智能体并行 | 在所需记录上补充责任、写入范围、基线及集成检查 | 实际并行或交接时启用第 5 节 |

这些是选用条件，不是四套流程。单次工作可以直接交付；没有必要的独立审查、观察或分工，不用建立占位记录，也不要求填写"不适用"来豁免。

## 2. 信息放在哪里

| 信息 | 主要维护位置 | 更新时机 |
|---|---|---|
| 当前知识、稳定目标、有效要求、系统现状与限制 | 既有主题正文或项目说明；可选 PROJECT | 新认识、需求、契约或现状实质变化时 |
| 当前目标、已完成内容及依据、未决问题与下一步 | 既有工作记录；可选 ITERATION | 有意义的进展、阻碍或接续点变化时 |
| 值得长期追溯的关键选择、理由与代价 | 既有决策章节；必要时 DECISIONS | 决策采用或被替代时 |
| 历史版本、完整审查和调试细节 | Git、PR 或已有任务记录 | 需要追溯时保存；不复制成另一份当前状态 |

同一结论指定一个主要维护位置，其他场景只补差异与必要链接。已有 OpenAPI、schema 等精确契约时引用原位置，正文补行为语义与限制，不复制易漂移的字段定义。文档与代码冲突时依据有效需求判断修哪一方，不能默认代码正确。

有效要求可以尚未实现；现状只写实际存在的内容。建议与拟议设计不等于采用，采用不等于实现，实现不等于验证。知识正文更新当前解释；历史记录中的旧判断通过更正或替代关系保留，不能改成仿佛一直正确。

## 3. 证据、结论与追溯

证据应能回答"据什么得出这个结论，支持到哪里"。代码结果说明检查方法、实际结果与适用版本；调查说明来源、关键观察及推断过程；建议说明条件、比较依据与未知。不要求所有任务填写同一证据表。

- 仅列测试文件、组件或命令名不能证明已运行。必要时补充环境、输入、时间与复现方式；人工检查也记录实际观察，不伪装成自动验证。
- 代码基线可用提交，或基础提交加可还原的工作区补丁标识；仅有时间或文件列表不足以还原版本。文档审查和调研按需要标明材料版本或来源日期。
- 相关改动或环境变化可能使旧结论不再支持当前状态。保留原结果并标明适用范围，对受影响内容补查；无需无差别重复检查。
- 长期结论应链接可定位的提交与文件位置、固定版本报告、持久 CI 结果或带版本的记录。提交只定位代码，仍需检查结果支持验证结论。只链接会被覆盖的 ITERATION 不能作为长期验证依据。
- 临时记录不可持久访问时，将必要的结果、复现条件与关键失败原因保留在现有正文或持久记录中。未形成稳定依据时明确标注，不能提前声称历史已保存。

简单工作用自然语言即可。多项验收或任务需要相互引用时，可采用 AC-01、P-01、E-01 等编号，仅建立实际需要的对应关系，不强制 `R → AC → P → E` 全链条。跨轮次追溯时再增加稳定的工作编号或版本引用；已被引用的 ID 不改作无关内容。

状态也按需使用，避免多个章节重复维护同一状态。使用任务表时可标未开始、进行中、受阻、待验证、完成或取消；验收表可标未检查、通过、失败、受阻或移出范围。取消与移出范围说明有效依据，不算通过。审查结论仅针对实际审过的范围；自检不得称为独立审查。

"通过验收项数 / 当前范围验收项总数"只表示验收项通过情况，不代表项目整体进度，各项工作量与重要性可能不同。

## 4. 接续、交付与历史

需要接续时，保留当前目标和有效约束、实际完成内容及依据、未决问题和下一动作即可。发现偏离目标时调整计划或实现，把原因写在相关内容附近；不要再建 Observation 重复维护问题、验收与下一步。

完成由用户目标、有效约束及约定的完成依据决定。开发核对行为与必要检查，调查核对问题是否得到有依据的回答，知识整理核对逻辑、信息保留和链接；若任务或项目要求审查，处理其阻断发现。没有此类要求时不默认增加计划审查、代码审查或观察阶段。

交付先说明结果、依据和限制。仍有实质缺口就如实说明未完成部分；不能靠勾完计划、减少验收项或改写文档迎合实现来宣布完成。需求范围变化需有有效来源，更新受影响的记录；普通已授权修订不增加审批。

更新或替换当前工作记录前，确认需要保留的依据已有持久版本，并显式带入仍有效的约束和未决项。必要时先将长期结论的链接改为稳定引用，再压缩旧工作内容。Git 未记录的内容不能以"历史已有"为由清空；按仓库提交流程保存，不因模板自行推送或发布。

历史默认交给已有版本记录。仅在无 Git、外部交付或审计需要时使用 [archive](archive/README.md)，不按轮次自动复制文档。篇幅按用途决定，先去重复、压缩无增量过程，保留关键条件与失败；只有独立维护需求确实存在时才拆分。

## 5. 并行协作与交接（可选）

只有存在多个写入者或实际交接时使用本节。单人串行工作无需指定维护权；并行任务也不必凑齐固定角色链。

| 可选职责 | 负责什么 | 交付什么 |
|---|---|---|
| 计划 | 将目标转为可执行安排与必要验收 | 任务、依赖、范围和完成依据 |
| 实现 | 在约定范围内修改与检查 | 实际变更、结果和限制 |
| 审查 | 检查指定计划、代码或材料 | 发现、依据、影响和建议 |
| 对齐观察 | 在确有需要时检查目标与结果是否一致 | 偏差、缺少的证据及下一动作 |
| 共享状态维护 | 多个参与者需要更新同一状态文件时协调落盘 | 汇总核实后的当前记录 |

多个参与者涉及同一共享状态文件时，指定一名最终写入者，其他人提交反馈或局部补丁；交接时说明已接收内容。同一文件分章节仍可能相互覆盖。担任审查职责时只提交反馈，由负责修改者吸收；不按 reviewer 或轮次创建长期文档。

并行代码任务写明负责人、文件或模块范围、必要依赖和基线。重叠范围先协商拆分或串行执行，保留他人未提交修改。独立分支或工作树的结果集成后执行受集成影响的检查，分支通过不能替代集成验证。Markdown 约定不提供锁或工具权限。

交接可在已有消息、PR 或工作记录中使用下列提示，只保留需要的内容，不另建模板文件：

```text
对象与范围：要接续什么；必要时补编号和版本
结果与依据：实际完成内容、检查或来源、支持范围
未决问题：具体差异、影响、处理人或需要的输入
下一步：接收者、下一动作及必要依赖
```

影响接续的问题不能只藏在不可访问的临时消息中；需要时写入当前工作记录。已解决问题可压缩为结论及持久依据，不丢弃改变判断的关键失败。
