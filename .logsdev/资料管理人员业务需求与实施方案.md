这套产品面向不具备技术基础的资料管理人员。主要操作应是选资料库、点分类、点项目、选现成问题、上传材料和查看整理好的结果；自由输入用于补充，不能成为普通流程的必经步骤。

会议明确了三条业务线：自然科学基金资料管理、资料分析、申报材料的形式与专业审查。以下将这些方向细化为页面、数据、交互、规则和分批验收；未提供的指南、模板和政策条款不被假设为真实规则。

## 3. 面向资料管理人员的交互原则

### 3.1 页面要回答什么

每个页面首屏说明：“这里有什么”“我可以做什么”“当前展示的是哪些资料”。技术字段留在可展开的详情中。

| 当前技术表达 | 用户界面建议 |
| --- | --- |
| corpus / indexed / stale | 资料库 / 可用于分析 / 原文已更新，请重新整理 |
| target / facets / evidence | 四维整理 / 场景·问题·技术·成果 / 原文依据 |
| coverage_partial | 已分析部分资料；以下结论仅对应这些项目 |
| run / engine / tokens | 本次分析 / 分析方式；用量放入详情 |
| candidate / similarity score | 可比较的项目 / 为什么显示为相近 |
| rule / pending / unsupported | 检查要求 / 需要核实 / 当前不能自动检查 |

结果优先展示“归纳要点＋对应项目”，其次是原文依据。失败应说明用户下一步能做什么，例如“这份材料无法读出正文，请换一份可复制文字的文件”。

### 3.2 默认操作与推荐问题

- 选库后直接进入归纳总览，不要求输入问题或理解筛选表达式。
- 页面显示当前库、立项年份、选中项目数量和整理覆盖；点击图表只改变浏览范围，不悄悄替换正在进行的任务输入。
- 每个页面保留 3–4 个高频问题按钮，其余收在“更多问题”中。
- 点问题进入已填写好的任务摘要；用户只需确认资料范围并点击“开始分析”。普通用户不用选择模型、提示词或技术参数。
- 结果页提供“查看依据”“对比这些项目”“继续分析”“保存为成果”。
- 内容较多时可折叠，搜索为可选辅助；不是完成流程的前置。
- 原文返回后保留筛选、图表选择、项目列表位置和当前展开项。
- 键盘操作、焦点、颜色文字和屏幕宽度一起设计；不会操作图表的用户始终能使用项目列表。

## 4. 资料对象：项目与文件分开

自然科学基金业务中的计数单位是“项目”，不是 PDF 或 Markdown 文件。一个项目可能有项目条目、摘要、结题报告和补充材料。

### 4.1 项目最小信息

| 信息 | 来源与处理 |
| --- | --- |
| 项目名称、批准号、负责人、单位 | 优先结构化项目条目，其次明确的原文；保留来源 |
| 立项年、结束年 | 文件名现有起止区间；和原文明示时间不一致时展示冲突 |
| 项目类型 | 明确的结构化字段或原文，不根据标题猜测 |
| 资助金额 | 明确金额、币种、单位、金额口径和出处；不能把申请预算混成批准资助 |
| 四维条目 | 已发布、当前版本有效的 target 结果及其证据 |
| 成果状态 | 已取得、预期、原文未明确；保留指标、条件与限定语 |
| 文件与版本 | 该项目关联的全部文件，选定证据始终绑定版本 |

项目主键建议采用“资助体系＋批准号”。批准号缺失时先作为待核对项目，不能用相似标题或同名负责人自动合并。跨库出现同一项目不移动文件，可以共享项目身份并保留多个库归属。

同项目多文件中的经费或时间冲突不能简单“取最新/取最大”。界面提供出处对照和候选值确认，确认结果作为独立修订，保留原提取值与来源版本。资料管理员确认字段不等于修改原文件。

### 4.2 可用不等于整理完成

每个库显示总项目数、已完成四维整理数、待整理、原文已更新、整理失败和信息待核对数。文件已入库与四维已整理是两件事。

未完成四维的项目仍可浏览原文，但不混入“原文未提及”统计；未提及、提取失败和未整理使用不同文字。局部整理不作为完整关系图或全库结论的依据。

## 5. 一级卡片与二级归纳页面

### 5.1 一级卡片

保留现有卡片布局。卡片展示库名、项目数、四维整理进度和异常提示；支持“查看归纳”“管理资料”两个明确动作。资金、关系图和长篇摘要留在库内页面，首屏不堆字段。

### 5.2 二级页面结构

~~~text
AI与医疗
项目总数 · 已整理项目数 · 待核对信息
[立项年份] [项目类型] [当前筛选摘要] [重置]

[四维归纳] [时间与经费] [项目关系] [资料列表]

场景：研究在哪些实际情境中开展？    问题：试图解决哪些困难？
技术：用了哪些方法或路线？         成果：取得或计划取得什么结果？

点击归纳条目 → 关联项目列表 → 项目四维摘要 → 原文依据
~~~

默认“四维归纳”，其余是同一库、同一筛选范围的视图，不创建四份重复资料。管理员从归纳总览能进入资料列表上传或整理，无需退回一级页面。

### 5.3 四维归纳的展示规则

四张维度概览卡先各显示若干主要条目和去重项目数，点击一个维度可展开完整条目列表。条目至少包含名称、关联项目数、代表项目与证据入口。

| 维度 | 展示重点 | 推荐按钮 |
| --- | --- | --- |
| 场景，红色 | 疾病、应用环境、服务对象、实际使用位置 | 这些项目面向哪些场景？ |
| 问题，蓝色 | 已明确的困难、限制和需要解决的矛盾 | 各场景最常见的问题是什么？ |
| 技术，绿色 | 方法、路线、数据与关键技术要素 | 哪些项目使用相近的方法？ |
| 成果，黄色 | 已取得结果、预期结果、定量指标及条件 | 已取得哪些成果？还有哪些只是计划？ |

四维“成果”指项目研究产出；一级“成果”指本工具保存的分析结果。说明与按钮采用“研究成果”“保存分析结果”等明确词，避免两个对象混淆。

一个项目可属于多个场景/技术，计数按项目去重，各条目数量不可直接相加。展示分母，例如“8 / 35 个已整理项目涉及医学影像”；分母跟随筛选与有效整理版本，不是检索命中的前几份。

首版按原有条目名称进行空白/格式归一并计数，不让模型擅自把“深度学习”“卷积网络”“AI”合并为同一个标签。同义归并确需引入时，以可核对的别名映射处理，保存原词和确认依据。项目特征有条件或对象差异时，即使同名也不能合并结论。

默认成果概览突出已取得，预期和未明确状态可点击切换。归纳结果不能把拟开展工作计为已实现应用。长期效果、实验条件、样本规模等限定信息在详情中保留。

### 5.4 一次归纳，多次浏览

标签聚合与项目统计由已发布结果构建，切换页面不重新调用模型。新资料或原文版本变化后重新整理相关项目，再更新统计；旧结果标记失效，不与新结果混算。

首版使用“常见条目＋项目数＋代表项目”的确定性归纳即可。自动撰写库级叙述摘要可作为显式“生成概览”任务，带覆盖范围和保存成果，不在每次开页面时后台生成。

## 6. 时间与经费图：定义清楚再画

### 6.1 基础图形

横轴为立项年，纵轴为资助金额，单位优先统一为万元；一个点代表一个项目。2021—2025 的项目落在 2021 年位置。点越高表示同一口径下资助金额越多，不表示质量、先进性或实际影响更大。

推荐一个图中切换“场景 / 问题 / 技术 / 成果”，维度使用会议指定的红、蓝、绿、黄；切换后展示所选条目关联的项目。提供四个小图的对照视图作为后续增强，不默认同时显示四张大图。

项目仍是点，而不是“项目中的每个标签各画一个点”。选择“技术→深度学习”时显示该标签关联的项目；同项目同年度同金额不因多个技术条目重复画点。每个维度总体图可能相似，这是同一组项目的事实，不人为造差异。

### 6.2 交互

- 默认显示当前库可用的立项年份，点击年份区间筛选；鼠标悬停和键盘聚焦都能看到摘要。
- 点击项目点固定详情：名称、立项区间、资助金额及口径、四维摘要、原文依据。
- 点详情中的“查看项目”打开同一个项目检查器，“分析这些项目”进入范围摘要。
- 年份点击、图中选择和维度标签联动下方项目列表，可随时重置。
- 同一位置重叠时显示项目数量，点击展开列表；仅在年份带内做明确的横向避让，不改变纵向资金值。
- 首版支持年份范围、点击筛选、悬停/聚焦和详情；不要求自动动画、自由缩放、多层钻取或复杂播放。
- 图旁可显示每年项目数、可统计资助总额与缺失数量。只有覆盖及口径一致时显示同比/占比，否则注明不足。

### 6.3 金额与时间的诚实处理

| 情况 | 行为 |
| --- | --- |
| 金额与单位明确 | 保存原值及单位，用 Decimal 精确转换；展示来源与资助口径 |
| 总经费与直接费用并存 | 分别保存，当前图按明确选择的单一口径绘制，不混在同一纵轴 |
| 币种不一致 | 默认分别统计，首版不自动汇率换算 |
| 金额缺失 | 单列“金额待核对项目”，可点击查看，不画成 0、不用模型估算 |
| 明确资助金额为 0 | 与缺失区别，按 0 显示 |
| 时间冲突或批准号缺失 | 单列待核对，不自行把项目塞入某一年 |
| 部分文件无法整理 | 在覆盖数字中保留，不从总体悄悄消失 |
| 经费极端大 | 保持真实值；必要时可选明确标注的刻度方式，不隐藏异常值 |

当前年份窗口的两种业务语义必须区分：**本页面按立项年筛选**；已有专项报告按项目区间与年份窗口相交筛选。二者不能共用一个含糊的 year 字段，也不能为满足时间图改写所有旧报告口径。UI 在任务摘要中显示“按立项年”或“项目区间相交”。

## 7. 项目关系：先做能解释的简单图谱

### 7.1 首版关系

采用“项目—四维标签”的关系，而非自动判断谁继承了谁、谁优于谁。选一个项目后，按某个维度查看共有标签和对应项目，推荐局部两层展示：中心项目→共享标签→相近项目。

- 项目节点采用中性色，维度标签使用红/蓝/绿/黄。
- 关系明确写“共享场景”“针对相同问题”“使用同名技术条目”“涉及同类研究成果”。
- 点击连线或标签能查看两边项目各自的原文证据。
- 同项目不同文件不变成两个相似项目节点。
- 默认只展示选定项目或条目附近的关系，提供数量与“查看全部列表”，不渲染全库所有两两连线。
- 图与列表是同一数据；用户不操作图也能完成比对。

### 7.2 事实关系与分析关系分开

| 关系 | 是否首版支持 | 必要依据 |
| --- | --- | --- |
| 共享归纳条目 | 支持 | 两个项目的有效标签及各自引用 |
| 同一个项目的不同资料 | 支持 | 批准号与关联文件，不属于“技术相似” |
| 文内明确的场景→问题→技术→成果关联 | 复用已有 relations 展示 | 原文明示与定位 |
| 语义相近但名称不同 | 可在专业分析中作为候选建议 | 对照说明及双边证据，不能混成确认图谱 |
| 技术继承、因果、路线优越、项目重复 | 不自动建立事实边 | 需要明确文本或专家确认，不能由标签共现推导 |

同一技术名不代表路线完全相同，涉及对象、数据、指标和条件必须可展开。共享条目数量可以用于排序，但不命名为“先进性分数”或“重复率”。

### 7.3 存储选择

推荐在现有 SQLite 中建立项目元数据和按维度归一的标签索引，关系视图通过项目—标签关联查询生成。相较于：
- 直接扫全部 target JSON：原型简单，但每次筛选重复扫描且缺乏稳定版本快照；
- 专用图数据库与图谱引擎：扩展能力强，但当前局部共享标签查询不足以支撑新增部署和维护。

首版无需图数据库。索引按文档/项目及提取版本更新；原文更新后旧关联失效，历史分析仍保留当次证据快照。

## 8. 普通资料分析：现成问题驱动

普通流程：选择库或项目 → 选择问题 → 确认已填好的范围 → 开始分析 → 查看结果及依据 → 保存分析结果。

### 8.1 首批问题卡

| 场景 | 预设问题 | 输出 |
| --- | --- | --- |
| 看项目分布 | 本库有哪些主要应用场景？各有多少项目？ | 按项目去重的索引统计、覆盖说明 |
| 看技术路线 | 这些项目主要采用哪些方法？ | 路线归纳、代表项目、原文 |
| 比较项目 | 这几个项目在问题、数据、技术、成果上有何异同？ | 对比卡片和来源，不直接排名 |
| 看已取得成果 | 哪些成果已经取得，哪些还在计划中？ | 分状态清单和量化条件 |
| 看变化 | 不同立项年份的项目关注点有什么变化？ | 年度统计事实＋有据解释 |
| 看薄弱点 | 已读资料中哪些问题尚未解决或证据不足？ | 已述困难、资料缺口与分析建议 |
| 形成报告 | 生成本范围的综合报告 | 既有报告模板与可编辑成果 |

问题卡通过已发布模板填写库名、年份或所选项目，不让用户编写 prompt。避免堆叠几十个按钮。管理员可以从现有任务编辑器维护少量预设模板，普通使用者只选择和执行。

### 8.2 统计与模型分析两条路径

全库项目数、经费合计、年度分布、四维关联计数使用完整有效索引计算。BM25 的前 3/5/8/10 个结果不能作为全库分母。

对背景解释、路线比较、趋势推断等问题继续使用预算内证据检索，明确“本次实际读取 X 个项目”。界面把“统计事实”“依据资料”“分析推断”分开展示，不把生成文字当作已建立的数据库统计。

项目勾选超过现有 API 限制时不截取前 20 个。后续通过服务器解析的范围引用传递年份/标签筛选，冻结实际成员；统计处理整个筛选范围，文本分析仍受预算限制。首批实施前明确范围接口与限制文案，不能只扩大 allowed_doc_ids 数字来声称全集可读。

## 9. 外部信息＋资料库分析

### 9.1 最短用户旅程

选择“分析外部材料” → 上传技术说明/方案，或粘贴简短描述 → 选择一个现成分析目的 → 选择库（页面可预选） → 检查范围 → 开始。

首版允许材料内容代替填写技术名称、目标和关键词。系统提取后显示可点击确认的摘要；必需内容缺失才请求补充一项明确问题，不让用户完成技术调查问卷。

外部材料是工作材料，默认不入库、不改变四维统计、不创建确认关系。提供的论断、指标与应用情况先按“材料自述”处理，不能借生成报告变成已证实事实。

### 9.2 四个分析目的

| 目的 | 要回答的内容 | 资料不足时 |
| --- | --- | --- |
| 技术背景 | 场景与待解决问题、相关路线、需要的前提 | 标出材料未说明与知识库未覆盖 |
| 国内外研究现状 | 国内资料、国外资料、路线对照、资料时间 | 自然科学基金库主要提供国内项目，不能自动凑出国外结论 |
| 可行性 | 技术路径、数据、指标、实验条件、资源与部署依赖 | 给条件性判断与需要补的证据，不代替真实试验 |
| 痛点/薄弱点 | 已述难点、关键假设、证据空白、可比较项目差异 | 区分客观问题、材料描述不足和检索覆盖不足 |

默认使用本地库；需要国外现状或政策资料时，可以追加用户上传的文献/官方材料，或明确选择“补充公开资料”。公开检索遵守现有受控来源范围并保存可回读快照，不为每次普通分析自动联网。

国内/国外分类以机构/资料中的明确地域信息为依据，未知保留未知，不能以中文/英文区分。项目立项时间不冒充论文发表时间或成果发生时间。网络抓取时间与发布时间分开显示。

### 9.3 结果模板

首屏显示：已知背景、主要对照发现、可行性条件、需补材料。后续按标题卡片列出：
- 本次外部材料摘要（自述）；
- 已核对的技术背景与研究现状；
- 与库内项目的对比；
- 条件性可行性判断；
- 痛点与薄弱点；
- 建议补充的材料及可点击的后续问题；
- 分析范围与来源清单。

卡片包含结论、证据、差异/限制和建议。用户可以只选一种目的，也可以选综合分析；无需按四个目的重复上传。

## 10. 填报审查：两个入口、两个业务场景

推荐将现有“形式审查”一级入口扩为“填报审查”，页内提供同级的“形式审查”“专业审查”两个明确入口。这是本次方案建议，实施前统一导航称呼；无需再增加两个一级导航。

进入任一入口先选择：
1. 自然科学基金项目申请；
2. 企业合作项目投标。

这两个业务场景绑定不同的材料模板、申报要求和发布版本，不能把基金条件自动套到企业投标。企业投标需指定合作方/采购方及项目文件；“企业合作”这一名称本身不足以推出规则。

形式与专业审查可以独立运行，形式未完全通过不一律禁止专业分析。材料无法读取或缺少主体技术内容时阻止相关执行，并明确说明原因。

两类结果分别保存，显示材料版本、规则/政策版本、资料范围与执行时间。当前旧流程含技术评议，不代表两个入口已经实现；新任务明确 formal / professional，形式任务不重复执行专业分析。

## 11. 材料包、预置模板与申报要求

### 11.1 材料包

建立最小“申报材料包”，按一个申报项目组织文件与已确认元信息：

| 材料槽位 | 要求 |
| --- | --- |
| 申报书正文 | 按大纲撰写的主文件 |
| 申报信息表 | 名称、负责人、参与单位、时间、资金、账户、成果等 |
| 附件 | 只在当前指南明确要求时收集，例如资质/专利证明 |

用户可一次多选上传，系统建议文件角色，用户点选确认。每个槽位明确“已收到/待补充/无法读取”，不能用文件名推断已经具备全部材料。首版正文与信息表采用 PDF/DOCX；信息表 XLSX 若为实际交付格式，单独补单元格定位，不用把 XLSX 伪装成 PDF 解析。

替换文件形成新版本，旧审查结果标记“基于旧材料”，不自动转为新材料通过。文件身份、hash 和有效角色都保留。两个审核入口共享材料包，避免重复上传和元信息互相覆盖。

正文与信息表名称/负责人/单位/预算不一致时显示并排候选及两边出处，不按“最新文件”自动覆盖。账号等字段只在本地作必要比对，默认掩码展示；不向技术分析模型发送完整账户信息。

### 11.2 模板与要求分别管理

“申报书模板”约束大纲、格式和填写位置；“申报要求”约束资格、材料清单、期限、数量和金额。发布为一个可选择的要求包，引用原指南和相应模板版本。

规则至少带：业务场景、发布方、年度/批次、适用类别、原文条款与定位、检查对象、方法、单位、适用条件及发布版本。采用现有草稿→核对→启用流程，普通使用者不编辑规则。

纪要中的学历不低于本科、参与单位需含高校且不超过 5 家、预算不超过 500 万、专利成果不少于 3 项，均作为**演示条件**。真实门槛来自具体要求文件；“专利 3 篇”需核对计量对象及单位，不能与论文数量混为一谈。模板未绑定真实条款时显示“示例要求”，不得输出政策合规结论。

## 12. 形式审查 pipeline

流程：材料完整性 → 解析与定位 → 规则适用性 → 可确定的程序检查 → 有证据的语义核对 → 跨材料一致性 → 按大纲生成问题卡。

### 12.1 检查类型与执行方法

| 检查 | 主要方法 | 不能自动确认的边界 |
| --- | --- | --- |
| 文件类型、大小、加密、可读取性 | 服务端实际文件/字节检查 | 扩展名不能代表真实文档类型 |
| 正文与信息表是否齐全 | 已确认材料角色和清单 | 文件名相似不能证明材料完整 |
| 大纲章节是否存在、顺序、必填位置 | 提取结构＋明确的章节别名 | 标题同义或复杂排版不确定时待核实 |
| 字数/字符数 | 按条款明确的计数范围与单位 | 不把字符数当词数，不假设标题/表格/参考文献是否计入 |
| 篇幅页数 | PDF 真实页数；DOCX 需稳定排版渲染 | 现有文本块数不能冒充 DOCX 页数 |
| 字体、字号、行距 | DOCX 有效样式解析；PDF 可确认的文字布局属性 | 扫描件、样式继承不明、缺字体时不能判合格 |
| 学历资格 | 结构化字段＋条款认可的资格类型 | 缺少证明不能宣称学历真实性；不得只匹配“本科”关键词 |
| 单位数量与高校条件 | 明确单位列表去重＋单位类型依据 | 名称包含“大学”不等于已核实单位性质 |
| 截止时间 | 指南时区/截止时间与可核验申报时间比对 | 填表日期、上传本工具时间不等于正式申报时间 |
| 预算上限与汇总 | Decimal、单位转换、条款上限与跨表校对 | 申请经费/总预算/直接费用必须先确定口径 |
| 专利数量及状态 | 去重的专利号、状态、要求日期及归属 | 申请/公开/授权不混计，重复列示不重复计数 |
| 正文与信息表一致性 | 同字段双边证据 | 冲突显示两边原值，不自行选择 |

执行器按实际检查类型实现，不建设任意代码规则或万能 DSL。模型负责定位、解释和语义核对，算术、大小、数量与时间比较由可复核程序处理。暂不支持的检查明确标“未检查”，不能换成模型猜测通过。

### 12.2 四种结果状态

- **发现问题**：已取得足够证据且明确违反当前适用要求；
- **需要核实**：存在缺失、冲突、识别不确定或证明不足；
- **已核对通过**：本项检查确已执行且证据支持；
- **未检查/不适用**：区分能力未覆盖与条件不适用，不能计入通过。

整体页面显示各状态数量和覆盖，不自动给“申报合规”总章。缺信息表属于缺少要求材料；信息表已收到但字段无法识别属于识别不足，两者提示不同。

截止日期只有日没有时分、时区不清或申报时间缺乏来源时标待核实。比较是否含截止当日也按条款，不把纪要“之前”静默解释成任意统一规则。

### 12.3 按大纲与文本框展示

主区左侧是正文大纲/信息表字段列表，主区正文为标题卡片，右侧沿用统一原文检查器。卡片显示“当前位置—具体问题—要求—原文—修改建议”。

例如：
- 研究目标：未写出可核查的技术指标；定位正文段落；
- 项目预算：信息表填写 520 万元，当前示例要求上限 500 万元；双边字段与条款；
- 参与单位：已确认 6 家，超过示例上限 5 家；提供计数列表；
- 专利成果：三条记录中两条是同一专利；提供去重依据。

仅在原文件及版本、段落/单元格和引文定位可靠时高亮。PDF 使用物理页，DOCX 使用段落/表格单元格；不能伪造页码。不能精确定位时提供对应章节和引文，不放置错误高亮。

高亮使用红/橙等问题提示与文字标签，绿色表示已核对。四维红蓝绿黄表示分类，二者在不同视图配明确图例，避免“红色场景=错误”的误解。

## 13. 专业审查 pipeline

流程：提取技术主张 → 查找可比项目 → 对照背景与方法 → 核对选定政策/规划资料 → 检查先进性与必要性依据 → 组织问题与建议。

### 13.1 技术主张与候选项目

提取场景、要解决的问题、拟用方法、数据来源、预期指标、对照方法、已有基础和主要依赖，每项附材料中的出处。缺失就标缺失，不要求用户自行输入技术关键词。

按主张组织多条检索查询，先在选定库内召回，再逐一核对候选全文/片段。BM25 分数用来找候选，不能作为重复工作判定或先进性评分。需要语义检索时以真实样本验证增益，再采用已配置的 embedding；不把更换模型当作无需验证的默认答案。

每个相近项目展示“相同点、不同点、目前无法判断的点”，至少比较目标、对象、数据、方法、指标与验证条件。已有项目的预期成果不作为已完成技术基线。

### 13.2 输出的六个维度

| 维度 | 要核对什么 | 结果语言 |
| --- | --- | --- |
| 相近工作与差异 | 是否已有相同问题/路线，申请书是否交代差异 | 存在相近项目，建议补充差异说明；不能直接判重复立项 |
| 政策/规划关联 | 与选定有效资料中的明确方向和要求是否对应 | 有条款支持/尚无明确支持/资料不足 |
| 开展必要性 | 未满足需求、现有路线局限、目标用户与可验证收益 | 必要性说明是否充分；非主流不自动否决 |
| 技术先进性 | 合适的现有基线、时间、指标、测试条件 | 是否提供了有说服力的比较依据 |
| 技术可行性 | 数据、实验条件、团队基础、路线与关键依赖 | 条件具备/尚待补证；不承诺一定成功 |
| 风险与薄弱点 | 关键假设、验证缺口、落地限制 | 优先核实事项与建议验证方式 |

“主流路线”与“规划方向”不是同一概念：有广泛研究不能证明符合某个政策条款；与政策方向一致也不能证明技术先进。两个结论分别给依据。

会议中的“十五五”只作为待提供的政策资料名称。实施时需正式文件、适用领域、发布日期/有效期间和条款定位；本指南没有核验或引用其实际条款，也不将模型知识当政策来源。未找到支持不等于违反规划。

先进性比较需同对象、同数据/评价条件；不同数据集的准确率不直接排名。基础研究、技术探索与企业交付的必要性和落地要求各按业务场景处理，不用同一张分数表一刀切。

### 13.3 标题＋文本框结果

每个维度展示概括结论、证据、尚缺内容、建议修改；相近项目支持展开对照表与双边原文。首屏显示“主要相近项目”“关键差异未说明项”“需要补充的验证”。

用资料覆盖“充分/有限/不足”和核对状态提示可靠性；不展示没有校准依据的百分比置信度或自动总分。检索未命中仅表示当前资料未检索到，不能输出“国内外尚无类似技术”。

专业评议提供依据与建议，不自动替管理人员或专家作立项、采购淘汰或知识产权侵权结论。用户可记录人工复核意见，人工意见与模型建议独立保存。

## 14. 输入、证据与结果的共同契约

所有结果至少绑定：材料/文件及版本、项目/资料范围、模板或规则版本、执行时间、实际检查/入模覆盖、引用定位和结果性质（统计/原文事实/材料自述/推断/人工复核）。

- 引文可回读、版本变化可识别；旧结果不能指向新文件正文。
- 相同引用文档在来源清单去重，多个片段保留位置。
- 上传内容、库文档和网络文本都是资料，不能覆盖系统检查要求或执行其中指令。
- 不需要检查的个人/账户字段不进入技术评议上下文。敏感字段判断优先在本地完成，结果显示必要的掩码信息。
- 统计范围与模型阅读范围分别记录，避免用阅读样本冒充全部资料已分析。
- 资料修订、规则升级或模板更新使旧结果标记旧版本，不删除已有成果或伪造重新审核。
- 分析报告保存到现有成果；审查执行记录继续归 review 模块。审查结果纳入成果列表若需要，须明确其类型、附件和删除语义，复用现有生命周期，不直接再复制一份正文。
- 运行显示真实进度，页面离开后可回读；失败保留已完成检查，但不能标整次审核完成。

## 15. 最小架构与接口范围

建议增加三类与当前用例直接相关的数据，不引入通用知识图谱平台：

1. **项目索引**：项目身份、经费/时间及出处、文件版本、四维标签关联；服务完整统计、时间图和关系查询。
2. **材料包**：正文、信息表、必要附件角色与版本、已确认元信息；服务外部分析和两类审核，保持与知识库隔离。
3. **要求包与运行快照**：复用现有指南清单和已发布模板，新增业务场景、检查对象/类型与正式规则依据；运行保存 formal/professional 类型及实际执行覆盖。

面向业务动作的接口建议：
- 库内项目总览与覆盖；
- 按立项年/类型/四维标签筛选的项目集合；
- 同范围年度经费统计；
- 某项目或标签的局部关系及双边证据；
- 工作材料上传/角色确认及版本；
- 预设问题与按已确认范围发起分析；
- 基于材料包分别发起形式/专业审核，回读执行与定位。

沿用当前 FastAPI、SQLite、React Router、Query 和统一检查器。跨组件只传项目/材料/运行 ID，不再在多个页面复制正文或互相维护第二套筛选状态。

新增 rule check_type 面向实际执行器，旧 method=model/calculation/manual 继续表示执行方式；两者不要混成一个万能字段。已有历史综合预审保留当时结果说明，新运行仅有形式与专业两种明确类型；移除旧“同时完成全部”的执行入口，不再维持两套新旧任务引擎。

图形首版优先复用现有浏览器/SVG 能力和列表，不先引入大型图形编辑库。性能取舍按当前 517/510 项目实际数据测量后决定；视图加载不能逐节点调用模型或渲染全库两两边。

## 16. 分批实施与退出依据

以下为推荐执行顺序。各批交付一条可运行的用户旅程，不先做数轮纯框架迁移。

| 批次 | 主要工作 | 完成依据 |
| --- | --- | --- |
| M1 四维归纳与点击分析 | 先完成基金体系/批准号/文件关联/待核对的最小项目索引，再做项目去重、覆盖和确定性四维聚合、代表项目、预设问题及范围摘要 | 选库→维度→条目→项目→原文→返回→点击问题；计数与范围一致 |
| M2 时间与经费 | 字段来源/口径核对、按立项年统计、交互散点与缺失列表 | 同项目多文件只计一次；2021—2025 放在 2021；缺金额不当 0；图与列表一致 |
| M3 项目关系与外部分析 | 局部项目—标签图、双边证据；上传材料与四目的模板 | 图边可解释且版本有效；外部自述与本库证据区分；无国外资料时如实提示 |
| M4 双材料形式审核 | 两个业务预置、正文/表材料包、实际可执行规则、按大纲问题卡 | 上传→角色确认→要求包→审核→正文/字段问题与定位；缺证据不假通过 |
| M5 独立专业审核 | 技术主张、可比项目、政策资料包、必要性与先进性对照 | 专业入口独立；两边证据可读；非主流不自动否决；未命中不宣称唯一 |

M4 的材料包基础可与 M3 共用，但不为未来格式扩展先建设通用文档发布平台。已有形式审查不能因为尚缺所有规则就隐藏：先声明支持范围，再按真实指南补检查类型。

每类先取少量已核对样本：同项目多文件/经费冲突；缺金额和未知币种；有/无四维；相同标签但技术条件不同；正文与表信息冲突；格式不可验证；存在明确相近项目但有实质差异。样本应能推翻错误设计，不用随机几份绿色结果充当完成。

## 17. 验收旅程与具体失败

优先扩展已有 target facets、任务、成果和审查浏览器旅程，接口/文件/计算使用真实存储与解析。当前单材料审查无法覆盖双文件规则时，再增加一条材料包端到端旅程，不逐字段补同义测试。

| 旅程 | 必须区分的失败 |
| --- | --- |
| 两个文件同批准号，四维标签重复；筛选后查看计数 | 把文档数当项目数，重复成果计数，分母不跟筛选 |
| 立项 2021、结束 2025；资金 200 万与 2000000 元；还有缺资金项目 | 起止口径错误、单位错误、缺金额变零 |
| 点击散点/关系边→证据→返回→重置 | 视图状态丢失、误改任务范围、定位到错误文件 |
| 同名技术不同数据/条件；相近名称尚未确认 | 把同名当等价路线，把模型建议当事实关系 |
| 点击预设问题，筛选 50 个项目 | 静默截取 API 前 20 个、拿 top-k 算全库统计 |
| 外部材料称指标领先，但库证据不足或无国外资料 | 自述变事实、编造国外现状或先进性 |
| 正文＋信息表单位/预算/负责人不一致 | 自动覆盖冲突、把一个文件当完整申报包 |
| 示例 500 万上限，但实际要求包另有标准；模板跨年度 | 硬编码纪要门槛、使用错年度/场景规则 |
| DOCX 文本块 30 个；扫描 PDF 无字体；同日截止无时间来源 | 假页数、假字体通过、错误截止判定 |
| 专利重复号、申请与授权混合、附证明缺失 | 重复计数、无证据确认资格 |
| 专业审查未命中；或偏离选定规划但必要性证据充分 | 未命中=原创、非主流=不准开展 |
| 修订文件或规则后回读旧结果 | 旧核对冒充新版本，通过错误的原文定位 |

操作人员验收应使用现成问题和鼠标点击完成三个核心旅程；观察其是否能理解范围、状态和下一步。页面视觉好看不能替代原文准确、计数正确和检查执行覆盖。

## 18. 需要对接方提供的最小材料

不阻塞本轮需求展开；下列材料决定实际验收标准，实施对应检查前需获得：

1. 自然科学基金、企业投标各一套真实年度/批次的申报书模板、信息表、指南和必要附件清单；优先一套现用版本，不收集所有历史版本作为首版前置。
2. 资助金额的展示口径：批准资助、总经费还是直接费用；给几份来源示例及冲突项目。
3. 企业合作投标的发布方/采购方、具体项目与截止时间来源，不能用基金示例代替。
4. 专业审查要采用的正式政策/规划材料，以及对接方认可的技术比较样本；包含“很相近但并非重复”的案例。
5. 实际交付格式，尤其信息表是否为 XLSX、正文是否必须核对真实页数和字体；没有原格式不能承诺完整版式检查。
6. 当前使用者常用屏幕与是否需要只读打印；先观察现有使用环境，不设计多终端全功能同步。

本方案默认先落地可确定的四维归纳、项目统计和点击分析；时间经费须先补字段依据，关系图须先补索引；规则和专业结论须绑定真实资料。上述输入缺失时交付明确的支持范围，不伪造“全部已支持”。


审核修订（2026-09-30）：多文件汇总、统计分母、输入版本持久化、独立运行类型、确定性执行器及反例验收，以正式需求第 13 节为准。项目身份先于四维统计；真实规则未经样例核对不标业务验收通过。
