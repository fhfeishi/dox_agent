## 1. 项目定位与范围

基于已复制到本仓库的源码（原 static1 的 Agentic RAG 实现），收敛为小型、专业化的 Agentic Chatbot，面向国家自然科学基金、省重点、省重大、面上项目等科研项目的可检索历史报告，提供专业知识问答、专项报告生成、本地目录浏览与 PDF 原文阅读。

基金名称、主管机构和项目类别按实际材料记录，不预设所有"省重大"等项目属于同一基金体系。

首期默认单用户、本地服务、已有本地报告库。可检索历史报告是数据前提，并不意味着自动获得基金数据库访问权限；本期不新增外部数据库接入、全网爬取或自动同步。

核心交付只有三项：

1. 对报告库进行带来源的专业问答，支持多轮追问和有限补充检索。
2. 按领域、时间范围和模板生成成果介绍、研究热点、未来研究方向及综合分析文档。
3. 网页右侧滑出资料窗口，展示本地目录，点击文件查看 PDF，点击引用跳转原文页。

现状依据：`src/main.py`、`src/agent/*.py`、`src/knowledge.py`、`src/dense.py`、`src/official_docs.py`、`src/parsers.py`、`src/workspace.py`、`frontend/src/*`、`launch.sh`、`.env.example`。复制前的系统设计见 `dev_logs/archive/static1_design/API_PIPELINE.md`。

- **技术栈**：后端 Python/FastAPI + LangGraph/Deep Agents；SQLite 保存原文与版本；BM25Plus 稀疏检索；可选本地 HuggingFace embedding + Chroma，并与 BM25 做 RRF 融合。前端 React 19 + TypeScript + Tailwind 4 + Vite 7。

- **现有 HTTP 接口**：
  - `GET /api/health`、`GET /api/documents`、`GET /api/documents/{doc_id}`（`page`、`start_line`、`version`、`section`）
  - `POST /api/ingest/local`、`POST /api/ingest/text`
  - `GET|POST /api/official-docs`
  - `POST /api/web/preview`、`POST /api/web/confirm/{preview_id}`
  - `POST /api/chat`（SSE）
  - `GET /api/workspace/{sessions|notes}`、`PUT /api/workspace/{sessions|notes}/{key}`

- **现有前端能力**：多会话保存/恢复、重命名/归档、问题编辑分叉、停止/重新生成/复制、耗时与 token、来源展示、资料范围选择、本地导入与网页预览、官方文档更新。PDF 阅读器、目录树、报告界面**尚未实现**。
- **未挂载组件**：`frontend/src/Notes.tsx` 已存在，但未挂载到 `main.tsx` 主界面。

### 2.2 目标差距

下表是后续变更要求，不表示当前已完成。

| 能力 | 现状 | 目标 |
|---|---|---|
| 专业问答、检索与原文阅读 | 已有 search/read、引用及有限补查机制，语料为官方技术文档 | 保留机制，语料切换为科学基金历史报告 |
| 问题分类 | 有社交/通用/资料等意图分类与 `query_routing` 分支 | 移除自动分类分支与分类模型调用；改由 §9.3 用户显式选择任务（task1–4）决定回答职责；二者不是同一机制 |
| 回答范围、材料遵循等级 | 有前端"回答范围"和"证据要求"选项，以及 `query_routing`、`evidence_level` 字段 | 删除对应前端选项及新契约中的 `query_routing`、`evidence_level`；统一执行基于本地报告的专业回答 |
| 非专业问题 | 由分类分支与统一职责说明处理 | 只保留统一职责说明，不建设其他问答能力或独立识别服务 |
| 资料选择 | 有可选 `allowed_doc_ids` 指定文件范围 | 保留该过滤条件；它是检索过滤条件，不是"材料遵循等级" |
| 快速/深入研究选择 | 有 `execution_mode`（auto/quick/research）选项 | 首期不暴露执行模式选项，服务端使用固定的有限研究流程与预算 |
| 会话与流式交互 | 已有会话历史、流式回答、停止、重新生成、复制、真实检索/阅读状态和错误提示 | 保留 |
| 官方文档导入、网页采集、笔记导航 | 已有 `/api/official-docs`、网页预览确认、`Notes.tsx`（未挂载） | 不纳入本项目主界面与首期验收；本轮不删除旧代码 |
| 领域和时间筛选 | 无 | 增补元数据及检索前过滤，问答和报告共用 |
| 本地文档界面 | 无目录树、无原始文件服务、无右侧预览窗口 | 增补目录树、原始 PDF/Markdown 文件服务、右侧预览窗口和引用跳页 |
| 报告生成 | 无统一生成入口 | 增补一个通用生成入口，使用模板区分文档类型，无须为三种报告建立三套 Agent |

自动意图分类与显式任务选择是两种机制：前者由模型猜测并在代码中分支，本期移除；后者由用户在会话创建时明确选择并加载对应提示词，不新增分类模型调用，也不建设独立分类服务（对应 §8.2 的"首期不做"）。

取消"材料遵循"配置不取消事实引用：具体成果、数据和应用情况须能追溯原文；未来方向可以综合推断，但必须与已证实事实分开表达。

## 3. 专业知识问答

- 支持单报告查询、多报告对比、领域进展、方法与应用分析，以及基于上下文的追问。
- 固定流程：解析专业问题 → 在限定范围检索 → 阅读原文 → 必要时有限补查 → 带引用回答。
- 每条关键事实标注来源文件和 PDF 页码，能够直接打开原文。
- 无资料、资料冲突或解析失败时明确说明；不把未检索到解释成该领域不存在相关成果。
- 展示实际执行阶段，不展示或虚构模型内部思维过程。
- 回答职责由 §9.3 的用户显式任务（task1–4）决定；本期不做自动意图分类。
- 沿用现有搜索次数、模型调用和超时限制；无需增加多 Agent、规划平台或工作流编辑器。

## 4. 专项报告与分析文档

### 4.1 输入与输出

必填：研究领域、起止年份、报告模板。可选：基金/项目类别、指定报告文件、分析重点。分析文档复用同一入口，不另建子系统。

首期提供四个模板：

| 模板标识 | 内容 |
|---|---|
| `achievements` | 研究进展、代表性成果、关键技术/方法、应用领域及实际应用证据 |
| `hotspots` | 主要研究主题、代表项目和成果、不同阶段变化、尚存问题 |
| `future_directions` | 已有基础、研究空白、可能方向、推断依据与局限 |
| `comprehensive` | 成果、热点、未来方向合并形成专项分析报告 |

输出采用 Markdown，支持网页预览、复制和 `.md` 下载。原始资料的 PDF 预览属于首期必需；生成报告导出 PDF/Word 暂不作为首期必需，避免混淆两个需求。

报告附带领域、时间口径、基金筛选条件、模板版本、实际使用的来源及页码、生成时间和资料局限。

### 4.2 时间与数据口径

- 首期默认按报告年份筛选，使用包含起止年份的闭区间；文件修改时间不得替代报告年份。
- 报告年份范围与成果实际发生时间分别表达。例如 2024 年报告回顾 2020 年成果，不能自动称为 2024 年新成果。
- 年份缺失的资料不混入严格年份筛选结果，提示需要补录；年份信息不可靠时明确标注。
- 领域可采用人工维护标签结合关键词检索，不建设学科本体或知识图谱。
- 基础元数据：文档 ID、标题、相对目录、报告年份、领域标签、基金/项目类别、内容版本、解析状态；项目编号存在时记录，用于识别同一项目的重复报告。
- 首期允许通过简单元数据清单补录，不额外开发复杂标注管理平台。

### 4.3 最小生成流程

筛选资料 → 按模板章节检索并阅读 → 汇集带页码证据 → 用模板提示词生成 → 核对引用有效性 → 保存与展示。

模板可以控制结构、语气和分析重点，但不能代替领域/时间过滤、证据读取和引用绑定。只取一次全库 Top-K 后直接生成整份报告，可能遗漏重要项目；应复用现有检索能力，按章节适量补查，并记录实际覆盖资料。达到预算后说明覆盖局限，不另建复杂研究框架。

"热点"默认指当前可用报告样本呈现的主题，不声称代表整个学科。若输出主题频次，须基于实际统计、说明分母并按项目去重，不能让模型编造热度或趋势数字。未来方向表述为基于材料的分析建议，不是确定预测。潜在应用与已经落地应用分别说明。

### 4.4 提示词模板基线

模板保存为少量服务端文本配置，首期不开发模板管理平台。通用要求如下：

```text
你是科学基金历史报告研究助手。
请基于提供的原文证据，生成《{领域}领域{开始年份}—{结束年份}{报告类型}》。
时间口径：报告年份；基金/项目类别：{筛选条件}。
分析重点：{用户补充要求}。

按模板章节组织正文，每个关键事实引用给定的来源编号与 PDF 页码。
区分已取得成果、已实现应用、潜在应用和未来方向推断。
不得将申请目标、计划工作或预期成果写成已经完成的成果。
同一项目多份报告中的重复成果不得重复计数。
不生成证据中没有的数字、项目编号、论文、专利或引用。
资料不足或存在冲突时说明；热点结论限定于本次资料样本。
最后列出资料范围、来源清单与分析局限。

模板章节：{模板章节}
可引用原文证据：{证据及来源信息}
```

## 5. 右侧本地文档窗口

- 主页面保留聊天区域，右上方提供"本地文档"入口，点击滑出右侧窗口。
- 文档类型包括 PDF、Markdown 与 txt；PDF 用阅读器，Markdown 渲染并可查看原文。
- 窗口展示配置的报告根目录下的真实相对目录结构，可展开/折叠并按文件名筛选。
- 点击文件名，在网页内打开预览；PDF 支持页码、翻页和缩放；关闭窗口不丢失聊天上下文。
- 点击回答或报告中的引用，打开相应 PDF 并定位物理页码。页内高亮后续按需要增加。
- 浏览文件与限定问答范围是两个操作：单纯打开 PDF 不自动改变检索范围，限定资料时显示已选文件。
- 目录显示未入库或解析失败状态。PDF 可预览但不可检索时如实提示，不把预览成功视为入库成功。
- 文件不存在、原文版本变化时明确提示，不能将新版原文当作旧答案的原始证据。
- "本地"指后端可访问的报告目录；浏览器通过服务接口读取 PDF，不直接读取任意电脑路径。
- 文件接口仅允许读取配置根目录内的资料，用文档 ID 映射文件；路径穿越和指向根目录外的链接不可访问。

优先使用 PDF.js 阅读器。现有逐页文本读取接口提供检索证据，不等于原始 PDF 预览接口，两者需要分别保留。

## 6. 目标接口契约（尚未实现）

优先复用现有接口；以下路径是后续目标契约，不表示现在可以调用。

| 接口 | 目标用途与最小参数 |
|---|---|
| `POST /api/chat` | 复用流式聊天；保留 messages/run_id，新增 task_id（task1–3）与 filters（domain/year_from/year_to/fund_types），可选 allowed_doc_ids；不再要求 query_routing/evidence_level/execution_mode；**task4 不在 chat 生成**，转 `POST /api/reports` |
| `GET /api/tasks` | 返回任务列表（id/name/description/是否有模板）；首期固定四项，不新增模板 CRUD |
| `GET /api/documents` | 扩展现有列表，返回相对路径、元数据和入库状态，前端构建目录树，无须另设目录服务 |
| `GET /api/documents/{doc_id}` | 保留现有原文证据读取与版本核验 |
| `GET /api/documents/{doc_id}/file` | 新增原始 PDF 响应；支持阅读器需要的文件读取，接受可选版本校验 |
| `POST /api/ingest/local` | 复用本地导入/更新，补充元数据读取与解析状态 |
| `POST /api/reports` | 新增统一生成入口：domain、year_from、year_to、template_id，可选 fund_types/doc_ids/focus；流式返回阶段、正文、来源和最终 report_id |
| `GET /api/reports/{report_id}` | 读取已保存的 Markdown、参数、模板版本与引用，供预览和下载 |
| 现有会话与健康接口 | 保留，供历史恢复及服务/知识库状态显示 |

filters 使用与报告相同的领域、年份和基金类别口径。检索范围在搜索与阅读中始终一致，不能搜索时限定、补查时扩展到范围外。

模板列表首期由前后端约定固定四项，不新增模板 CRUD 接口。报告首期沿用请求式流处理，不引入任务队列；取消或失败保留未完成标记，不承诺后台续跑。只有成功完成后返回可正常获取的报告 ID。

报告与引用信息复用现有 SQLite 存储方式即可，不增加新的数据库或对象存储服务。缺少必填范围或模板未知应返回明确输入错误；没有匹配资料时不生成伪报告。

## 7. 开源工作调研

调研日期：2026-09-21。以下能力依据项目官方仓库/README，未在本机安装运行，不能视作完成兼容性或中文基金报告效果验证。适配成本为结合 dox_agent 现有技术栈（复制自 static1）的判断。

| 项目与官方来源 | 已公开能力 | 本项目适用方式 | 适配缺口/取舍 |
|---|---|---|---|
| [Kotaemon](https://github.com/Cinnamon/kotaemon) | 文档问答、混合检索、Agent 推理、带高亮的浏览器 PDF 引用预览 | 优先参考"问答—引用—PDF"交互，最接近专业资料问答体验 | UI 基于 Gradio；不直接替换现有 React。基金元数据、真实目录树和专项模板仍需适配 |
| [GPT Researcher](https://github.com/assafelovic/gpt-researcher) | 基于网页和本地文档生成带来源的研究报告，支持报告导出 | 优先参考报告结构、来源汇总和本地资料研究 | 本项目限定本地语料；不引入其完整多 Agent/联网研究体系。年份口径和基金筛选仍需实现 |
| [PDF.js](https://github.com/mozilla/pdf.js) | Mozilla 支持的浏览器 PDF 解析与渲染阅读器 | 可直接作为右侧 PDF 阅读组件基础 | 只负责阅读；目录、文件接口、文档 ID 与引用页码映射由本项目提供 |
| [RAGFlow](https://github.com/infiniflow/ragflow) | 文档理解、RAG 与 Agent 平台 | 作为复杂 PDF 解析与知识库能力备选参考 | 官方列出至少 4 核 CPU、16 GB 内存、50 GB 磁盘及 Docker 等前提；对当前小型增量项目较重，不建议整体迁移 |

Kotaemon、GPT Researcher 与 PDF.js 的仓库页面均标示 Apache-2.0；实际复用时保留相应许可声明，并按选定版本核对依赖。本文不依赖星数或未经核验的性能排名。

结论：已有开源工作分别覆盖核心能力，但本次核查没有确认一个项目能无需适配地满足全部基金业务口径。建议保留 dox_agent 现有技术栈（Python/FastAPI + LangGraph/Deep Agents + React/TypeScript），参考 Kotaemon 的交互和 GPT Researcher 的报告组织，采用 PDF.js 补齐阅读器；不将四套系统同时集成。

## 8. 实施顺序、验收与遗留清理

### 8.1 实施顺序

后续实施建议按三个小步骤推进：

1. 收敛专业问答入口，补齐资料元数据、目录树、PDF 预览与引用跳页。
2. 增加统一报告入口和四个提示词模板，支持预览与 Markdown 下载。
3. 用真实基金报告验收领域/时间范围、引用和内容质量，针对失败样例调整。

### 8.2 首期验收标准

- 界面不出现问题分类、材料遵循等级和通用闲聊入口；专业问题可以多轮追问。
- 右侧目录与配置目录一致，中文文件名和多级目录正常展示；点击可打开对应 PDF。
- 引用定位正确文件和物理页码；引用失效有明确提示。
- 给定领域和年份生成四类文档，包含范围、正文、来源与局限。
- 用包含范围外年份、年份缺失、重复项目的样本验证筛选与去重；不得混入范围外事实或虚增成果数量。
- 对计划目标、已取得成果、已落地应用、未来推断能够正确区分。
- 无匹配材料时如实提示；停止、失败、重新生成及会话恢复状态可辨认。
- 中文扫描 PDF 和复杂表格需用真实样本检查解析质量，不能用英文 PDF 的既有验证替代。

首期不做：多租户/权限后台、多 Agent 协作、知识图谱、工作流画布、独立问题分类服务、材料遵循等级系统、自动全网研究、自动订阅同步、模板管理平台和分布式任务队列。

待真实样本提供后细化的事项：报告数量与页数、扫描件占比、元数据完备度、是否改用项目执行期作为时间口径、是否必须交付 Word/PDF。以上不阻碍当前需求整理；首期暂按本文默认口径执行。

## 9. 功能更新（2026-09-21 15:09）

### 9.1 定位补充

dox_agent 定位为成熟的 Agentic ChatBot，参考 ChatGPT 的会话体验，自动完善会话管理职责：左侧边栏的会话新建、历史列表、重命名、归档/恢复、分支与任务标签，并让每个会话绑定明确的回答职责。

### 9.2 本地文档展示与预览（扩展 §5）

- 本地文档类型明确为 PDF、Markdown（兼容 txt）。
- 主界面提供简单入口，点击后在右侧滑出窗口预览本地文档。
- 预览窗口包含真实的相对目录树与文件预览（PDF 阅读器、Markdown 渲染），关闭窗口不丢聊天上下文。
- 点击回答/报告中的引用，在预览窗口中打开对应文件并定位物理页码。
- 浏览文件与限定检索范围仍是两个操作，浏览不自动改变检索范围。

### 9.3 任务系统与提示词（新增）

- 定义四类任务：`task1` 精准问答、`task2` 对比分析、`task3` 趋势推测、`task4` 专项报告。
- 每个会话绑定一个任务；左侧 "+" 打开任务选择（单选列表，可带勾选态样式），选中后切换到对应任务的 prompting。
- 任务提示词归置于源码 `src/prompts/`（共享基线 + 各任务提示词），服务端加载，首期不做模板管理平台。
- 任务边界：`task3` 用于聊天式、不落盘的趋势讨论；`task4` 用于生成可保存的结构化报告，复用 §4 的四个报告模板（`achievements`/`hotspots`/`future_directions`/`comprehensive`）。需要留存的结构化输出一律走 `task4`。
- `task4` 不在 `POST /api/chat` 生成正文：选择 task4 后进入报告表单，生成统一走 `POST /api/reports`（§6），结果作为会话中的报告记录展示。
- 任务取代已被移除的 `query_routing`/`evidence_level`/`execution_mode` 的策略角色；事实引用、事实/推断分离等硬约束不因任务切换而取消。
