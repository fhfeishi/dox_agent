## 1. 系统：五个对象，一个运行服务

### 1.1 核心对象（唯一来源）

| 对象 | 身份 | 生命周期 | 唯一存储 | 现有代码 |
|---|---|---|---|---|
| 资料库 Library | `corpus_id` | 新建 → 导入中 → 可用 → 删除 | `corpora.json` + 库目录 | `agent/corpora.py`、`knowledge.py` |
| 资料 / 项目 Document / Project | `doc_id@version`；项目由 `project_index` 归并 | 上传 → 解析 → 可检索 → 归纳 → 过期 | `knowledge.sqlite3`（每库一个）、`project_index` | `parsers.py`、`targets.py`、`project_index.py` |
| 任务定义与执行 | `task_id`标识定义，`run_id`标识执行，绑定模板版本 | 定义：草稿/发布；执行：排队 → 运行 → 完成/失败/中断 | 应用库 `tasks`、`runs` | `custom_tasks.py`、`runs.py`、`reports.py`、`intelligence.py`、`period_summary.py` |
| 成果 Artifact | `artifact_id@version` | 生成 → 编辑版本 → 导出/发布 → 回收 → 清理 | 应用库 `artifacts` | `artifacts.py` |
| 证据 Citation | `corpus_id/doc_id@version#location` | 跟随成果版本冻结 | 写在成果版本中 | `citation` 相关代码 |

约束：

- 普通报告、回答快照、情报分析、周期总结继续用Artifact正文与版本。审查报告通过统一成果入口展示，其条款、计量和复核结果仍由审查领域唯一持有，不转换成Markdown后丢失结构。
- 统一Run持有执行身份、状态与进度，关联审查明细；如增加成果索引，通过review_run_id关联，不复制可独立修改的结论。
- task_id表示任务定义，run_id表示一次执行；模板草稿/发布与运行排队/完成分开，不混用生命周期。
- 每个对象只有一个存储位置。迁移完成后，被替代的表和读路径一并删除。

### 1.2 工作上下文（WorkContext）

```
WorkContext = { browsing_corpus, scope: { corpus_ids, doc_ids@version, source: "auto"|"manual" },
                task_type, question, template_version }
```

- `browsing_corpus` 是当前正在浏览的库，`scope` 是本次分析的范围，两者在类型上分开。浏览一个库不等于本次分析用这个库。
- 入口只负责预填，执行路径只有一条：
  - 资料列表选中后点“对比所选”，预填 `scope`；
  - 存量分析卡片预填 `task_type`；
  - 对话直接输入问题，由系统推荐范围。
  - 预填后都调用同一个 `POST /api/tasks/{type}/runs`。
- 已提交任务的上下文保存在服务端（Run 记录中），刷新或换设备都能恢复。面板宽度、滚动位置等只放在浏览器本地。

### 1.3 运行服务（解决 E-01）

| 方案 | 收益 | 代价 | 适用 |
|---|---|---|---|
| A. 进程内任务运行器：持久化 `jobs` 表 + asyncio worker；前端通过 SSE 订阅，断开后可以重新订阅 | 不加依赖；离开不中止；重启后标记中断并允许重试 | 单进程，无法横向扩展 | 单机本地部署（当前与 2-product-demo） |
| B. 外部队列（RQ/Celery + Redis） | 可以多进程、多机 | 新增服务和运维，Windows 一键启动变复杂 | v0 之后确有并发需求时 |
| C. 维持现状，只在流式代码里补断线重连 | 改动最小 | 三套执行模型继续并存，E-01 只能被掩盖 | 不推荐 |

推荐 A。统一运行契约，异步与受控线程分别承担适合的工作，阻塞解析不直接占用事件循环。长任务按批接入：对话回答、报告、存量分析、情报分析、周期总结、审查、导入、四维提取。运行状态包括：排队、运行中、完成、失败、中断（重启时发现未完成的运行）、取消。重试前提示用户会再次调用模型。

先持久化运行与冻结输入再交给worker；重复提交复用或明确拒绝，结果保存避免重复成果。SSE断线后可读取当前快照及续接进度，关闭订阅不代表取消。取消需明确合作式停止边界，不能只改状态而后台仍在收费；停机、超时、来源变更、完成但通知未送达分别验收。

成立的前提：当前是单机单进程部署（README、launch 脚本）。如果 v0 要支持千人并发，再从 A 升级到 B，到时接口不需要变化。

### 1.4 存储（解决 E-03）

| 方案 | 收益 | 代价 |
|---|---|---|
| A. 维持多个文件，各自加 `user_version` 迁移 | 改动最小 | 跨对象没有事务；成组备份仍靠约定 |
| B. 应用级数据合并为一个 `state.sqlite3`，加统一迁移器；每库的 `knowledge.sqlite3` 保持独立 | 会话、运行、成果在同一个事务里；数据库可一致备份；附件仍需成组备份；一套迁移代码 | 需要一次离线迁移（已有 `artifact_migration` 的备份→暂存→替换模式可以复用） |
| C. 改用 PostgreSQL | 并发好 | 本地部署要多装一个服务，当前不需要 |

推荐 B，但分对象执行：B3 先建公共模块和迁移器，之后 B1、B2 拆到某个对象时，再把它的表迁入 `state.sqlite3`。账户库同样迁入，路径从 `.local/usr/` 移到 `STATE_DIR`。账户迁入已获D1授权；先在副本演练，保留账号、口令哈希与身份。

迁移契约：停止旧服务写入，使用SQLite一致性备份并考虑WAL；清点数据库和附件，核对ID、外键、版本、引用、账号登录，不只比较条数。按域迁移期间只有一个写入方，不双写；校验后切换。失败回滚完整备份，新库已有新写入时不得直接覆盖回旧库。备份在验收完成前保留，不上传真实业务数据。

### 1.5 权限矩阵（替代路径正则）

| 能力 | 普通用户 | 领导 | 管理员 |
|---|---|---|---|
| 浏览资料、对话、分析、审查、成果 | ✓ | ✓ | ✓ |
| 上传、整理资料（10-16 决定：所有账户都可以） | ✓ | ✓ | ✓ |
| 重新生成谱系、层级、四维 | — | — | ✓ |
| 维护公共分析任务、审查规则 | — | — | ✓ |
| 自建报告模板 | 按当前接口约定 | 按当前接口约定 | ✓ |
| 发布报告 | 作者可发布 | 作者可发布 | 可发布 |

### 1.6 统计契约与既有图表

当前 /api/overview/libraries 已返回库级及年度项目数/直接经费。C2–C4已接受现有展示，B4先核对并扩展既有契约，不创建同义 /api/stats/projects。

## 2. 功能：两条主流程，统一入口

### 2.1 主流程 A：资料整理到对比报告

已有 `AnalysisWorkspace` 和 `browser_analysis_workspace` 通过（DeepResearch 08 §3）。目标是把它迁移到统一的运行服务和成果模型上：

上传 → 每份文件的处理结果 → 选两个项目 → 对比所选（范围已带入） → 发送 → **可以离开** → 从“我的工作”或成果页回来 → 阅读差异 → 打开引用原文 → 返回原位置 → 保存或编辑 → 导出

### 2.2 主流程 B：申请书审查

保持业务规则；统一Run调度，审查材料/规则/结果保留领域明细，统一成果入口引用该结果。去除重复执行状态，不删除结构化审查数据。

### 2.3 入口收敛

| 现状入口 | 目标 |
|---|---|
| 自由对话 | 存量分析下拉末项，复用已有自由输入会话 |
| 存量分析（4 个内置任务） | 保留，是“目的优先”的入口，预填任务类型 |
| 库内“与资料对话” | 改为“资料优先”的入口，预填范围，与对话共用同一个会话组件 |
| 情报分析 | 作为一种任务类型（外部材料 + 模板），共用运行服务和成果 |
| 周期总结 | 作为一种任务类型，从成果页发起 |
| 资料审查 | 独立业务，共用运行服务和成果 |

对用户来说，入口数量基本不变，变的是：每个入口的提交、进度、失败、结果去向完全一致。

### 2.4 降级

模型不可用时，下面这些仍然可以使用：资料浏览、原文、历史成果、模板预览、资料管理、统计图。只有提交按钮禁用，并说明原因。

### 3.5 导航与业务入口

普通用户/管理员：首页｜资料库｜存量分析▾｜资料审查▾｜情报分析｜成果。

### 3.7 统一资料预览（F3b）

首屏：标题、库名色标与文字、类型、已确认项目年份、正文。

删除旧Explorer前迁移仍需的定位与返回；不删除资料库分组目录或谱系树。缺失不猜测、PDF页与Word文本块不混称。

## 4. 工程：目录与依赖规则

### 4.1 后端

```
src/
  app.py                 # 装配入口示意，可沿用 main.py；负责配置、中间件、路由与 lifespan
  core/                  # config、db（连接 + 迁移器）、auth（Depends）、errors、logging
  jobs/                  # 运行服务：jobs 表、worker、SSE 订阅、重启恢复
  library/               # router.py + 现有 corpora/knowledge/parsers/targets/hierarchy/lineage/project_index
  analysis/              # router.py + graph、tasks、templates、reports、intelligence、period_summary、web
  artifacts/             # router.py + store、export（docx、zip）
  review/                # 已有，接入 jobs 与 artifacts
  accounts/              # router.py + store
  stats/                 # router.py：统计契约
```

规则：

- 路由只负责入参、授权、调用、响应，计算和存储放在领域模块里；
- 领域模块之间只通过公开函数调用，不 import `app.py`；
- 装配入口不得承载领域计算和持久化实现；用依赖、调用与行为检查验收，不用200行阈值或文件改名替代解耦。

### 4.2 前端

```
frontend/src/
  app/        # router、providers、Shell、导航配置表
  shared/     # ui/、api/（生成的类型 + query hooks）、copy.ts、lib/
  features/   # home、library、analysis（chat、tasks、workspace）、results、review、intelligence、settings
```

状态分三层，替代 `store.tsx`：

| 层 | 负责 | 实现 |
|---|---|---|
| 服务端数据 | 会话、文档、任务、成果、统计 | 只用 TanStack Query，不复制进 context |
| 工作上下文 | `browsing_corpus`、`scope`、当前任务 | 保存在 URL 参数和服务端 Run 中；一个很小的 `WorkContext` |
| 界面布局 | 主面板和返回栈、侧栏折叠、宽度 | `PanelManager` context，本地持久化 |

规则：

- `shared` 不导入 `features`；
- `features` 之间不互相导入，只通过 `shared` 或路由跳转；
- 组件中不出现 `fetch(`。

这些规则由检查脚本中的 import 规则测试强制执行，不另加 lint 依赖。

### 4.3 契约

`npm run gen:api` 从后端 `/openapi.json` 生成 `shared/api/schema.d.ts`，检查脚本对比生成结果，有完整OpenAPI返回模型的字段变化才能被生成类型捕获。先补主流程响应及错误schema，SSE事件另定义；生成类型不替代运行时语义测试。手写的 `api.ts` 和 `reviewApi.ts` 按领域逐步替换，替换完成后删除。
