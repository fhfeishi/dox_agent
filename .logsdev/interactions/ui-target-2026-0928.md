# UI 调整方案 · 知识库 target 四要素（场景 / 问题 / 技术 / 成果）

- 依据：`.logsdev/query.md` → `## 2026-0928 1006`（甲方意见 + 需求梳理）
- 日期：2026-09-28
- 范围：仅前端 UI（设计语言 + 交互逻辑）。后端 target 目录与提取链路是前置依赖，本文只给契约草案。

---

## 0. 结论摘要

1. **四要素不能做成"目录树"**。场景/问题/技术/成果是同一份报告的四切面，彼此多对多交叉；做成"场景 → 问题 → 技术 → 成果"的嵌套文件夹会让用户误以为是分类，且一份报告必须被复制四次。正确结构是 **报告单元（Report Unit）为最小信息单元，四要素是该单元的四个切面视图**。
2. **当前卡片到文件列表是"两级扁平"，必须升到"三级"**：知识库 → 报告单元 → 四要素切面。中间这层今天不存在（`CorpusFiles` 直接列 source 文件名）。
3. **容器宽度是硬阻塞**。`CorpusDetail` 是 `max-w-[560px]` 的抽屉，560px 放不下"四要素并排 + 溯源"；详情必须升级为全宽面板（≥960px），报告详情用**面包屑同级替换**，不要层层堆叠抽屉。
4. **提取状态是一个新的正交状态维度**，必须在 UI 上和"入库状态"分开：一份报告可以 `已入库` 但 `未提取`。今天 `CorpusInfo` 无任何 target 字段，这是新增。
5. **先做基础设施再做界面**：间距/圆角/字号目前全是手写魔法数字，四象限嵌套会放大不一致。第一批只做 token 化 + 三级结构骨架，视觉精修放第二批。

## 1. 业务场景与用户诉求

### 1.1 query 要点（原文归纳）

- 甲方要求：从 **场景、问题、技术、成果** 四个维度做管理与技术研判。
- 数据侧：定义 `schema-target = {"场景","问题","技术","成果"}`，每份报告（source 下的 pdf/md）经 LLM + schema 抽取到 `target/xxx`，该目录与知识库下 `source / parsed / datadb / vectordb` **同级**。
- 界面侧：知识库一级仍是卡片网格；**点开卡片后要看到嵌套板块**，点进去能看到该报告的技术、成果等具体内容。
- 最小信息单元 = 一份报告，包含 `source`（不可改）、`parsed`、`datadb`、`vectordb`、`target`。

### 1.2 场景还原

使用者是做**科研/产业技术研判**的人（NSFC 方向：AI+医疗、AI+机器人自动化）。典型动作不是"读一份报告"，而是：

- **盘家底**：这个库里有哪些方向、哪些问题已经被研究过、做到什么程度。
- **找差距**：某个场景下，别人用什么技术、得到了什么成果，还有哪个问题没人做。
- **出结论**：跨报告横向对比，形成管理/技术判断（后续要出 Word 报告）。

### 1.3 诉求分层（决定 UI 优先级）

| 层级 | 诉求 | UI 承载 | 优先级 |
|---|---|---|---|
| L1 管理 | 库 → 报告的家底清单，状态可见可控 | 知识库详情·报告单元列表 | P0 |
| L2 阅读 | 单份报告的四要素速读 + 回原文溯源 | 报告详情·四要素切面 | P0 |
| L3 研判 | 跨报告按"场景 × 问题"横向对比 | 聚合看板（矩阵/分组） | P1（P2 做完整版） |

### 1.4 成功标准（可验收）

- 从知识库列表到达"某报告的成果内容" ≤ 3 次点击。
- 任一报告都能回答三件事：**是否入库 / 是否已提取 / 四要素哪几项缺失**。
- 四要素中任一段内容都能一键跳回原文（PDF 页码 或 Markdown 行号）。
- 库级能在 10 秒内看出"多少份已提取、多少份失败、哪些待处理"。

## 3. 设计语言

### 3.1 视觉风格

**保持并强化现有的"纸感中性 + 低饱和"基调**，不引入卡片阴影堆叠和玻璃拟态。

- 底色统一 `--canvas`（#ffffff），分组区用 `--surface-soft`（#fafaf9），不用多层灰叠灰。
- 阴影只保留两级：卡片 hover `0 4px 12px rgba(15,15,15,0.08)`（沿用现状，不加深）、浮层 `0 16px 48px -8px`。
- 分隔用**发丝线**（`--hairline` 1px）而非阴影；嵌套层级靠**缩进 + 左侧色条 + 分区标题**，不靠边框套边框。
- **新增一条硬规则**：嵌套不超过 3 层视觉边框。四要素面板内部一律"无边框分区 + 标题 + 间距"，靠留白分栏。

### 3.2 配色

**主色不变**（`--primary #5645d4`）。新增"四要素维度色"，仅用于**标识**（chip、左侧 3px 色条、图标底色），**不用于大面积背景**——四个色同时铺开会花。

| 维度 | 色条/图标底 | 文字/图标色 | 现有 token（复用，不新增） |
|---|---|---|---|
| 场景 scenario | `--tint-sky` #dcecfa | `--link` #0075de | ✅ 已有 |
| 问题 problem | `--tint-yellow` #fef7d6 | `#9a6500` | ✅ 已有（现状 `:274` 已用此文字色） |
| 技术 technology | `--tint-lavender` #e6e0f5 | `--purple` #7b3ff2 | ✅ 已有 |
| 成果 outcome | `--tint-mint` #d9f3e1 | `--green` #1aae39 | ✅ 已有 |

- 状态色沿用：`--green` 成功 / `--orange` 警告 / `--red` 失败 / `--stone` 未开始。**状态色与维度色不得混用**：维度色回答"这是什么"，状态色回答"它怎么样"。
- 缺失要素用**虚线描边 + `--stone` 文字**，不用红色——缺失是常态不是错误；红色只留给失败。
- 无障碍：维度色不作为唯一区分手段，必须同时有文字标签 + 图标形状；色条与正文对比度 ≥ 3:1。

### 3.3 字体与排版

建立 type scale（新增 token，替换手写值）：

| Token | 值 | 用途 |
|---|---|---|
| `--fs-display` | 26 / 22 | 页面标题、库名 |
| `--fs-title` | 16 / 14 | 卡片标题、报告标题 |
| `--fs-body` | 13.5 / 13 | 正文 |
| `--fs-meta` | 12 / 11.5 | 计数、路径、时间戳 |
| `--lh-body` | 1.6 | 段落 |
| `--lh-title` | 1.35 | 标题（现状卡片已用 `leading-[1.35]`，统一即可） |

- **报告标题 vs 文件名必须区分**：报告标题用 `--fs-title` + `--ink` + semibold；原始文件名用 `font-code` + `--fs-meta` + `--stone`，弱化呈现（现在是两者混在一个 `truncate` 里，`:232`）。
- 所有计数/统计数字加 `font-variant-numeric: tabular-nums`，避免列表数字宽度跳动。
- 中文正文 `line-height` ≥ 1.6；四要素内容区每行 40–60 中文字符（约 `max-w-[680px]`，与现状 `CorpusGrid` 说明文字宽度一致）。

### 3.4 间距与层级

**这是本次最需要先做的事**：现状间距全是手写像素（`p-[15px]`、`gap-[11px]`、`mt-[18px]`、`pt-[26px]`），四象限嵌套后必然不一致。

- 采用 **4pt 栅格**：`--sp-1:4 --sp-2:8 --sp-3:12 --sp-4:16 --sp-5:20 --sp-6:24 --sp-8:32 --sp-10:40`。
- 圆角三档：`--radius-card:12`（容器）、`--radius-control:7`（按钮/输入）、`--radius-chip:999`（chip）。取消 5/6/8/10 混用。
- 层级间距规则（**嵌套越深，外间距越小**）：
  - 页面 → 区块：`--sp-6`(24)
  - 卡片内部 → 分区：`--sp-4`(16)
  - 四要素分区之间：`--sp-4`(16)，分区内标题到正文 `--sp-2`(8)
- 迁移策略：**新增 token，新组件全部使用，旧组件不动**（避免一次性大改引入回归）。

### 3.5 组件与图标体系

新增组件（放在 `frontend/src/components/`，复用现有 `Drawer` / `Pill` / `Button` / `Icon`）：

| 组件 | 职责 | 优先级 |
|---|---|---|
| `ReportCard` | 报告单元卡片：标题 + 原名 + 入库状态 + 四要素完备度 + 主操作 | P0 |
| `FacetPanel` | 四要素切面容器（分区渲染 / Tab 渲染两种形态） | P0 |
| `FacetSection` | 单要素分区：图标 + 标题 + 正文 + 溯源链接 + 缺失态 | P0 |
| `FacetChip` | 维度标识（色条 + 图标 + 文字），含"缺失"形态 | P0 |
| `ExtractionBadge` | 提取状态徽标（未提取/提取中/已提取/失败/待复核） | P0 |
| `EvidenceLink` | 溯源跳转 → PDF `?page=N` 或 Markdown 行号 | P0 |
| `MatrixBoard` | 场景 × 问题聚合看板 | P2 |

图标（`Icons.tsx` 扩展，须与现有体系一致：**24px 网格、stroke 1.6–2.0、无填充**）：

- 场景 → `compass`（或 `map-pin`）
- 问题 → `target-crosshair`（避免与"状态告警"的 `alert-triangle` 混淆——问题是研究客体，不是错误）
- 技术 → `layers`（或 `cpu`）
- 成果 → `trophy`（或 `sparkles`）

**明确禁止**：用 `alert-triangle` 表示"问题"维度——会和解析失败/提取失败的状态图标语义冲突。

## 4. 交互逻辑

### 4.1 信息结构

**现状**：`知识库卡片 → source 文件平铺列表`（两级，文件与索引混排）
**目标**：三级 + 双视图

```
L1 知识库卡片网格        （保持现状布局，增加"提取进度"信号）
   └─ L2 知识库详情（全宽面板）
        ├─ 视图 A「报告」   → ReportCard 列表（默认）
        └─ 视图 B「研判」   → 按场景 / 问题 分组聚合（P1）
             └─ L3 报告详情（同级替换 + 面包屑）
                  ├─ 四要素切面（场景 / 问题 / 技术 / 成果）
                  └─ 原文（PDF / 正文）Tab
```

关键决策：

- **报告单元 ≠ 源文件**。一份报告 = `source` 一份 + `parsed` + `target`。UI 上以 `doc_id` 为主键，源文件路径降为次要信息（`CorpusFiles.tsx:106-116` 的字符串匹配 join 应由后端返回结构化的报告单元，前端不再兜底）。
- **"有索引无源文件"必须显式呈现**，不能混在 `indexed` 里（现状 `:114` 造假行）。新增状态 `源文件缺失（仅有索引）`。
- **视图切换放在详情顶部**，默认落在「报告」，不要默认落在聚合视图（研判是高阶动作）。

### 4.2 操作路径

| 动作 | 现状 | 调整 |
|---|---|---|
| 打开知识库 | 3 个等价入口（卡片主体进 Inspector、footer "打开"、按钮"添加资料"） | **收敛为 1 个**：点卡片主体 → 全宽详情；卡片 hover 只留 1 主操作 + "更多"菜单 |
| 进入报告详情 | 不存在 | ReportCard 点击 → 同级替换，顶部面包屑 `知识库名 / 报告名`，Esc 或面包屑返回 |
| 触发提取 | 不存在 | 报告级：卡片内「提取四要素」；库级：「批量提取未处理」（带数量 + 预计耗时提示） |
| 溯源 | 仅 PDF 整篇预览 | 四要素每段右侧 `EvidenceLink` → 打开原文并定位页码/行号 |
| 危险操作 | `window.confirm`（`CorpusDetail.tsx:132/143`） | 「删除知识库及文件」改为**输入库名二次确认**；与常规操作分组隔开 |

路径长度校验：卡片 → 详情 → 报告 → 成果 = **3 次点击**，满足 §1.4。

### 4.3 状态反馈

引入**两维正交状态**，UI 上分两个徽标，不合并成一个文案：

- **入库状态**（已有）：待导入 / 已入库 / 解析失败 / 源文件缺失
- **提取状态**（新增）：未提取 / 提取中(n/total) / 已提取 / 提取失败 / 待复核

呈现规则：

- 卡片级：`ExtractionBadge` + 四要素完备度 `3/4`（缺失项用虚线 chip 明示是哪几项）。
- 库级：顶部汇总条 `已提取 32 / 未提取 8 / 失败 2`，失败项可点开看清单（现状只有"部分失败" pill，无入口）。
- 提取是长任务：**必须可感知进度**。沿用 `CorpusJob` 模式，但进度要显示在**触发位置**（卡片/行内），不能只在详情底部一行文字（现状 `CorpusDetail.tsx:222-227`）。
- 失败原因落到**报告单元可见位置**，并提供「重试本份」。

### 4.4 异常与空态

区分四种空态（**文案与行动各不相同**，现状只有一句通用文案 `CorpusGrid.tsx:311`）：

| 空态 | 文案要点 | 行动 |
|---|---|---|
| 无知识库 | 还没有知识库 | 新建知识库 |
| 库内无源文件 | 该库还没有资料 | 拖放/选择文件（指向 `source/`） |
| 已入库但未提取 | N 份已入库，尚未提取四要素 | 批量提取 |
| 该报告无 target | 这份报告尚未提取 | 提取四要素（并说明预计耗时） |

其他异常处理：

- **部分失败**：库级给失败清单入口，不只用 pill。
- **要素缺失 ≠ 提取失败**：某要素抽取为空（如该报告没有"成果"章节）显示为"原文中未识别到"，用 `--stone` 虚线态，**不要**报红。
- **面板数据加载失败**：分区级错误态 + 重试，不让整页挂掉。
- 现状空态用了 `-mt-[120px]` 的负边距 hack（`:311`）对齐卡片，改为正常布局容器，避免后续嵌套错位。

### 4.5 动效与反馈时机

- **hover 位移只给最外层**。`CorpusGrid.tsx:169` 的 `hover:-translate-y-px` 保留；四要素内层分区**只用背景色/边框变化**，绝不加位移——嵌套元素一起位移会视觉抖动。
- 时长：`--dur-fast:120ms`（hover/chip）、`--dur-base:200ms`（面板/展开），缓动 `ease-out`。
- 面板：右侧滑入 200ms；内容切换**不要高度跳变**（CLS）——报告详情用固定高度容器 + 内部滚动。
- **长任务反馈时序**（硬要求）：
  - 点击后 ≤100ms 出现可见反馈（按钮禁用 / 徽标转"提取中"）
  - >1s 显示进度（n/total）
  - >10s 允许后台化，用户可离开当前页，回到库级能看到汇总进度
- **无障碍/偏好**：全局遵循 `prefers-reduced-motion: reduce` 时关闭位移与滑入，只保留颜色变化；四要素分区用 `role="region"` + `aria-label`，维度 chip 带文字标签（不靠颜色单通道传达）。

## 7. 前置依赖与接口契约（草案，待后端确认）

`src/` 内目前**没有** `target/` 或 `schema_target` 的任何实现，以下为 UI 所需的最小契约：

```
CorpusInfo  += target_count: number          // 已提取报告数
               target_pending: number        // 待提取
               target_failed: number         // 提取失败
               schema_target: string[]       // ["场景","问题","技术","成果"]

GET  /api/corpora/{id}/reports
     → [{ doc_id, title, source_name, source_kind, rel_path,
          index_status,              // new|indexed|error|removed
          extract_status,            // none|running|done|failed|review
          extract_progress?: {completed,total},
          facets: { 场景: "done"|"empty"|"missing", 问题: …, 技术: …, 成果: … },
          has_source_file: boolean }]

GET  /api/corpora/{id}/reports/{doc_id}/target
     → { doc_id, version,
          facets: [{ key:"场景", status, text, evidence:[{page|start_line,end_line, quote}] }, …] }

POST /api/corpora/{id}/reports/{doc_id}/target        // 单份提取
POST /api/corpora/{id}/target/batch  { mode:"pending"|"failed"|"all" }   // 批量
```

UI 侧假设（若后端口径不同需回来改）：`doc_id` 稳定不变（重命名源文件不改 doc_id）；extract 为异步 job，复用 `CorpusJob` 形态。

## 8. 明确不做（避免过度设计）

- 不做"场景 → 问题 → 技术 → 成果"的四层目录树（见 §0.1）。
- 不做可拖拽自由画布 / 看板自定义（研判视图先给固定分组）。
- 不做 schema 可视化编辑器（四要素硬编码，配置化留 P2 之后）。
- 不做深色模式（本次不动 `globals.css` 的明色基调）。
- 不做一次性旧组件全量重构（token 只在新组件生效，旧代码按批次迁移）。

## 9. 验收要点（可检查）

1. 知识库 → 报告 → 成果内容 ≤ 3 次点击。
2. 卡片与库级均可见"已提取 / 未提取 / 失败"三项计数，且失败项可点开清单。
3. 四要素任一缺失项显示为虚线 chip，不报错红。
4. 任一要素内容可跳回原文并定位（PDF 页码 / Markdown 行号）。
5. `npm run build`（tsc + vite）通过；现有 `tests/browser_*.py` 无回归。
6. 键盘可达：报告卡片、面包屑、四要素分区均可 Tab 聚焦；`prefers-reduced-motion` 下无位移动效。
