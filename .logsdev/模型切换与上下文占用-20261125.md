## 3. 方案

### 3.1 模型切换（三处改动）

```
src/agent/providers.py   provider 目录：id → {base_url, 默认模型列表, 各模型窗口}
                         静态表，不联网；新增 provider 只改这一处
src/agent/models.py      model_for(settings, override=None)
                         override = {"provider": ..., "model": ...}，None 时行为不变
src/model_choice.py      每账户的选择：存 .knowledge/.state/model_choice/<owner>.json
                         （一个账户一个文件，与 expert/ 同构，不建表）
```

注入点：`chat`、`reports`、`intelligence`、`review` 四条路径都读当前账户的选择。读不到就用全局默认（当前行为）。

API：`GET /api/model` 扩展为返回 `{current, available[], context_window}`；`PUT /api/model` 设当前账户的选择（只允许目录里的 provider+model，不接受任意 URL/key）。

前端：头像左边一个「模型」按钮，所有角色可见（当前只有 admin）。点开是一个小面板：provider 分组 + 模型列表 + 当前选中打勾 + 每项标注窗口大小。

### 3.2 上下文占用

**数据来源的取舍**——这是本方案最需要想清楚的地方：

| 口径 | 能拿到什么 | 问题 |
|---|---|---|
| A. 模型返回的真实 usage | `input_tokens` 是**真实**的 prompt 大小 | 只有合计，不区分系统/任务/工具 |
| B. 本地估算（现有 `estimate_tokens`） | 能按来源拆分 | 是估算，与真实值有偏差 |

**推荐：以 A 为总量，以 B 为拆分比例。** 环形进度的分子用真实 input_tokens（准确），明细里各段的数字用本地估算（能拆），并在弹窗里注明「分段为估算，合计为模型回报」。这样既不说谎，又能回答「系统占了多少」。

窗口上限：从 `providers.py` 的静态表取，查不到就不显示环形（只显示已用 token 数），**不猜**。

位置：对话工作台输入框右下角。模型名 + 环。点击弹出小窗，列出：

```
系统上下文    约 3.2k    (base.md + 任务提示词 + 专家基线)
资料上下文    约 18.4k   (6 份文档，按预算截取)
历史对话      约 2.1k    (8 轮)
工具/其他     约 0.3k
──────────────
合计          24.0k / 128k
```

## 6. 审核本规划（2026-11-25，自查）

按 verification.md「先列该改动可能的失败方式」，逐条核对上一节，发现三处缺陷：

### 缺陷 1：漏了 review 路径，`model_for` 不是唯一入口

规划写「四条路径都读当前账户的选择」，但 `src/review/model_client.py` **不用 `model_for`**，
它自己拼 `base_url`/`key`/`model`，还支持 `REVIEW_MODEL_*` 覆盖。所以改 `model_for` 不会影响
资料审查。

**处理**：明确 review 路径**不跟随**用户选择。理由：审查是后台质量关卡，用固定模型才能保证
「同一份材料两次审查结论可比」。用户换模型是换「谁来写」，不该换「谁来审」。这一点写进代码
注释，避免以后被当成遗漏来「修」。

### 缺陷 2：上下文拆分的四段里，「工具」这一段本项目没有

规划的小窗列了「系统 / 资料 / 历史 / 工具」四段。但本项目**没有工具调用**（`grep bind_tools`
为空），也没有 agent 的工具结果。照抄别家产品的分段会列出一个永远为 0 的「工具」。

**处理**：改成三段——系统（`base.md` + 任务提示词 + 专家基线）、资料（检索到的文档）、历史
（对话轮次）。另加一行「其他」（用户问题本身等）。不为了像别家而保留空段。

### 缺陷 3：`estimate_tokens` 未标定，用它算比例会给出假精度

`estimate_tokens` 的注释写着「uncalibrated」。若用它算「系统占 13%、资料占 77%」，那两位
小数是假的。

**处理**：明细里的分段数字**只给到千位**（约 3.2k），不给百分比。百分比只在环上出现一个
（总量/窗口），因为总量是模型回报的真实值。弹窗里注明「分段为估算，合计为模型回报」。

### 缺陷 4（补充）：`PUT /api/model` 的越权面

若接口接受 `{provider, model}` 以外的字段（如 `base_url`、`api_key`），普通账户就能把请求指向
任意地址，等于把服务端变成 SSRF 跳板，或用别人的 key。

**处理**：接口**只接受** `provider` + `model` 两个字符串，且必须在静态目录里查到；查不到就 422。
key 与 base_url 永远只来自 `.env`，接口层不可写。这一点要有测试锁定。

## 上下文窗口长度校正（2026-11-26）

第一版目录里的窗口数字**没有一个是对的**。表头写的是「128K unless noted」——那是 DeepSeek V3
时代的数字，然后被复制到了所有 Qwen 行。真实值大 2 到 8 倍：

| 模型 | 原值 | 校正后 | 来源 |
|---|---|---|---|
| deepseek-v4-flash | 128,000 | 1,048,576 | `GET /models` 的 `context_window` |
| deepseek-v4-pro | 128,000 | 1,048,576 | 同上 |
| qwen3.8-27b | 131,072 | 1,000,000 | 百炼模型页「上下文限制」 |
| qwen3.6-27b | 131,072 | 262,144 | 同上 |
| qwen3.5-27b | 131,072 | 262,144 | 同上 |
| qwen3.8-flash | `None`（未知） | 1,000,000 | 同上（原生 1M） |

数字本身不是最重要的，**错的分母会让环撒谎**：20.7k 用量在 128k 分母下画出来是 16%（看起来
快满了），在真实 1M 下是 2%。这正是当初「未核实就不画比例」要避免的情况，只是这次错在有数字。

### 两种测量，互相印证

1. **超限探测是免费的**：发给 provider 明显超长的输入，它在报错里写出允许区间。
   `qwen3.6-27b` → `Range of input length should be [1, 229376]`；`qwen3.5-27b` → `[1, 258048]`。
   注意这两个数是**最大输入长度**，比上下文长度小，且思考模式下另有更小值——所以分母取
   「上下文长度」，不取输入上限。
2. **needle 测试证明窗口是真的**，不只是标称：把 `ZEBRA-4471` 放在 380k token 提示的最前面，
   填充在后，要求复述。DeepSeek v4-pro 与 qwen3.8-27b 都答对了。仅「返回 200」不足以说明
   没有被静默截断，必须把词放在会被截掉的那一端。

### 顺带发现

- `deepseek-v4-flash` 是别名，`/models` 列的是 `deepseek-flash`，API 会回 `"model":"deepseek-flash"`。
  两个都能用，保留既有名字。
- DeepSeek 的 `max_output_tokens = 393,216`，而我们请求里 `max_tokens` 远小于此。1512 那次
  「thinking 吃光 4096 导致空答案」的根因是把输出上限设小了，不是模型问题——但关 thinking
  仍然是对的选择（首字 3.6s vs 267s）。
- 副作用：环在 1M 分母下变成 2%，12px 圆上看几乎不可见。数值文本仍准确，环退化为粗指示。
