## 1. 目标与范围

**目标**：面向国家自然科学基金、省重点/省重大、面上项目等科研项目历史报告的**本地、单用户** Agentic RAG 系统。基于本地报告语料提供带来源的专业问答、专项报告生成，以及本地目录浏览与 PDF 原文阅读。

**范围内**：
- 带 `[n]` 引用、支持多轮追问与有限补查的专业问答；
- 每个会话绑定一个任务（task1–4），任务决定 system prompt 与输出契约；
- 本地文档目录树、网页预览、引用跳页；
- 按模板生成专项报告（Markdown 预览/复制/下载）；
- 多知识库隔离、选择与按库问答，含知识库与库内文件的增删改查、上传导入与预览；
- 多知识库（≤6）会话/任务与跨库联合检索（KB-4，首期新增，取代原“不做跨库”）；
- 申报书形式审查（W8）：指南驱动检查清单 + 五阶段预审 + 可追溯报告导出（后端已实施、前端入口已实现待验收；见 §2 末节与 ITERATION §16.43/§16.44）；
- 单用户本地部署（默认只监听 `127.0.0.1`）。

**范围外（首期不做）**：多租户/权限后台、多 Agent 协作、知识图谱、工作流画布、独立问题分类服务、材料遵循等级系统、自动全网研究、自动订阅同步、外部资讯抓取与科研头条、多模型路由与模型管理后台、模板管理平台、分布式任务队列。（`VITE_UI_NEWS`/`VITE_UI_MODELS` 等仅占位，不属首期交付。）

> 2026-09-23 修订（需求来源：用户提出的知识研究工作台目标，见 §9/ITERATION §16）：上列「**模板管理平台**」已被 §16 **W4（自定义任务/输出模板）与 W7（Prompt/Skill 产品化）分期承接**，不再是首期范围外；「**自动全网研究/外部资讯抓取**」由 §16 **W6** 以显式、受控、可追溯的方式承接（W6-B 受控搜索需真实使用证据触发，不自动联网）。其余条目仍为首期范围外。冲突时以 §9/§16 的分期与退出条件为准。

## 2. 需求要点

**专业知识问答**
- 固定流程：解析专业问题 → 限定范围检索 → 阅读原文 → 必要时有限补查 → 带引用回答。
- 检索（计划 L）：搜索空间为报告 markdown；hybrid chunk 检索 → 选相关报告 → 全文 markdown（预算内）入上下文；事实引用绑定报告+页。
- 每条关键事实标注来源文件与页码，可直接打开原文；无资料/冲突/解析失败明确说明，不把"未检索到"说成"领域不存在"。
- 展示真实执行阶段，不展示或虚构内部推理；沿用搜索/模型调用/超时预算，不增加多 Agent 或工作流编辑器。
- 回答职责由用户显式选择的任务（task1–4）决定；本期不做自动意图分类。

**任务（task1–4）**
- `task1` 精准问答（先结论 + `[n]` 引用，不推测）、`task2` 对比分析（维度表 + 差异 + 可比性前提）、`task3` 技术研判（研判技术路线成熟程度与后续工作，事实/研判分段，限定样本；2026-10-09 由“趋势推测”更名，报告模板“未来方向报告”同步更名为“技术研判报告”，id 仍为 `future_directions`）、`task4` 专项报告（按模板章节 + 范围/来源/局限）。
- 提示词归 `src/prompts/`（`base.md` 硬约束 + 各任务角色/输出契约 + 加载器）；未知 task id 抛 `UnknownTaskError`，不静默回退。
- task4 不在 `POST /api/chat` 生成正文，走报告入口；但**允许自由文本输入**（chat 只做报告参数采集 intake）。见 [`ITERATION.md`](ITERATION.md) §8。
- 推导许可由任务提示词决定：task1/task2 收窄不推测，task3 放开并要求区分事实/研判意见；输出小节标题只写名称，不附加格式说明（修复报告中出现“（带 [n]）”）。
- **扩展（规划，非首期验收）**：task5 项目画像/task6 成果汇编/task7 领域综述/task8 可视化简报；两轴分离（意图 × 产出物输出参数）。Markdown 和真实 DOCX 已可从成果导出；PDF/图表仍后置。W4 的自定义任务复用 task1–task4 执行模式，不等于这些新任务引擎已实现。见 [`ITERATION.md`](ITERATION.md) §9/§16.18。

**专项报告**
- 当前生成端点仅单 `corpus_id`；多库会话在报告卡片独立选择一个报告库，确认前不生成，不默认使用基础库。报告请求携带本轮选中且属于所选库的 `doc_ids`；会话检索集合保持原值。多库 intake 不从首库静默填领域；选定报告库后可显示其可靠领域建议，由用户确认或改写。
- **报告体验**：自然语言需求形成带来源的可编辑摘要（单库可靠领域建议、最近五个完整自然年的项目年份窗口、类别不限、综合或任务固定模板），确认前预检实际入选/排除资料；多库缺报告库/领域、文本冲突或零入选时给就地修正动作。确认后的写作参数进入生成提示，再从成果页审阅、修订与导出。服务端过滤、模板版本和单库边界保持可核对。
**预检可诊断**：`POST /api/reports/preflight` 按文件名项目起止区间与所选年份窗口相交筛选，返回逐份排除原因（`period`/`year`/`category`/`stale`）。文件名缺少有效项目区间时提示按当前命名规则修正；填表日期缺失不再排除资料。
- 必填：研究领域、起止年份、模板；可选：基金/项目类别、指定文件、分析重点。
- 四模板：`achievements`/`hotspots`/`future_directions`/`comprehensive`；输出 Markdown，支持预览/复制/`.md` 下载。
- 2026-09-28 用户更改年份口径：报告年份窗口按文件名中的项目起止区间相交筛选；项目年份不代表报告提交时间或成果发生时间。`资助类别`仍从解析文本读取，用户指定类别时精确匹配，缺类别不能猜测。旧填表日期筛选与其解析覆盖阈值不再作为报告入选条件。热点结论限定样本、按项目去重；事实、已实现应用、潜在应用、未来推断分开表达。

**本地文档窗口**
- 右上方“本地文档”入口 → 右侧滑出窗口：真实相对目录树（展开/折叠/筛选/入库状态）+ 预览（PDF 直接展示原始文件 / Markdown 渲染 / Word 转 HTML（K9 目标，当前为纯文本）/ txt 纯文本）。预览面板**桌面约占视口 50% 宽、圆角居中**，窄屏为全屏抽屉；元信息显示解析器（旧 `liteparse` 会提示重导入为 mineru）。
- 引用 `[n]` 可点击并定位物理页码；失效或版本变化明确提示。
- 浏览与限定检索范围是两个操作；浏览不改变范围，限定资料时显示已选文件。
- 文件接口仅允许配置根目录内的资料，按文档 ID 映射，防路径穿越。

**侧栏与文献库**：侧栏可收束为图标栏/展开为全宽并持久化，收束后核心入口与异常提示仍可达；提供"文献库"一级入口浏览已入库文档并打开预览。

| 接口 | 说明 |

### 4.2 `POST /api/chat`

多库边界（已实施）：会话只维护 1–6 个检索库集合，取消 `base ∈ retrieval set` 前端约束。应用统一显式发送 `corpus_ids`；旧 `corpus_id` 接口兼容，二者仍不可同送。服务端直接 API 从未包含浏览基础库概念。旧缺省默认库逻辑已改为目录顺序首库，配置 `DEFAULT_CORPUS` 不再支配该选择。

请求：`messages`（1–20 条，每条 ≤12000，总 ≤40000，末条必须 user）、`allowed_doc_ids`（可空，非空 1–20）、`task_id`（默认 `task1`，`task1–4`；**task4 走 intake 分支、不生成正文**；未知 422）、`corpus_id`（可选，缺省默认库；未知 404）、`corpus_ids`（可选，1–6，**与 `corpus_id` 二选一**，同送 422；缺省默认库；KB-4）、`run_id`（8–80）、`session_key`（W3-A 可选）、`run_context`（W3-A 可选：`visible_params`/`param_sources`/`resource_policy`/`output_intent`）。禁止额外字段（含已移除的 `execution_mode`/`query_routing`/`evidence_level`）。

W6-A 网页资料：`web_snapshot_ids`（可选，≤6 个已确认快照 id，不可重复）；有快照时服务端把 `resource_policy` 定为 `local_plus_urls`，网页引用为 `kind="web"`（带 `snapshot_id`/`url`/`fetched_at`/`version`/`truncated`），与本地引用统一编号。快照正文与本地证据**共用** `RETRIEVE_CONTEXT_TOKENS` 预算，超出即截断并在来源标 `truncated`。所选知识库未就绪时仍可运行，但 `preparation`/`stop_reason` 保留真实状态，**不伪装为 ready**。

SSE 事件：`run`（W3-A 服务端有效范围/模型/资源策略）、`status`、`policy`（route/stop_reason/notice/allowed_doc_ids）、`step`、`telemetry`、`sources`（附服务端 `citation`，先于 token）、`token`、`usage`、`done`、`error`。无 `done` 的断流视为未完成；失败用 `error` 且不发送 `done`。

### 4.3 数据模型

- 知识库 SQLite `docs(id, version, payload)`：`id` 由 origin 稳定派生，`version` 包含页文本和 Markdown；引用版本不符时拒绝把当前原文冒充旧版。`files` 是源文件增量清单；当前未提交实现另加观察到的哈希与错误字段，并拟将正文、页、chunk 和成功文件指针一起事务发布。旧报告/成果能回读已保存正文，不代表旧 PDF 原文已归档。准确字段与状态以当前 schema/ITERATION §16.32 为准。
- 工作区 SQLite `records(id, kind, revision, payload)`：`kind ∈ {sessions, notes}`；会话数据含 `turns`/`options`/`branches`/`task_id`/`corpus_id`，并已持久化 `corpus_confirmed`/`corpus_ids`；旧会话缺失新增字段时按安全回退规则恢复。报告表新增 `session_key`/`run_id`/`corpus_id` 的旧记录以空值表示未知来源，不得由 UI 推断为当前库。`BEGIN IMMEDIATE` 校验 revision（冲突 409），单记录 >4MB 413；笔记 `body`≤20000、`reviewed`、`sources` 1–6 条且版本可读。
- 阅读行号是规范化视图行号（超长行按 300 字符切段），非 PDF 原版排版行号；`section` 窗口按标题/代码围栏切块并返回 `heading`/`truncated`/`code_omitted`。

### 4.4 检索（L 阶段已实现）

报告级两级检索当前以标题/标题层和项目元数据作候选，再以 chunk 词面命中精排、按项目去重与覆盖率筛选；在未提交工作树中补入标题窗口外的正文词面候选。命中文档正文进入模型前仍受 `RETRIEVE_CONTEXT_TOKENS`/`REPORT_TOKENS` 限制，可能截断，不能概称“全文入模”；综述模式的逐段处理另见 ITERATION §16.31–16.33。当前真实语料 Recall、最终引用和延迟门槛尚未验收。

- 图：`understand → retrieve → assemble → validate → (retrieve|answer) → finish`（确定性，无 LLM search/read 工具循环；`validate` 在 `answer` 前，`validate_citations` 内联）。
- 检索为 **BM25-only**（`EMBEDDING_PATH` 空）；dense 留作增强。
- **参数**：`MIN/MAX_REPORTS`、`MIN_TERM_COVER`、`PER_DOC_TOP_M` 待评测校准；`REL_COVER`/`GENERIC_DF_RATIO` 固定默认。评测：`src/evaluate.py` + `tests/data/fund_retrieval.jsonl`（15 条，BM25-only：recall/MRR=1.00、no_match=0、ctx≈56k/69k、P50≈0.6s；样本饱和，待扩样）。
- 默认关/延后：MMR/覆盖贪心/字段权重/LLM 多查询/rerank/过滤下推（year/domain/project，依赖 H9/B2/B4/B5）。
- `Knowledge.search` 已委托 `retrieve`（单索引，旧窗口 BM25 删除）。

### 4.5 错误语义

422 请求校验/页行/版本；409 准备中写入、官方任务重入、revision 冲突、预览过期、同名冲突或已登记库目录缺失；413 记录超限/文件超限；404 文档/未知库不存在；415 文件类型不支持；流建立后失败走 SSE `error`。

已实现的 chat 缺失库响应为 HTTP 409、JSON `{"detail":{"missing":true,"corpus_id":"…","message":"…"}}`。前端按 `detail.missing === true` 分流，保留 corpus_id 引导重新选择，不回退默认库；不能把所有 409 当缺失库。其他 409 保留原 detail 字符串/对象与各自语义。

### 10.2 四个维度及最小信息结构（推荐）

| 维度 | 应回答的问题 | 内容边界 |
|---|---|---|
| 场景 | 在什么对象、环境、业务环节中使用？ | 提取报告实际涉及的应用环境，不能只把库名当场景 |
| 问题 | 要解决什么具体困难或需求？ | 保留问题对象、约束和原文限定，不把研究标题直接当结论 |
| 技术 | 用什么方法、机制或技术路线解决？ | 写清方法与所解决问题；没有关系证据时只列技术，不强行关联 |
| 成果 | 报告记载取得了什么结果？ | 论文、专利、原型、性能指标、应用验证等；预期目标与已取得成果必须区分 |

已实施首切片采用固定 schema，不提供可视化 schema 编辑器；后续多方案设计以 §11.4 为准，固定 schema 不再是长期结构约束。每份 target 保存文档身份/版本、源内容哈希、schema 与提取提示版本、生成模型/时间、处理覆盖，以及四个维度的条目。条目包含本次结果内的 id、简短名称、说明和证据定位；成果另标“已取得/预期/原文未明确”。原文未提供的维度显示“未提及”，不能编造补齐；提取失败或文本未完整处理不能显示成“未提及”。

每条内容至少有一段可定位的原文引文，绑定当前文档版本和正文位置；PDF 有可靠页码时附页码，没有则打开解析正文位置，不伪造页号。结构校验与引文匹配只能证明格式及出处，不能替代语义核验，也不显示没有依据的置信度百分数。

一份报告可以涉及多个场景、问题和技术。只保留原文支持的关联条目 id，不把四个列表做笛卡尔积。未确定关联的内容仍在文档详情中可见。首版按原文名称及简单空白规范化聚合，不自动合并同义词、不强制一份报告只属于一条树路径。聚合数按去重报告数展示，不能把重复出现的同一成果算成多份报告。

### 10.3 落盘与生命周期（推荐）

保留现有结构，报告是逻辑单元，不为每份报告重建一套数据库或向量库：

```text
.knowledge/<知识库>/
  source/                 原始文件，提取流程只读
  parsed/                 现有解析产物
  datadb/                 现有数据库
  vectordb/               现有向量目录（如启用）
  target/<doc_id>.json     推荐新增：该文档当前四维提取结果
```

有两个可行方向：**JSON 为主记录**，直接满足本地查看和随库迁移，首版实现较小，聚合读取成本较高；**SQLite 为主记录并导出 JSON**，筛选更方便，但增加导出同步和恢复契约。推荐首版选择 JSON 主记录，先用实际库测读取体验，确有瓶颈再增加可重建索引；不同时维护 JSON/SQLite 两份权威结果。

抽取对象必须已有可用解析正文，默认不重跑 PDF 解析、不调用图像模型。先冻结本次正文，校验结构与引用后原子替换单份结果；生成中断/失败不覆盖上次成功结果。源版本变化后旧 target 标记“待更新”并退出当前聚合，旧内容可带状态查看；源文件缺失同样不继续贡献当前研判证据。库重命名随现有整体目录操作，关联使用库/文档标识；明确删除文件后失效对应结果，不另建复杂级联框架。

“source 不可更改”解释为提取/归纳流程不修改原始内容；不擅自取消现有用户显式重命名、替换、删除文件的管理能力。target 只存当前派生结果，首版不做无限历史版本；已保存系统成果继续走现有成果版本。新提取失败、缺字段、未处理、待更新必须能区分。

### 10.4 最小界面与使用流程（推荐）

一级知识库卡片保持不变。点击后在当前知识库内部提供“资料”和“四维浏览”两个视图，保留上传/刷新。四维浏览以“场景→问题”为浏览路径，中央列出关联报告卡片，每张卡简要展示技术与成果；同时允许按技术/成果切换筛选，避免只有固定树才能找资料。

采用面包屑/筛选标签表达当前路径，不层层再弹抽屉。点击报告时右侧显示该报告四个分区和出处；点击证据切换原文预览，并可返回原来的筛选位置。“未分类/未提及”可见，不能因没有场景或没有成果就把整份报告隐藏。

未整理时显示“生成四维信息”，支持单份或勾选资料后批量处理。按钮旁说明会调用模型；用户无需编写抽取提示词或逐字段确认。首版按需触发，普通上传、刷新、打开页面不会自动对全库计费提取。批量逐份执行，显示已完成/失败，失败单份可重试；只重试失败或待更新项，不做常驻后台调度与通用任务队列。

一份文档过长时复用现有分段思路提取并合并，不静默只读前几页。显示实际文本处理覆盖；未完整处理的结果不标“已整理”，也不混入完整覆盖统计。首版可以明确提示超出当前处理预算，保留原资料与已有结果，不以增加整库自动恢复系统解决。

### 10.5 与问答、报告和成果的关系

四维提取是资料描述，技术研判是后续推理，两者分开。用户在筛选后的报告上点击“基于这些资料提问/对比/生成报告”，复用现有 doc_ids 范围与任务模板，不再造一套聊天系统。新增提取本身不要求项目年份或基金类别齐全；只有进入已有报告生成时才按当前报告契约执行年份/类别筛选，并显示最终纳入范围，不保证筛选所见全部自动进入报告。

技术研判可按“场景需求—问题瓶颈—技术路线—已有成果—证据缺口”组织正文，明确区分文献事实与模型判断；target 辅助导航与候选整理，原文仍是事实依据。不能依据提取条数推断技术先进性、成熟度、市场价值，首版不增加评分排行榜。

四维中的“成果”在知识库内称为“文献成果”；左侧已有“成果”入口继续存放用户生成、编辑的报告/分析。一次 target 抽取不自动向系统成果页创建四份新成果。

**接口职责（列表、详情和执行已实现，详见 `src/main.py` 的 target 路由）**：读取库内四维列表、读取单份 target 与证据、提交所选 doc_ids 的提取/失败项重试；同库筛选与聚合计数仍待实现，见 §11.13。写入请求由服务端校验库归属和正文版本，同一文档版本/schema/提示版本已成功时默认复用，用户显式重新提取才再调用模型；处理期间范围改变则拒绝发布过时结果。进度与失败返回沿用现有运行状态方式，当前以提交提取任务、轮询状态和读取结果承接这些职责。首版不另建 target 编辑、删除、发布审批 API。

### 10.6 实施范围与完成依据

**建议先做一个纵向样本流程**：选择现有可读报告，提取 JSON → 四维展示 → 点击证据回原文。再增加同库筛选与选中资料发起已有任务。现有版本一致性直接复用，只修确实阻碍这条流程的问题，不把全部历史清理、OCR 总体评测或旧缓存迁移作为开工前置。

首批完成需在真实解析资料上证明：四维条目有依据；预期目标未当作已取得成果；缺字段与提取失败可区分；多场景报告不产生虚假关系；长文覆盖说明准确。用已有 browser_library.py / browser_document_preview.py 扩展“库卡片→四维→原文→返回”场景，结合 browser_tasks.py 验证所选文档范围继续有效；已有 API 行为测试承接原子写入、失效及重试。真实 LLM 小样本另行核对抽取语义，浏览器替身通过不代表抽取质量通过。此处只规定行为，不要求为每个字段新增测试。

首版不包含自由 schema 编辑、跨库实体消歧、自动知识图谱、技术评分、全库自动抽取、人工审核工作流、新存储服务或旧格式迁移器。人工修订、同义归并、多库四维比较在真实使用暴露需要后再安排。以上 JSON/schema/交互均为推荐方案，具体成本预算与抽取效果需通过样本验证，不能把本报告当成已实现的 API 契约。

#### 10.7.2 四维内容要求

| 维度 | 必须能理解的问题 | 阅读线索（非新增必填字段） | 展示和研判约束 |
|---|---|---|---|
| 场景 | 在什么环境、对象和条件下开展工作？ | 业务/工程载体；运行条件、干扰和适用边界 | 不只显示领域名，比较时带上关键条件 |
| 问题 | 具体要解决什么困难？ | 机理/系统瓶颈；感知、算法和决策难点 | 区分原文问题与研判提出的未解问题 |
| 技术 | 采用什么机制、路线和实现手段？ | 架构、理论模型；算法、协议、软硬件策略 | 名称相同不自动代表方案相同；保留应用约束 |
| 成果 | 有什么可核对的产出与效果？ | 平台、样机、软件；性能指标；应用、论文与专利 | 保留原始数值、单位、基线与测试条件；明确已取得/预期/原文未明确 |

提取 `name` 采用历史稿的 6–20 字名词短语写作指导，完整名称和限制保留在说明/引文；不得为凑字数删掉科学含义，也不将其直接变成拒绝专业英文名称的硬校验。量化数据不改写成“显著提升”，无数据不补；不同指标、测试集、样本量或基线不能直接排名。子维度只帮助覆盖内容，不变成十余个新表单字段。

历史阅读稿“同一项工作会在四维里各出现一次”仅可理解为阅读顺序，不能作为基数约束：实际每维可以零项、多项，彼此关系可以不明确。四维不是四层目录，也不是强制填满的四格。部分处理、异常、未提及与结果待更新继续按 §11.4.2 区分。

当前 `targets.py` 每段每维最多 20 项、每项最多 5 条证据；提取提示词尚未声明这些上限，超过会报结构非法。升级时应对齐实际校验与提示，不能静默截条目后声称完整；现有按规范化名称合并且取较长说明的方式也不能证明同名内容语义一致。这两项是小样本核对重点，不由前端新增同义词合并或图谱解决。`relations.basis = 原文明示` 是模型声明、代码过滤条件，不是人工关系核验；检查条目引文能否支持关联，证据不足时不据连线推断因果或优劣。

#### 10.7.3 任务提示词和报告模板的接入规则

- **task1 精准问答**：不注入四维阅读框架；仍可从四维筛选结果带着文档范围进入问答，输出遵守具体问题与原文证据。
- **task2 对比分析**：默认按“场景 → 问题 → 技术 → 成果”对照，但先给可比性前提；每个差异有来源，至少两个可区分对象。不满足比较条件时描述各自事实并解释不可比，不生成优劣榜。
- **task3 技术研判**：阅读框架辅助组织事实基础，不覆盖“事实 / 推断 / 样本局限”的既有任务结构。项目起止年不能当作成果发生年；无可信时间序列只能做样本差异分析。保留任务自身对方向性不确定性的说明，不给 target 条目添加置信度分数。
- **task4 专项报告**：阅读框架仅接 `phase="report"`；四份内置模板在来源/局限前增加“四维技术图谱”章节，指带引用的四段式文字组织，不建设图数据库或图形画布。综合报告应在现有“未来方向”之后插入并连续编号，修正历史草案中新增/原章节编号冲突。不重复生成整篇同义摘要，不改变各模板原有主旨。

阅读框架只规定阅读与证据语义；task2 提示词规定对比输出，task3 规定事实/推断结构，报告模板独占章节结构。由一个提示装配入口按任务和阶段引用，避免同段框架在基础提示、任务提示、模板各复制一份。自定义任务可以细化输出；已发布自定义模板保持其版本内容，历史已接受不自动加入新节，用户复制新版内置模板后再显式采用。不能把“新设计替换旧代码”解释为重写用户已保存的任务、模板或成果。

### 10.8 运行中提取的保护与升级边界

当前用户再次明确提取仍在进行。本轮只更新文档，不改 `target_extract.md`、`PROMPT_VERSION`、任务提示词、模板、进程或 target 文件，不触发重新提取。

**两种改动不应捆绑**：前端四维筛选/阅读和 task2/task3/task4 的阅读组织本身不改变提取规则，不应因此提升提取版本或要求全库重跑；改变提取规则才同步增加提示版本。历史已接受升级后待更新的结果，不代表要求立即让运行中的任务失效。实现升级需等相关写入结束，核对实际产物版本与处理覆盖，再用隔离样本验证新口径，安排提示内容、校验和版本的一次切换。不得伪改旧 JSON 的版本号冒充重新提取，不得自动对全库重跑。

更新后旧 target 保留并明确待更新，不参与新口径聚合；原文及原文检索仍可用。按需重提取，不能因为缺少新版 target 就阻塞所有阅读和研究。运行中的独立脚本产物是否与产品入口一致需要单独核对；文件数量不等于提取成功，成功份数也不等于事实和关系准确。

## 11. 前端顶层设计优化方案（2026-09-29，提案，未实施）

### 11.1 核心架构结论与适用边界

**建议把 dox_agent 建成以资料为中心的本地研究工作台：用可定位的页面组织资料，用同一阅读器核对证据，用版本化任务组织活动，用成果版本保存研究结果。采用模块化单体前端，保留 React + TypeScript + Vite，以路由、服务端查询缓存和领域模块替换集中式 AppProvider；Tailwind CSS 4 保留，但通过语义令牌与少量 shadcn/ui 组件形成统一界面。**

优先建设资料库，不先建设通用工作流平台。原始文件、解析正文、结构导航、提取结果和检索索引是同一资料的不同表示，不是五套彼此独立的资料库；四维整理是第一种提取方案，不应成为所有资料的唯一模型。数据库目录不是产品导航结构，用户主要看到“资料、整理视图、处理记录、库说明”。

| 核心选择 | 推荐结果 | 主要理由与代价 |
|---|---|---|
| 应用形态 | 浏览器 SPA + 现有 FastAPI；一个前端工程 | 符合本地单用户、Python 解析/检索服务；避免第二个应用服务器。原生文件能力仍依赖后端 |
| 产品骨架 | 左侧全局入口 + 当前上下文导航 + 中央工作区 + 单个检查器/阅读器 | 可表达嵌套与返回；避免连续抽屉挤压。需明确导航状态归属 |
| 模块边界 | app / features / shared，按领域逐步迁移 | 资料、任务、对话、成果独立维护；不为未来拆微前端或多包仓库 |
| 数据流 | URL 管导航，TanStack Query 管服务端状态，React 局部状态/小型 Context 管临时交互 | 解决重复取数、切库串数据、页面恢复和全局状态耦合；需一次明确的状态迁移 |
| 知识表示 | source 只读处理；解析与结构并存；同文档可有多个带版本的提取方案 | 支持科研归纳和技术文档结构导航；多方案需要后端身份、发布与失效契约 |
| 检索 | 优先 BM25；整理摘要/目录定位候选，再读版本化正文；保留正文召回通道 | 避免摘要漏项成为唯一入口；本次不扩重型 RAG、图谱或向量服务 |
| 组件体系 | Tailwind 4 + CSS 语义令牌 + 按需引入 shadcn/ui | 延续现有界面并补齐交互原语；复制进仓库的组件由项目维护 |

**本节是经本轮自审修订的设计方案，尚未实施。** 用户最新明确要求：新旧逻辑冲突时以新设计为主，删除不必要的旧逻辑。因此本方案中的路由取代页面状态切换、查询缓存取代重复取数、领域职责取代集中式业务 Provider，不再受历史首批“不引入路由/不拆组件”的限制；实施时直接替换对应路径，不增加兼容开关，也不为同一取舍再次请求确认。保留仍有效的业务行为、用户数据与尚未完成的验证，不把“删除旧逻辑”扩成删除资料或取消功能的授权。导航归并等确有业务歧义的事项仍列于文末；本轮继续只修订方案。

| 所有状态进入 AppProvider | URL / 查询缓存 / 临时交互 / 局部状态分治 | 消除多重事实源；需要逐旅程清理旧字段 |
| 五个一级入口固定 | 推荐保留对话、资料库、任务、成果为常用入口；Prompt/Skill 收入任务内的“资源”页 | 降低首屏认知负担；这是对 §9 的产品建议，未确认前不删现入口 |
| 原文只读 | 处理流程不改原始内容；显式替换/重命名/删除仍是管理操作 | 延续 §10.3；如果要求法律意义的不可变档案，需另一套版本策略 |

### 11.3 整体技术路线比较

比较标准是现有功能复用、本地部署复杂度、资料交互能力、团队维护负担和迁移风险；不是框架流行度。

| 方案 | 收益 | 代价与主要失败方式 | 适用条件 |
|---|---|---|---|
| **A：React + Vite SPA，模块化改造（推荐）** | 复用阅读器、SSE、会话/成果与现有测试；可逐旅程替换 | 必须真正拆状态职责，否则换目录仍是单体 Provider | 当前本地研究工作台 |
| B：Vue 3 + Vite 或 Svelte 重写 | 可使用其响应式与组件组织方式；新项目起步简洁 | 现有 React 组件、状态逻辑与交互回归成本高；没有证据表明框架是瓶颈 | 团队主要技能改变，且接受完整迁移成本 |
| C：Next.js 等全栈 React 框架 | 对公网内容、SSR 和服务端页面有价值 | 和 FastAPI 形成第二个服务职责中心；本地私有工作台暂无 SEO/SSR 需求 | 将来明确建设公网/多人服务时重新评估 |

Electron/Tauri 是部署形态的另一个维度，不作为本次前端重写理由。只有确认必须提供原生目录授权、系统托盘或桌面分发时再比较；当前浏览器 + 本地 API 足够。保留 npm 与现有锁文件，不为单前端工程改 monorepo、pnpm workspace 或微前端。

### 11.4 资料领域模型与数据布局

#### 11.4.1 一个资料身份，多种表示

```text
知识库 Corpus
  ├─ 文档 Document（稳定身份、作者/时间/来源说明）
  │    ├─ 原始文件 Source（内容哈希、文件位置）
  │    ├─ 解析版本 Parsed（正文、页码/字符定位、解析器版本）
  │    ├─ 结构 Structure（目录、章节树、结构说明、定位关联）
  │    └─ 提取结果 Target（方案版本、源版本、字段、证据、覆盖状态）
  ├─ 提取方案 Profile（目的、schema、完整提示词、版本）
  └─ 可重建索引 Index（解析/target 投影、BM25；向量为可选能力）

资料范围 + 任务版本 → 运行快照 → 回答 / 成果版本 → 引用回原文
```

Document 不等于物理路径；引用至少绑定 corpus、doc_id 和文档版本。库名与目录名仍按现有约定一致，路由与引用使用后端 ID，不以显示名称或数组下标作身份。文件移动是否保留 ID 必须由后端契约决定，前端不能通过相似标题猜测。

数据说明分三处：库说明记录范围、来源、更新方式与限制；文档元数据记录作者、发布日期/项目区间、抓取时间及出处；提取方案说明记录目的、字段含义与适用范围。时间字段分开，不再把项目年份、填表日期、网页抓取日期混成一个“年份”。缺失值显示未知，不推断作者或完成时间。

结构说明与正文分离：技术框架文档可先显示目录/章节摘要，再定位对应正文。解析器生成的标题树与人工/模型补充的结构解释必须有来源标记；保持原文标题和位置，不把导航语义写进原始正文。结构导航是阅读方式，不强制所有基金报告转换成同一种大纲。

#### 11.4.2 多提取方案

每个 Profile 是“schema + 完整任务提示词 + 适用对象 + 输出约束”的版本化整体。JSON Schema 描述结构，提示词描述提取任务，不把两者混在一个含义不明的 `schema` 字段中。四维方案作为内置 `research-facets`；新增研究目的建立另一 Profile，不改写旧结果。第一阶段只读查看方案说明和版本。多方案阶段用简单本地定义文件保存 schema、完整提示词和说明，不建设方案发布平台、分发机制或编辑器。

结果身份推荐 `(corpus_id, doc_id, source_version, profile_id, profile_version)`。发布时固定输入正文、schema/prompt 版本和模型，完成结构校验与证据定位后再次核对源版本，再原子发布。资料或方案更新会使相关结果待更新，但不会使其他方案的有效结果失效。JSON Schema 校验通过只证明结构合法，不能证明归纳准确。

| 状态维度 | 示例 | UI 规则 |
|---|---|---|
| 源/索引可用性 | 可检索、待同步、失败、源缺失 | 决定能否成为新运行证据；显示失效原因 |
| 处理状态 | 未处理、处理中、已完成、未完成/失败 | 只显示真实已处理份数/片段；不按字段数量计算完成率 |
| 字段内容 | 有内容、原文未提及、提取异常 | 未提及可展示，异常可重试，不混为“空” |
| 结果时效性 | 当前、源变化、方案变化 | 过期结果可带标记查看，不加入当前聚合 |
| 成果性质 | 已取得、预期、原文未明确 | 四维中的成果始终显示该性质 |

摘要不是证据终点。按整理内容筛选时明确“仅在已有效整理的资料中查找”，同时显示未整理/失败资料入口；不能把 target 无命中解释为原文无相关资料。先用整理筛选确定显式文档范围，再复用现有正文 BM25 与阅读流程。摘要筛选之外保留全文检索入口；本次前端改造不捆绑新增双通道召回、融合排序或索引服务。

#### 11.4.3 推荐物理布局与迁移

保留库自包含边界和现有目录名称，不因 UI 重构搬动真实语料：

```text
.knowledge/<库>/
  source/                         原始资料，处理流程只读
  parsed/                         既有解析产物，布局沿用现有约定
  datadb/knowledge.sqlite3         既有正文与版本；后续可加可重建 target/结构索引
  vectordb/                       已存在时保留；BM25 模式无需创建/启动向量服务
  target/
    profiles/<profile-id>.json   版本、用途、schema、完整提示词；每方案一份定义
    results/<profile-id>/<doc-id>.json
                                  各方案当前发布结果，内含源/方案版本
.knowledge/.state/                现有应用级状态，继续按既有成组备份契约
```

这是多方案阶段的候选布局，当前仍是 `target/<doc_id>.json`，本次不创建上述目录。每库方案定义以本地文件为权威，不再保留一份可独立修改的代码内定义；迁移内置四维时一次写入即可，不做持续分发。定义变更递增版本，结果保存该次定义快照或可核验的固定内容及哈希，避免只留一个无法回读的旧版本号。每方案只保留当前结果，不建无限历史目录；研究运行所需证据仍按现有 Run/Artifact 契约保存，新增快照字段须同批补后端契约。

两种存储方式均可行：JSON 权威 + 可重建 SQLite 投影便于整库复制和审阅，但需索引失效管理；SQLite 权威 + JSON 导出便于查询与事务，但引入导出一致性和恢复语义。推荐前者以延续 §10；只有实测 JSON 聚合读取成为瓶颈时才增加投影，投影记录源结果指纹并可重建，不能形成双写权威。

多方案迁移必须等待当前提取结束，以独立批次执行：备份 → 将现有四维结果标识为内置 Profile 对应版本 → 校验文档身份与内容哈希 → 写新布局 → 对比数量与可读性 → 切换读取入口。确认切换后删除旧代码路径；旧物理文件可留在备份，不在运行时永久双读。迁移失败切回备份和原版本应用；不得用重新提取全部资料代替保留既有结果。应用级八库合并不解决当前前端问题，暂不调整。

### 11.5 信息架构、嵌套与核心交互

#### 11.5.1 页面骨架

```text
┌─────────┬────────────────┬──────────────────────────────┬───────────────┐
│ 全局入口 │ 当前上下文导航  │ 面包屑 / 搜索 / 当前范围       │ 检查器        │
│ 资料库   │ 库列表或目录树  │ 资料 / 整理视图 / 处理 / 说明   │ 元数据、四维  │
│ 对话     │ 可折叠节点      │                              │ 与证据        │
│ 任务     │                │ 列表、卡片或文档阅读           │               │
│ 成果     │                │                              │ 返回 / 放大   │
└─────────┴────────────────┴──────────────────────────────┴───────────────┘
```

以上是布局关系草图，不是像素级视觉稿。沿用暖中性色和紫色动作色，借鉴 Codex Desktop 的侧栏、中心工作区与辅助阅读关系，不声称已复刻其内部架构。

资料库首页保留库卡片：标题进入库内，添加资料直达上传，与此库对话直达现有对话。库内导航包含：

| 区域 | 主要内容 | 不承担的职责 |
|---|---|---|
| 资料 | 实体目录、文档列表、搜索、状态过滤、批量选择 | 不展示数据库文件作为普通资料 |
| 整理视图 | 选择提取方案；四维筛选/关系浏览；文档摘要与证据 | 不修改原文，不把图形连线当事实关系 |
| 处理记录 | 导入/提取状态、失败原因、继续查询、单份重试 | 不把前端断连当任务失败，不虚构恢复能力 |
| 库说明 | 内容范围、来源、结构说明、数据更新时间与限制 | 不承担全局模型或系统配置 |

资料列表每行以标题、类型、时间/作者、可用性和整理状态为主；详细路径、解析器、哈希等进入检查器。工具栏固定当前库和筛选范围，批量选择后出现操作栏；明确“本页 N 份”与“筛选结果 N 份”，后者只有服务端可固定范围时才提供。

#### 11.5.2 嵌套、展开、折叠与合并

物理目录树与语义分类分开：目录树反映文件位置；场景/问题路径只是过滤投影。同一报告可以出现在多个分类下，计数按去重 doc_id；不移动、不复制原文件。目录逐层展开，先使用已有文件清单构树；只有清单传输/渲染实测成为瓶颈才增加按层加载接口。面包屑始终可返回上层，不随层级增加抽屉。

“合并”默认解释为折叠展示、合并选中范围和去重结果；不自动同义归并，不物理合并库或文件。若将来需要“术语 A/B 归为同一概念”，应保存显式映射、保留原名称与来源，并作为另一个已确认能力实施。

四维默认支持每维单选、跨维交集，筛选标签可独立移除。“同时包含场景 A、问题 B”不等于二者存在关系；只有后端返回的原文明示 relations 才能进入“关联路径”视图。无关联的条目在“未关联内容”中保留，不能为画出一棵树而丢失。

#### 11.5.3 三条优先旅程

1. **资料到证据**：库 → 目录/筛选 → 文档 → 选择原文/解析正文/结构导航/整理结果 → 点引文。可靠 PDF 页码走 PDF；无可靠页码走解析正文的当前定位；版本不匹配停在“资料已更新”，不跳到新版的旧位置。关闭阅读器恢复筛选、展开节点、选中行和滚动锚点。
2. **资料到整理**：选资料 → 选提取方案及版本 → 显示数量、会调用模型和当前处理状态 → 提交 → 切换页面仍可找回 job → 失败项重试。只在显式提交时提取；上传、刷新页面与普通浏览不自动全库调用模型。接口未提供取消时仅允许“停止查看进度”，不标成“取消任务”。
3. **整理到研究成果**：筛选/勾选 → 基于这些资料提问、对比或生成报告 → 显示最终范围与任务版本 → 执行 → 查看来源 → 保存成果/导出。不得悄悄替换当前会话范围；默认新建带显式范围的研究会话，修改现有会话须用明确动作。报告继续遵守当前单库、项目年份窗口和类别预检，显示排除原因。

右侧只保留一个检查器容器；四维详情→证据阅读使用可返回状态，不叠加无限弹窗。长文可放大为主区阅读，返回到原页面。桌面建议上下文栏 240–280px、检查器 360–480px，作为原型起点；宽度不足优先隐藏上下文栏，窄屏改为单栏详情。关闭、返回、折叠分别有独立语义；Esc 只关闭最上层临时界面，焦点回到触发控件。

#### 11.5.4 四维管理到推理研判的完整闭环

本轮补齐的产品目标是“按四维找资料、理解差异、形成可核验研判”，不止展示四组标签。提示语义与历史接入要求统一见 §10.7；下面只规定它们如何影响界面和数据流。

**库内工作区**：保留资料/整理视图；整理视图顶部显示当前方案/版本、可用于当前整理的文档数和未处理/未完成/待更新数量。失败可能与已有成功结果同时存在，处理计数与结果可用计数分开标注，不相加冒充总量。四维筛选平行可达，默认可从“场景→问题”逐步收窄；技术和成果可直接作为起点。卡片展示文档标题及关键技术/成果摘要，逐项可打开来源；不新增与现有文档列表竞争的独立知识卡数据库。

**单份资料**：检查器按固定顺序查看四个切面，保留作者、项目区间、源版本、提示版本和处理覆盖。每个条目展示名称、说明和证据；成果附性质与原始指标。关联仅用简单文字链接展示，并注明“提取记录的原文关联”，可以核对相关引文；未核验前不标“已证实关联”。不把共同出现的场景和技术自动连成解决关系。

**跨文档对照**：勾选至少两个可区分对象后，先在当前工作区给出只读对照表（列为文档，行为四个维度），使用现有 target 字段，不创建新持久对象、不调用模型。单元格保留原文限定和证据入口；目标结果不完整时显示状态而非“原文未提及”。这张表支持材料核对，不自动给差异结论、排名或技术评分；“生成对比分析”才进入 task2。

**送入任务的最小内容**：显式文档范围、用户研究问题、任务/版本及现有参数。四维筛选用于确定范围，服务端再次检查可用性和报告年份/类别；显示“筛选命中、用户选中、实际纳入”的区别。第一批无需新增 target 全量传输协议，模型按现有原文证据回答；筛选词可以作为用户明确可见的问题背景，不能假装服务器收到了全部四维结果。后续只有原文研判实测确有缺口时才加入服务端有效 target 摘要，仍以原文引用为依据。

| 用户目的 | 复用任务 | 产出与证据要求 |
|---|---|---|
| 查明某项技术解决什么问题 | task1 | 直接回答并指向原文，不强制四维长篇 |
| 比较同场景不同技术路线 | task2 | 先比较场景/条件，再比较问题、技术、成果；数值不可比时明确说明 |
| 分析研究重点或路线变化 | task3 | 事实基础、条件推断、反证/缺口与样本局限；按项目去重，时间依据明确 |
| 形成成果、热点或综合报告 | task4 | 原模板主旨 + 四维文字归纳 + 来源/局限；不把预期写成已取得 |

**成果回溯**：研判仍保存到现有 Artifact，展示原文事实、模型推断与证据不足之处；target 不被研判结论反写，模型建议也不自动成为下一轮提取事实。文档浏览按 doc_id 去重，研究统计按可靠项目身份去重；缺项目身份时只报文档样本数，不冒充项目数。保存实际任务、范围和来源版本，不能只保存筛选标签；旧成果继续显示生成时证据边界。

### 11.6 路由与页面划分

推荐 React Router Data Mode：嵌套路由表达布局，路由级懒加载与错误边界负责页面；请求缓存统一交给 Query，loader 如需预取只调用同一 query 定义，不另存一份数据。[官方路由文档](https://reactrouter.com/start/data/routing)支持嵌套与布局组合。TanStack Router 的类型化搜索参数也合适，但本项目路由规模有限，React Router 配合少量显式参数解析足够；不同时引入两套路由。

以下均为**前端目标 URL**，不是新增后端 API：

| 路径 | 页面 |
|---|---|
| `/library` | 资料库首页 |
| `/library/:corpusId/documents?folder=...&q=...&status=...` | 资料列表，文件夹 ID/相对路径由契约决定 |
| `/library/:corpusId/documents/:docId?view=source&version=...` | 可独立访问的文档详情/阅读 |
| `/library/:corpusId/targets/:profileId?scenario=...&problem=...` | 整理视图；键和值编码，不把完整正文放 URL |
| `/library/:corpusId/jobs`、`/library/:corpusId/about` | 处理记录、库说明 |
| `/chat/:sessionId` | 对话工作台；无会话时提供新建入口 |
| `/tasks`、`/tasks/:taskId`、`/tasks/resources` | 任务与 Prompt/Skill 资源；静态资源路径优先匹配 |
| `/artifacts`、`/artifacts/:artifactId?version=...` | 成果列表与指定版本 |
| `/settings` | 本地应用设置 |

列表点击文档可用同一详情 URL 的侧面呈现；直接打开该地址则显示完整详情。显示方式可存在 history.state，业务身份必须在 URL 中；没有 history.state 也能正常阅读与返回库。证据位置可用稳定 evidence ID/定位参数，引用全文不进入地址。输入搜索时 replace，提交导航时 push，避免每个字符制造一条历史。

当前 `src/main.py` 静态处理器不支持上述深链刷新。实施同批补：允许的前端页面路径返回 index.html，`/api/*`、缺失静态资源及非法路径仍返回原错误；index.html 保持重验证，带哈希资源长期缓存。Hash Router 可避免服务端变更，但地址与片段阅读较难统一；若最终选 hash 路由，应统一采用，不能只让开发服务器深链可用。

### 11.7 架构分层与目录建议

```text
frontend/
  src/
    app/
      main.tsx                 入口与 providers
      router.tsx               URL、布局、页面懒加载
      query-client.ts          全局缓存默认策略
      shell/                   导航、检查器容器、全局通知
      routes/                  页面装配与跨领域旅程
    features/
      library/                 库、文件、目录、上传与库说明
        api/                   本领域 query/mutation 定义
        model/                 范围、过滤与展示模型
        components/
      targets/                 提取方案、结果、筛选与处理记录
      reader/                  原文/正文/结构、证据定位
      chat/                    会话、输入、流式运行与分支
      tasks/                   任务版本、模板与 Prompt/Skill
      artifacts/               成果版本、引用与导出
      settings/
    shared/
      api/                     HTTP、错误、SSE、生成的 OpenAPI 类型
      model/                   跨领域 DocumentRef、EvidenceRef 等小契约
      ui/                      Button/Dialog/Tabs/Menu 等通用组件
      lib/                     日期、格式化等确实复用的纯函数
      styles/                  tokens.css、globals.css、prose.css
  package.json
  package-lock.json
  vite.config.ts
  tsconfig.json
```

这是最终职责分布示意，不是第一批目录创建清单。先落 app、library、reader 和必要 shared 文件；四维可以先留在 library，只有内容形成独立职责时再拆 targets。其余领域沿用现有文件，轮到对应旅程时再移动，不提前填满空目录。依赖方向：app → features → shared；shared 不依赖业务；领域内部的组件、hook、API 可以互相协作，不把所有业务逻辑挪回 app。跨领域流程由 routes 层组合，例如 library 提交 DocumentRef[]，app 打开带范围的 chat；library 不读取 chat 的私有 store。reader 由应用装配到各领域旁，接受明确的引用对象，不直接修改其他领域状态。

采用 Bulletproof React 的按功能归组与应用层组合思路，保持比完整分层方法更少的层级；不增加 repository/use-case/entity 等空壳。只为真正共享且稳定的身份定义 shared/model；业务类型留在所属 feature。避免把全目录通过一个 index.ts 全量导出。[结构实践与适用说明](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)。

现有文件迁移：App 拆为 shell/routes；store 中会话发送进入 chat、导航进 router、库数据进 library queries、检查器历史进 shell；Inspector 按目标拆为 feature 内容，shell 只负责容器与返回；api.ts 按领域拆请求，公共传输留 shared/api；conversation.ts、branches.ts、引用定位逻辑尽量保留已存在的行为。用导入规则检查禁止反向依赖，不以文件行数作为验收标准。

### 11.8 数据流与状态管理

| 状态 | 唯一归属 | 持久化与恢复 |
|---|---|---|
| 页面身份、库、方案、筛选、选中文档/版本 | URL + 参数解析 | 刷新/前进后退可恢复；无效参数显式纠正或提示 |
| 库/资料/target/任务/成果/服务端 job | TanStack Query | 服务端权威；按领域键缓存，写成功后定向失效 |
| 检查器返回位置、尺寸、展开节点、滚动锚点 | 路由父布局内 reducer/小型 Context | 浏览返回时保留内存状态；尺寸沿用已有保存方式，不新增整页 sessionStorage 快照 |
| 流式回答的当前增量与输入草稿 | chat 内运行控制器/局部 reducer | 已完成会话仍由 workspace API 持久化；草稿按会话隔离 |
| 单个菜单、悬停、表单编辑 | useState/useReducer | 默认不持久化 |
| 已选文档集 | library/targets 页面范围状态 | 跨页选择显式显示数量；发起任务时固定为请求快照 |

**首批不引入 Zustand。** 小型 Context 只管理布局交互，不能重新汇集服务端业务状态；刷新恢复 URL 中的文档与筛选即可，不承诺所有临时选择和像素滚动位置跨刷新持久化。若实际测得该局部状态造成无关组件频繁渲染，再比较选择性订阅方案，例如 [Zustand](https://github.com/pmndrs/zustand)。Redux Toolkit + RTK Query 可覆盖类似职责，但当前不需要第二套服务端缓存。

Query key 至少包括影响请求的库、身份、版本和筛选。例如 `['document', corpusId, docId, version]`、`['targets', corpusId, profileId, profileVersion, filters]`。筛选对象先规范化，不能让同义参数产生不同缓存。当前没有 profile 的请求使用当前固定方案身份；后端多方案上线前不得发送未知字段。请求传递 AbortSignal；切库后的迟到响应只属于旧 key，不能覆盖新库。以上采用 [Query key 规则](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)，具体刷新策略由业务决定。

```text
用户操作 → URL/局部交互状态
                 ↓
         feature query/mutation → 类型化 HTTP → FastAPI → 本地存储
                 ↑                                  ↓
              视图订阅 ← 定向失效/回读 ← 已发布结果或 job 状态

发送问题 → chat 运行控制器 → POST 流式响应 → 本轮增量
                                           ↓ 结束
                                   回读 Run/会话/成果
```

读取失败保留已有内容但标明“更新失败”；空结果、离线、加载中分开。删除文件、改名、重新提取不提前乐观显示成功；成功后清理受影响 document、targets、库计数与范围缓存。失效文档仍需从显式选择中提示处理，不能静默剔除。库重命名根据服务端返回 ID/路径重定位。

SSE 继续走原生 fetch 流读取，因为现有聊天是 POST；不改用只能直接发 GET 的 EventSource。保留现有事件语义，增量按短间隔/动画帧合并渲染；绑定 session/run，切换页面不把 token 写进新会话。停止请求不等于服务端已取消，应以现有停止契约/服务端状态为准；流断开时不自动重发可能计费的 POST，也不承诺断点续传。

提取 job 提交成功后在应用父布局记录当前 job_id；打开处理视图时由 Query 查询/轮询，跨页面返回可继续查看，不新增常驻监视器。Query 轮询只在视图可见且服务端 running 时继续，终态停止。网络错误显示暂时无法查询，提供重查。当前 jobs 在服务端内存中，重启后查不到应说明“任务记录不可用”，并回读已发布结果；不假装恢复后台运行。需重启恢复时再增加持久 job 记录与恢复协议，不把队列中间件作为前置。

### 11.9 接口层、类型与后端配套

#### 11.9.1 当前接口与候选接口严格分开

以下当前路径已在 `src/main.py` 与 `frontend/src/api.ts` 核对；字段精确定义以代码为准，本节不复制整个接口表。

| 能力 | 当前路径 | 优化边界 |
|---|---|---|
| 库与文件 | `/api/corpora`、`/api/corpora/{corpus_id}/files` | 继续复用；目录分页/服务端筛选需新增契约 |
| 文档与阅读 | `/api/documents`、`/api/documents/{doc_id}`、其 `/file`、`/markdown` | 继续显式传 corpus/version；结构树若需新信息另加契约 |
| 四维列表/详情 | `/api/corpora/{corpus_id}/reports`、`/reports/{doc_id}/target` | 当前固定四维，不代表通用 Profile API |
| 四维执行 | `POST /api/corpora/{corpus_id}/target`、`GET /target/jobs/{job_id}` | 复用 job 语义；多方案与重启恢复尚未提供 |
| 对话、任务、成果 | `/api/chat`、`/api/tasks`、`/api/artifacts`、`/api/runs/{run_id}` | 保留现有任务/版本/范围规则 |

后续多方案阶段建议用 `profiles` 与 `targets` 命名通用资源，避免库内 `reports` 与研究成果报告混淆。候选接口示例为 `GET /api/corpora/{id}/profiles`、`GET /api/corpora/{id}/targets?profile_id=...`、`GET /api/corpora/{id}/documents/{doc_id}/structure`。这些**尚未实现**，只定义职责；请求字段、错误码、分页和发布语义必须先进入后端精确模型，再接前端。不为美化 URL 立即重命名当前接口；真正替换时同批更新调用者并删除旧分支，不另建永久兼容层。

分页建议服务端返回 items、total 与明确页参数，稳定排序以 ID 作次键；只有确认需要长列表游标时才引入 cursor。四维聚合返回全筛选范围的去重文档数，不能用当前页行数冒充总数。页面服务端筛选与客户端分页不能混搭成错误统计。

#### 11.9.2 类型来源

推荐后端 Pydantic 请求/响应模型 → OpenAPI → openapi-typescript 生成传输类型；生成文件不可手改。请求可先沿用现有 fetch，只有确实减少重复请求声明时才采用 openapi-fetch，不把替换传输库作为页面改造前置。当前 target 路由等有未声明精确 response_model 的返回，直接生成只会把缺口带到 TS，必须先补模型，不宣称现有 OpenAPI 已完整。[工具官方文档](https://openapi-ts.dev/openapi-fetch/)。

组件可直接消费生成的 DTO，不为 snake_case 改 camelCase 或中文状态翻译建立通用映射层。只有证据导航等组合行为需要时才定义小型展示类型；不以 `as TargetDetail` 代替运行时验证。以下仅为**组合行为的类型草图**，不是必须逐字段转换的网络响应副本：

```ts
type DocumentRef = {
  corpusId: string;
  docId: string;
  version: string;
};
type EvidenceRef = {
  document: DocumentRef;
  quote: string;
  locator:
    | { kind: 'pdf-page'; page: number }
    | { kind: 'text-range'; startChar: number; endChar: number };
};
type TargetView = {
  document: DocumentRef;
  profile: { id: string; version: number };
  freshness: 'current' | 'source-changed' | 'profile-changed';
  processing: 'unprocessed' | 'running' | 'complete' | 'partial' | 'failed';
};
```

字符范围必须声明与后端一致的计数单位；Python Unicode 字符下标与 JS UTF-16 索引不能直接等同，含 emoji/扩展汉字的正文需转换或返回可核验引文锚点。没有可靠 locator 时展示引文与文档，不能伪造一个定位对象。

TypeScript 负责静态检查；外部导入 Profile 的 JSON Schema 与完整提示内容由后端校验，前端展示校验错误。暂不同时维护一整套 Zod 响应模型。未来确需浏览器编辑 schema 时再引入 Ajv 进行输入预检；服务端仍是最终校验者。SSE 不是普通 JSON 响应，事件联合与解码单独维护并与后端事件契约对照。

HTTP 层统一 AbortSignal、状态码、错误消息与下载文件名处理，不接触 React。保留 status/detail 等信息，404 缺失、现有 422 版本或输入问题、服务不可达分别展示；未来如用 409 表示并发冲突须先改后端契约。仅幂等 GET 可有限重试，创建运行/提取 POST 不自动重试；需要安全重复提交时后端增加幂等键。本地服务地址使用同源 `/api`，客户端不持有模型密钥，不直接访问 SQLite、文件系统路径或向量服务。

### 11.10 组件、样式与设计系统

#### 11.10.1 三种组件路线

| 路线 | 优点 | 代价 / 条件 | 建议 |
|---|---|---|---|
| **shadcn/ui + Tailwind 4** | 组件源码可控，支持现有 React 19/Tailwind 4，可按需迁移 | 项目承担组件更新；需统一原语系列及样式 | 首选，先 Button、Dialog、Dropdown、Tabs、Tooltip |
| Astryx | React 19 设计系统，统一组件/主题/模式，预构建 CSS 可消费 | 当前公开版本标 Beta；整套语义/体积/交互需原型验证 | 有价值的完整替代路线，但本轮不默认引入 |
| 继续全部手写 | 依赖最少、现有样式延续 | 菜单、焦点管理、弹窗语义持续自行维护 | 保留简单现有组件，复杂交互逐步替换 |

Astryx 内部用 StyleX，不等于使用者必须重建 StyleX 编译链；其 README 明确支持预构建 CSS 和 className 覆盖。因此不以“与 Tailwind 不兼容”否定它。推荐 shadcn 的依据是本项目渐进迁移成本，而非断言 Astryx 能力不足。[Astryx](https://github.com/facebook/astryx)、[shadcn 的 React 19/Tailwind 4 支持](https://ui.shadcn.com/docs/tailwind-v4)。

不同时给相同 Dialog/Menu 引入两套底层原语。通过项目 shared/ui 固定语义、尺寸、焦点与错误表现，业务组件只组合它们；不是给每个原语再写一层没有行为的包装。自有 DocumentRow、EvidenceLink、TargetFacetSection、ScopeSummary 留在领域模块。

#### 11.10.2 Tailwind CSS 4 组织

保留 `@tailwindcss/vite`；tokens.css 保存语义 CSS 变量，globals.css 导入 Tailwind 与基础样式，prose.css 仅承接 Markdown/正文排版。使用 `@theme inline` 将语义变量暴露为工具类，不照搬 v3 的 JS 配置教程。[Tailwind 主题变量文档](https://tailwindcss.com/docs/theme)。

```css
@import "tailwindcss";
/* 下列值为提案示例；实施时从现有视觉令牌迁移并检查对比度。 */
:root {
  --surface: #ffffff;
  --foreground: #1a1a1a;
  --border: #e5e3df;
  --accent: #5645d4;
}
@theme inline {
  --color-surface: var(--surface);
  --color-foreground: var(--foreground);
  --color-border: var(--border);
  --color-accent: var(--accent);
}
```

业务 JSX 使用 `bg-surface text-foreground border-border` 等语义类。颜色、间距、字号、圆角收敛到少量尺度；拖动宽度可使用 CSS 变量，不把每个可变尺寸强行做 token。不动态拼接 `bg-${color}`，状态到完整类名用静态映射。复杂阅读器样式可局部 CSS，避免全局选择器泄漏；不再引入运行时 CSS-in-JS。

正文建议从 14–16px 起步、辅助信息 12–13px，密集表格允许紧凑模式；这是设计起点，不是已确认像素规范。维度色与成功/警告/失败色分开，状态始终有文字。保留浅色优先，主题变量为未来暗色提供边界，但首批不增加主题设置、字体下载或动画依赖。

键盘可完成树展开、列表选择、打开证据与返回；焦点可见，Dialog 有焦点约束与回退，非模态检查器不锁全页焦点，动态任务信息使用适当 live region。先用嵌套列表与展开按钮实现目录，只有实现完整键盘规范才标 `role=tree`。窄屏/200% 缩放不遮挡关键操作，减少动画偏好生效，颜色对比度在原型阶段实际检查。

### 11.11 关键依赖与引入时机

版本策略：现有基础栈继续使用锁文件基线；新增依赖采用实施当时兼容的稳定版并锁定。本文不是精确安装清单，不将 `latest` 视为兼容性保证。

| 依赖/工具 | 用途与选择理由 | 引入时机或替代 |
|---|---|---|
| React / TypeScript strict / Vite / npm | 复用现有资产，静态构建给 FastAPI；TS 做领域边界检查 | 保留；随改造检查 `noUncheckedIndexedAccess`，不单独全库修类型 |
| React Router | 页面身份、嵌套布局、前进后退、错误边界 | 资料库深链切片；不用 Next.js 或第二套路由 |
| TanStack Query | 文档/结果缓存、取消、失效、job 轮询 | 先迁移资料库；替换对应 useEffect 取数，不长期双写 |
| Zustand | 选择性订阅的候选，不属于首批依赖 | 局部 Context 实测存在渲染问题后才评估；跨页返回本身不构成引入理由 |
| shadcn/ui 及其选定原语 | 可控源码和一致的复杂交互 | 随实际控件逐个引入；不一键覆盖所有现有样式 |
| clsx / tailwind-merge | 组合条件类、处理可覆盖样式冲突 | 随 shared/ui，选支持 Tailwind 4 的版本；无需业务组件层层合并 |
| openapi-typescript / openapi-fetch | 生成类型；类型化请求客户端为可选简化 | 仅覆盖本次改动接口；先复用现有 fetch，生成类型不强制同时更换 HTTP 客户端 |
| TanStack Table / Virtual | 复杂列、选择与排序；长列表窗口化 | 普通列表先不用；实测出现渲染瓶颈再引入，二者职责分开 |
| react-markdown / remark-gfm | 已有 Markdown 展示 | 保留；不默认开放原始 HTML |
| 原生 PDF 阅读器 | 复用当前页码与文件预检 | 保留；确需稳定页内高亮/批注时再评估 PDF.js |
| Playwright（现有 Python 脚本） | 浏览器真实旅程验证 | 扩展现有脚本；不为前端改造再建立同功能 TS E2E 套件 |
| ESLint + React Hooks 规则、Prettier | 约束依赖方向、hook 用法与格式 | 只覆盖迁移代码；不为格式化重写整个仓库 |

[Table 官方文档](https://tanstack.com/table/latest/docs/framework/react/guide/virtualization)说明表格与虚拟化是可组合职责；选择 Table 不自动获得低成本的大数据渲染。暂不引入 Vitest/组件快照大套件、Storybook 平台、React Flow、图数据库、Service Worker 或浏览器离线数据库；只有对应需求与可验证收益出现后再增加。

### 11.12 性能、可靠性与扩展边界

性能措施以实际瓶颈为条件，当前没有本次测得的速度指标。第一批记录现有库规模、浏览器、构建版本与“开库→列表可操作”“打开正文→可读”“筛选反馈”“流式输入时主区响应”的基线，再与新切片同条件比较，不编造首屏时间、并发量或百万文档承诺。

- **传输**：列表返回摘要，不拉全库正文/target evidence；详情按需读取。服务端分页与聚合先统一语义，再按需加虚拟化，避免只减少 DOM 却仍下载所有资料。
- **渲染**：保留路由懒加载；PDF、长 Markdown 仅在打开时加载。流式 token 更新隔离到当前消息，避免整个资料树随 token 重渲染。对长文优先使用章节窗口，不用全页高亮扫描每次重新计算。
- **缓存**：Query 缓存是性能手段，不是有效性依据。任务执行前服务端重新校验范围/版本；目标结果的当前有效性由源版本和方案版本判断。查询过期时间按资源设置，不能全局无限缓存。
- **失败恢复**：网络断开保留阅读内容与未提交草稿，展示过期状态；服务恢复后重查，不自动重新调用模型。局部阅读失败不卸载整个工作台。
- **内容安全**：已有本地/网页 Markdown 视为不可信输入；不执行 HTML/脚本，链接协议受限。图片和文件访问沿用后端受控入口与路径校验，模型密钥留后端。此处针对真实文档渲染边界，不扩多租户权限系统。
- **扩展**：新增提取目的扩 Profile，新增成果格式扩 artifacts 导出，新增阅读格式扩 reader；不经全局 Provider 增长耦合。可视化先从统计、分组列表与关系表开始；图/矩阵仅展示有来源的数据，不以图形包装推断的事实。

若 profile 数量或结果规模增加，先优化后端索引与接口；不能仅靠换状态库解决磁盘扫描成本。前端无需感知 Chroma、Milvus、Qdrant、PostgreSQL-vector 的差异，本期不为假设向量后端编写驱动抽象或配置 UI。
