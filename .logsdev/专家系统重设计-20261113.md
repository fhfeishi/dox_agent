## 2. 三个方向

### 方向 A：检查层（把要求变成可执行的验收）

把专家从"prompt 最前面的一段角色描述"改成"生成之后的一组检查"。

```
src/expert_checks.py        每条检查是一个纯函数：markdown + 模版 → 违规列表
src/prompts/checks/*.md     每条检查失败时的修复指令（喂给已有的 repair 重试）
```

- `template_sections`：归一化后比对（去编号、去括号补语、同义映射），缺章报出
- `fact_vs_judgment`：研判类任务须有独立研判章节且含「判断/推断」
- `scope_and_limits`：须含「资料范围」「局限」段落
- `missing_listed`：命中不足时须含「缺失/未覆盖」
- `citations_valid`：复用已有 `validate_citations`

失败时把**具体违规**喂进已有 repair（`src/reports.py:406`），不新增模型调用。

| | |
|---|---|
| 收益 | 直接解决 5/7 缺章节；复用现有 repair；纯确定性，可单测；不改变用户可见行为 |
| 代价 | 只影响报告与情报分析，对话仍无专家；不解决"沉淀偏好" |
| 适用 | 只想让输出可验收，不追求"专家会学习" |
| 主要失败方式 | 归一化规则不够，误报导致 repair 反复重试烧额度 |

### 方向 B：方向 A + 修复存储层 5 个 P0

保留现有 4 席存储（表结构、版本、审批、账户隔离质量是好的），修 5 个 P0 让闭环真的转起来，再接情报分析与对话。

- 统一 `TASK_TYPES` 词汇表 + 旧行迁移（`task4`→`report`）
- 学习偏好默认不限库
- 审计页用真实调用参数
- 闸门下沉到 store（`explicit` 从 `feedback_id` 反查，不信调用方）
- 技能正文进 prompt + 校验 `sha256`，越界路径拒绝

| | |
|---|---|
| 收益 | 闭环可用；专家第一次出现在情报分析和对话路径；审计页不再撒谎 |
| 代价 | 保留 4 席（其中 2 席零调用）；`DEFAULT_PROFILES` 与 `AGENT.md` 的重复仍在；对话接专家会改变问答行为 |
| 适用 | 想保留"按账户学习偏好"这个能力 |
| 主要失败方式 | 修完 5 个 P0 后仍只有报告一处生效，收益与 A 接近而代码量翻倍 |

### 方向 C：整体收敛重写（A + 1 席 + 一条沉淀通道）

按前置审查的收敛建议：只留 1 席 `research-analyst`（= stock + intel 的模式合并），`AGENT.md` 只留"因角色而不同"的内容（≤400 字），删掉与提示词重复的部分；`checks.yaml` 承载验收；沉淀只认 `generated_version` vs `current_version` 的 diff。

- `project-application`、`corpus-ingest` 移出席位表（文件进 `archive/`）
- 删除 `DEFAULT_PROFILES`（与 `AGENT.md` 重复），`AGENT.md` 为唯一来源
- 现有 5 张表保留，但 `seat` 字段收敛为单值

| | |
|---|---|
| 收益 | 代码 1509 行 → 约 800 行；一处定义一处检查；审计页与界面都变简单 |

## 4. 建议

**先做 A，把 B 作为第二步按需触发。**

理由：A 直接命中唯一有真实证据的失败（5/7 缺章节），且复用已有 repair，不新增模型调用，可完全单测。B 的 5 个 P0 里，P0-1/2/3/4 修好后能带来的可观测收益，在真实数据上是 0——专家表 0 条数据、用户编辑 0 份，也就是说**闭环修好了，现在也没有数据流过它**。先把验收做出来，等真实有人用偏好和技能时再修闭环，那时才有证据判断值不值。

C 的前提（"1 席够用"）我同意方向，但它推翻 2269 行未提交代码和 40 个测试，在 A 尚未验证前做，风险与收益不成比例。

**结论依赖的关键前提**：你认可"先让输出可验收，再谈学习"。如果你认为"按账户学习偏好"本身就是必须交付的产品能力，那应该直接选 B 或 C。
