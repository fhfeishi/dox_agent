## 我对你目标的理解（请核对）

你要解决的不是某一份文档写得好不好，而是**协作开发的主线断了**。项目已经迭代约 4 周、67 条 query，每一轮都会产出新文档。`PROJECT / ITERATION / DECISIONS` 本来应该是主线，现在却变成只增不减的流水账。结果是新会话的 agent 读不完，也不知道该信哪一份，只能读最近几段，于是又写出一份新的“总体方案”。

你想要的是一套能**持续更新、定期收口**的文档机制：主文档始终只反映“现在”，历史有固定的去处（archive），规则文件反映项目的实际做法，并且这套机制和你“写 query → agent 实施 → 你看界面 → 再写 query”的工作方式配得上。工程化方面，你判断项目还处于 1-demo（玩具阶段）：缺少系统设计和上层设计，代码没有模块化，交互语言也没有成形，工作集中在细小的界面调整上。你想知道怎样才能走到 2-product-demo。

## 结论

1. **文档的问题出在制度和实际脱节，不是文档太多。** 规则写的是 `PROJECTION.md / INTERACTION.md`，实际文件是 `PROJECT.md / ITERATION.md`，映射从来没有写下来。你在 query 里写的“INTERACTION DECISION PRODUCTION”本身就说明了这种混淆。`.logsdev/README.md` 还带着另一套模板规则，其中写着“本目录只维护三份长期文档、过程材料不另存”，但目录里实际有 20 份根目录文档和 5 个子目录。两套规则同时存在，而且都没有被执行。
2. **三份主文档全部失去了“当前”属性。**
   - ITERATION 有 3720 行、607 KB。头部仍写着“更新时间 2026-09-30，当前执行入口 §16.46”，而 §16.46 有两个。61 个已经提交的小节仍标着“未提交”。
   - PROJECT 中有 457 行是“提案，未实施”的 §11，§13 之后变成了按 query 排列的变更记录。
   - DECISIONS 有 100 条，前 80 条按时间正序，后 20 条倒序插入，其中混有“规划”“待实施”的条目。
3. **证据和用户附件大多不在 Git 里。** `verification/` 的 48 个目录中只有 3 个入库；`archive/` 整个被忽略（162 MB）。query 里引用的截图，例如 `archive/主页进入的成果界面.png`，换一台机器或重新 clone 就找不到了。文档中有 24 处链接指向这些未入库的路径。
4. **工作节奏让流水账不断变长。** 每条 query 都会产生一个 ITERATION 小节。这个小节和提交信息、query 回链重复记录同一件事。同一个页面在一小时内被改三轮（领导首页 1551 → 1613 → 1654），每轮都留下一份记录，却没有“这一版已被你接受”的节点。
5. **阶段：同意“现在处于 1-demo”。** 准确地说，是功能广度已经超过 demo，骨架还停留在 demo：没有现行的领域模型；前后端契约靠手写类型；后端一个文件有 99 个路由，前端 68 个组件平铺；交互语言只写在文档里，没有做成组件。所以每一轮只能调整按钮和卡片。02 第二节给出了进入 2-product-demo 的六条出口标准和推进顺序，核心是**暂停细节修改，先做系统设计（先整理现状对象图，再定目标模型），再按对象重构，并把交互语言组件化**。
6. **工程基础上最影响后续工作的四点**（详见 02 第三节）：
   - 没有统一的检查入口，也没有 CI。26 个浏览器脚本要手工逐个运行，其中 2 个已知失败但一直没处理。
   - lint 规则没有固定在项目里，本机 ruff 报 67 项。
   - `.git` 有 2.8 GB，主要是历史中提交过、后来又删除的数据；当前入库的 `.knowledge` 约 667 MB。
   - `main.py` 有 2823 行、99 个路由。
7. **建议：做一次“节点收口”，改为四层文档。**
   - 规则层：AGENTS + DOCUMENTS，只保留一套。
   - 现行层：PROJECT、ITERATION、DECISIONS 和现行设计，全部压缩到“现在有效”的内容。
   - 任务层：每个较大的需求一张任务卡。
   - 档案层：archive，按节点存放快照，并入库。

   以后每个审查节点（例如今天）都执行一次收口。单条 query 的实施记录改为“提交信息 + query 回链”，不再新增 ITERATION 小节。具体文本见 03。
