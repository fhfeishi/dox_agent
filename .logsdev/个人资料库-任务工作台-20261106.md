# 个人资料库：一次任务的工作台（定位、范围化分析与任务模版复用）

日期：2026-11-06
来源：Owner 2026-11-06 讨论“个人资料库基本没什么用、设置产品实现上的缺陷”；结论一“个人资料库就是针对某一个具体的任务设置的”，“缺少信息的提取分析（四维提取、项目索引、场景层级、技术谱系、年度分布、项目关系、领域全景）也确实没有什么存在的意义”；结论二“任务模版复用一下呢？其余的按你的建议来吧”。
状态：草案（P0 第一刀已实施；后续按第 8 节推进）

## 1. 定位

- **系统资料库**回答“这个领域知道什么”：全库语料、管理员治理、四维/谱系/领域全景。
- **个人资料库**回答“我这次任务要用什么、我怎么用它”：一个具体任务的资料与结论工作区，仅本人可见。
- 主链：`建库选任务模版 → 收集（引用/上传）→ 解析校对 → 提取 → 范围化分析 → 对话/报告 → 交付`。
- 个人库**不是**小号系统库：不复制系统库的全库口径，不进入系统统计、领域全景与全员共享。

## 2. 核心机制：范围化分析

只对“本次范围”做分析，数据来源三档：

| 来源 | 做法 | 模型成本 | 落盘位置 |
| --- | --- | --- | --- |
| 系统库引用的文档 | 直接读系统库 `target/`、项目索引、`hierarchy.json`、`lineage.json`，按 `doc_id`/`project_id`/证据 `(doc_id,version)` 过滤 | 0 | 只读，不写系统库 |
| 本人上传的文件 | 在个人工作区跑同一套解析与提取（项目报告走四维，其他类型走资料卡） | 按新增/变更份数 | 个人工作区 |
| 系统库缺失或过期 | 个人提取缓存，标注“个人提取，未进入系统库” | 用户触发 | 个人工作区 |

四条原则：

1. **引用零成本**：系统库已有四维与项目索引，个人库引用后直接可见，不重跑模型。
2. **上传增量**：只对新增或版本变化的文件提取，缓存键 `source_sha256 + schema_version + prompt_version`。
3. **不污染系统库**：个人提取写个人工作区；系统库仍只由管理员维护（D-20261027-1 不变）。
4. **分析快照**：每次分析保存来源文档版本、指纹、参数、覆盖说明；系统库资料更新后提示“分析基于旧版本”，可重新分析。

## 3. 分析模块在个人范围下的含义

| 模块 | 个人范围下的含义 | 数据来源 | 限制 |
| --- | --- | --- | --- |
| 任务全景 | 本次资料来源构成、年份、项目、四维覆盖、缺口、待校对/待提取 | 汇总 | 1 份即可 |
| 项目索引 | 范围内按批准号归并的项目，显示来源库、文件、经费、年份、识别状态 | 系统项目索引过滤 + 上传解析 | 1 个项目 |
| 四维提取 | 每份资料/项目的场景—问题—技术—成果，显示缺提取/过期/覆盖不足 | 系统 `target/` 过滤 + 个人提取 | 1 份 |
| 年度分布 | 范围内项目年度计数与经费，只代表本次范围 | 项目索引 | 计数 1；均值/比例 ≥3 才显示 |
| 项目关系 | 范围内项目的相似/关联，只画范围内节点 | 项目相似度过滤 | ≥2 个项目 |
| 场景层级 | 范围内场景 → 问题 → 技术路线；先过滤系统库层级，不足时做个人范围综合 | `hierarchy.json` 过滤 / 个人综合 | 综合需 ≥3 个项目，否则只列原始条目 |
| 技术谱系 | 范围内技术条目、成熟度、承载项目，范围外节点不画 | `lineage.json` 过滤 / 个人综合 | 综合需 ≥3 个项目 |
| 对比矩阵 | 本次资料按维度并列（方法/数据/结论/指标等） | 四维 + 资料卡 | ≥2 份 |
| 证据包 | 每个结论对应的文件、版本、页码、引文 | 提取证据 | 1 份 |
| 领域全景 | **不做**：个人库不计入系统统计与领域全景 | — | — |

范围化处理规则：

- 年度分布：不足 3 个项目显示“样本不足”，不补零、不求趋势。
- 项目关系：相似只表示描述相近，不等于重复立项。
- 场景层级/谱系：过滤后显示“范围外 N 条”；范围内项目过少不做综合，改为“范围内原始四维条目”。
- 四维：项目报告类上传走同一 schema；论文、专利、政策、笔记走资料卡，不强行四维。

## 4. 任务模版复用（Owner 决定）

**不新建一套“个人任务模版”体系**：个人资料库的“任务”字段直接指向现有的任务模版与报告模版，两者共用同一份定义与版本。

已确认的复用规则：

1. **任务种类来自同一张表**：内置 `task1 精准问答 / task2 对比分析 / task3 技术研判 / task4 专项报告`（`src/prompts/__init__.py` 的 `TASKS`），个人库默认 `task4`。
2. **版本引用引用同一批定义**：个人库存 `task_id + task_version`（内置为版本 0）与 `report_template_id + report_template_version`，与报告运行快照同口径（`src/custom_tasks.py`、`src/custom_templates.py`）。
3. **报告模版来自同一目录**：内置四张（`achievements / hotspots / future_directions / comprehensive`）与自定义报告模版，个人库不改写、不复制。
4. **本人副本（P1，尚未实现）**：如果本人要改某张任务模版，再用现有 `copy_builtin → save_draft → publish → version` 复制成本人副本，副本带 `owner`；个人库绑定副本的 `task_id/task_version`。P0 先直接绑定共享模版，不复制，避免每个个人库都多出一份重复定义。
5. **编辑与可见性**：本人副本可由本人改、发布、归档；管理员不看、不改他人已发布的个人副本（与 D-20261027-1、D-20261028-1 同一思路：共享由管理员维护，个人各自维护）。
6. **运行口径**：个人库发起对话/报告时，服务端按 `task_version` 解析定义（现有 `app.state.custom_tasks.version`），不信任客户端传的定义。

需要延伸的既有机制（与第 4 条一起做）：

- `custom_tasks.sqlite3` 的 `tasks` 表增加 `owner`（当前无所有者），查询与写接口按账户限定；`GET /api/tasks` 只返回共享 + 本人。
- `/api/tasks/custom` 的 `ADMIN_ONLY` 放宽为“任何账户可复制内置或共享模版为本人副本”，其余增删改按 owner 校验（权限矩阵 `scripts/permission_matrix.py` 同步）。
- 报告的 `task4` 运行请求现在用 `find_corpus(corpus_id)` 取单库（`src/api/reports.py`），个人库要接入必须按 `personal:<library_id>` 解析为 `Scope`；P1 先做“单来源 + 所选文档”的报告，跨库报告另议。

## 7. 技术实现

### 7.1 统一 Scope 解析

```text
Scope = system:<corpus_id> | personal:<library_id>
resolve(scope) -> {
  sources:     [{kind: system|upload, corpus_id, info, docs}],
  projects:    [...],
  coverage:    {...},   # 缺提取、过期、样本不足
  fingerprints:{...},   # 文档版本 + schema 版本
  capabilities:{...}    # 能否四维/谱系/报告/审查
}
```

对话、报告、审查、分析、导出只认 `Scope`，不再各自判断 `scan_corpora` 或 `mine-` 前缀。个人范围用一个只读 `CorpusInfo` 视图表示（root / source_dir / db_dir / parsed 指向个人工作区，`kind="personal"`），使 `find_corpus`、`targets._load`、`project_index.library`、`lineage._load`、`hierarchy._load` 均可原样复用。

### 7.2 复用现有数据结构（已核对）

- `targets.py`：`target/<doc_id>.json`，含 `doc_id`、`version`、`schema_version`、`prompt_version`、四维 facets。
- `project_index.py`：聚合项目带 `files[].doc_id`、facets、年份、经费、`identity_status`。
- `lineage.py`：技术条目 id 形如 `<project_id>|<item_id>`，可回到项目与文档。
- `hierarchy.py`：场景/问题/路线/成果均带 `evidence[{doc_id,version}]`，`render_section` 已按来源过滤。

因此“按 doc_id/project_id/证据过滤”不需要重写分析引擎，主要新增一层范围过滤与覆盖统计。

### 7.3 个人提取缓存与分析快照

- 个人提取写 `.local/usr/<账户>/workspace/libraries/<id>/analysis/`，键为 `source_sha256 + schema_version + prompt_version`。
- 分析快照保存来源版本清单、项目归并口径（按批准号去重，显示来自几个库）、模块结果与指纹；报告引用快照，不引用实时数据。
- 复用现有 `runs` / `artifacts` 生命周期，报告进“报告中心”。

### 7.4 权限、成本、隐私

- 个人范围接口只对所有者开放，管理员亦不可见（`mine-` 现有规则不变，个人快照同规则）。
- 默认“仅用已有提取”；模型提取需本人确认并显示预计成本。
- 敏感资料可只检索、不调用模型；提示内容会发送到模型服务。
- 备份须覆盖 `.knowledge/.state/workspace.sqlite3` 与 `.local/usr/<账户>/workspace`（当前默认不入库）。

## 8. 分阶段

### P0：引用型个人库先有用（零模型成本）

- 个人库“分析”页：任务全景、项目索引、四维（只读已有）、年度分布、项目关系、范围内技术/场景条目、证据包。
- 每个模块显示范围、样本量、缺提取/过期；不足时显示“样本不足”。
- 对话接入个人库范围（`Scope`），会话持久化并标注来源。
- 质量页：解析质量、审核入口、提取覆盖。
- 验收：选 6 份系统库资料建个人库（默认 task4）→ 分析页看到 5 个项目、2 个来源、年度/关系/四维/范围内技术条目 → 就此提问得到带引用回答 → 不改系统库、他人不可见、系统统计不变。

### P1：上传、范围综合、任务模版副本与报告

- 上传文件增量提取（项目报告走四维，其他走资料卡）。
- 个人范围综合：场景层级/技术谱系；样本不足时不生成。
- 任务模版副本：`/api/tasks/custom` 对本人开放、`owner` 字段与按账户过滤、个人库绑定 `task_id/task_version`。
- 报告：单来源 + 所选文档；证据包；缺失/过期提取的“个人提取”动作。
- 验收：个人库 4 份引用 + 2 份上传 → 上传质量可见 → 提取后项目索引合并 → 生成技术研判/对比报告（按复用的模版版本）→ 报告可回读快照。

### P2：异构资料与协作

- 论文/专利/政策资料卡、对比矩阵、主题聚类、时间线。
- 分享/只读协作、申请加入系统库、配额与清理策略。
- 验收：非项目报告不强行四维；好的私有资料可提交管理员审核入库。
