## 分级标准

参照工业软件的缺陷分级。每条发现都写明位置、触发条件、影响和最小修正。

| 级别 | 含义 | 处理要求 |
|---|---|---|
| S1 阻断 | 数据丢失或错误、安全缺口、结论数字不可信 | 进入下一阶段前必须关闭 |
| S2 严重 | 主流程断裂，或结构问题使后续修改波及面不可控 | 在本阶段的重构批次中关闭 |
| S3 一般 | 维护成本高、体验不一致，但有绕行办法 | 排进对应模块的重构，顺带关闭 |
| S4 建议 | 偏好或优化项 | 进细节池，不阻断 |

## 二、系统与工程

### E-01〔S1〕对话和报告任务绑定在 HTTP 连接上，关掉页面任务就中止

- 位置：`src/main.py:2017` 的 `if await request.is_disconnected(): return`，位于 `/api/chat` 的流式生成器内。
- 触发：用户提交专项报告后关闭标签页、刷新页面或网络中断。
- 影响：
  - 模型调用中途被丢弃，已经花掉的费用拿不到结果；
  - 用户回来后找不到这次任务；
  - 设计规范 §7.2 的“任务已提交，可以离开”对审查成立，对对话和报告不成立。
- 同一系统里有三套执行模型：
  - 对话/报告：随请求流式执行；
  - 资料审查：线程加锁，有中断恢复（`src/review/routes.py:34-36`）；
  - 导入和四维提取：`app.state.corpus_jobs`、`target_jobs` 只存在内存里（`src/main.py:548-551`），服务重启后状态全部丢失。
- 最小修正：不是在流式代码里加分支，而是统一成一个持久化的任务运行服务，见 02 §1.3 和任务卡 B1。

### E-02〔S2〕后端 99 个路由都写在一个 `create_app()` 闭包里

- 位置：`src/main.py` 共 2828 行；第 500–2828 行是一个函数，99 个 `@app` 路由都定义在函数内部。路由分布：corpora 30、artifacts 13、templates 10、prompt-skills 10、tasks 9、web 6、reports 6，其余 15 个。
- 影响：
  - 路由之间通过闭包变量共享状态，无法按领域单独导入或测试；
  - 改任何一个领域都要动这一个文件，并行开发必然冲突；
  - 10-17 记录为 2823 行，现在 2828 行，说明拆分始终没有开始。
- 已有可复用的写法：`review/routes.py`、`workspace`、`intelligence`、`corpus_groups` 已经是 `APIRouter`（`main.py:591-594`）。
- 最小修正：按领域拆分，见任务卡 B2。

### E-03〔S2〕应用状态分散在 10 个以上的 SQLite 文件里，没有统一的迁移机制

- 位置：`.knowledge/.state/` 下有 `artifacts/artifacts.sqlite3`、`artifacts/templates.sqlite3`、`workspace`、`runs`、`custom_tasks`、`prompt_skills`、`project_index`、`web_snapshots` 各一个库，另有 `review/` 和账户库 `.local/usr/accounts.sqlite3`。每个 store 各自 `sqlite3.connect`、各自 `CREATE TABLE IF NOT EXISTS`。
- 触发：一次操作同时写成果和运行记录；备份时只恢复其中一部分；需要给某张表加字段。
- 影响：
  - README 要求“会话、运行与成果应成组恢复”，但这三者在三个文件里，没有跨库事务；
  - 表结构变更只能靠一次性的迁移脚本（`artifact_migration.py`），每次都要单独设计。
- 最小修正：建一个公共数据库模块，用 `PRAGMA user_version` 做顺序迁移；应用级数据逐个对象合并进一个 `state.sqlite3`，每个库的 `knowledge.sqlite3` 保持独立。取舍见 02 决定 D1。

### E-04〔S2，部署前升为 S1〕权限靠路径正则，默认口令不强制修改

- 位置：
  - `src/auth.py:42` 的 `ADMIN_WRITES` 正则；
  - `auth.py:49-51` 的三个默认账户（admin、owner、user）都使用 `123456`，首次登录不要求修改。
- 触发：
  - 拆分或改名路由时，正则不再匹配，管理员限制悄悄失效，而且没有报错；
  - 部署到多人网络环境时，默认口令可以直接登录。
- 影响：权限是否生效取决于路径字符串，不取决于路由声明。数据全员可见是 10-14 的已确认产品决定，不算缺陷，但进入 v0 前必须重新确认。
- 最小修正：
  - 权限改成路由级 `Depends(require_role(...))`，并保留一条“非管理员写入被拒”的接口测试；
  - 默认账户首次登录强制改密（B5）。

### E-05〔S2〕前端全局 store 承担了全部状态

### E-06〔S3〕前后端契约是手写的

## 三、界面与交互

### U-01〔S2〕设计令牌被大面积绕过，正文字号偏小

- 证据（只统计 `frontend/src/components`）：
  - 硬编码十六进制颜色 239 处，例如 `LeaderHome.tsx:24` 的 `text-[#1f3147]`、`WorkspaceHome.tsx:25-28` 的 `accent: "#4f6554"`；
  - 任意像素字号 10 种：`text-[12px]` 135 处、`[13px]` 111 处、`[11px]` 89 处、`[10px]` 10 处，而 14px 及以上合计约 56 处。
- 触发：机关场景中有年龄偏大的领导读者，常用设备是笔记本，系统缩放常设为 125–150%。
- 影响：
  - 主要阅读文字落在 11–13px，低于本项目自己的设计规范（上下层设计规范 §9：正文 14–16px）；
  - 颜色写死在组件里，同一个“深蓝标题”有多个色值，改一次主题要改几百处；
  - 这正是“每一轮都在调按钮和卡片”的结构性原因：没有可以统一修改的地方。
- 修正：U1 建立令牌和排版刻度，用检查脚本禁止组件中出现十六进制颜色和任意像素字号。

### U-02〔S2〕导航按角色分叉，同一个去处有多个名字

- 证据：
  - `TopNav.tsx:15-139` 中有三套菜单组合：管理员有“概览▾”，领导有“工作台▾”，普通用户是平铺的；窄屏还有一份折叠列表（第 115-119 行）；
  - 同一个去处的名字不统一：
    - 资料库：首页卡片叫“查阅资料”，导航叫“资料库”，库内页签叫“资料文件”，10-19 又要求改成“资料管理”；
    - 审查：“审查申请书”（首页）、“资料审查”（导航）、“形式审查”（子菜单）。
- 影响：
  - 每改一个名字都要搜遍全部组件；
  - 用户在首页点了 A，进去后标题是 B；
  - 10-19 query 提出的三处改名，就是缺少术语表的直接表现。
- 修正：U2 用一张导航配置表加角色过滤，生成全部菜单；U3 建立术语文案表。

### U-03〔S3〕首页按角色复制了三份

- 证据：`WorkspaceHome.tsx:24-29` 和 `LeaderHome.tsx:14-19` 各自定义了同样四项工作入口，只是文案不同；`Overview.tsx` 又是第三套。
- 影响：领导和普通用户的“开始工作”入口已经开始漂移。10-19 要求重做领导首页，如果仍在 `LeaderHome` 上单独改，会产生第四种变体。
- 修正：首页由共用区块组合而成（工作入口、统计卡、我的工作、资料库网格），角色只决定启用哪些区块和顺序（U4）。

### U-04〔S3〕右侧面板和浮层的层级规则分散

- 证据：store 中有 6 个独立的开关状态：`inspectorOpen`、`chatDocked`、`explorerOpen`、`previewDoc`、`drawerOpen`、`newCorpusOpen`，另外还有 `LibraryPage` 里的 fixed 浮层（`router.tsx:27`）。
- 影响：同时打开两个面板时谁让位、关闭后焦点回到哪里，都由各组件自行处理。设计规范 §8 的“一次只开一个主要对象，关闭后回到触发位置”没有一个统一的实现点。
- 修正：F2 中的面板管理器（同一时间一个主面板加一个返回栈）。

### U-05〔S2〕统计口径没有唯一来源

- 证据：首页、概览、年度分布、项目关系各自组织数字。`/api/overview/libraries`（`main.py:2221`）在路由函数里现场统计 `fields`；前端的 `briefing.ts`、`resultsSummary.ts`、`projects.ts` 也有统计逻辑。项目索引中已经有可靠的字段：`start_year`、`funding[].scope/amount_yuan`、冲突检测（`project_index.py:252-291`）。
- 影响：10-19 要求的四张图（领域项目、领域经费、年度项目、年度经费），如果在前端再算一遍，会出现第 N 套口径；经费的缺失、冲突和直接/总经费之分，很容易在图上被当成 0 或混算。
- 修正：一个统计接口，带口径说明（B4），首页图表只负责展示。

## 四、功能与流程

### P-01〔S2〕“开始一项分析”有六个入口、多条执行路径

- 六个入口：对话工作台、存量分析（4 个内置任务）、库内“与资料对话”、情报分析、资料审查、周期总结。它们最终都产生“带来源的正文”。
- 执行路径：
  - 对话、报告、存量分析走 `/api/chat` 加 LangGraph；
  - 情报分析和周期总结各有自己的路由；
  - 审查完全独立。
- 影响：
  - 范围传递、任务状态、失败提示、结果保存，每个入口各实现一遍；
  - E-01 的“离开即中止”只在部分入口存在，用户无法形成一致的预期。
- 修正：统一成“分析任务”对象（类型、范围、模板版本、运行、成果），入口只负责预填（02 §1.2）。审查保留独立的业务规则，但共用运行服务和成果对象。
