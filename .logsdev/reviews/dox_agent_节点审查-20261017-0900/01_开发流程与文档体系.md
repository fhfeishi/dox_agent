## 二、目标结构：四层文档

原则：**每一层只回答一个问题，并且有体积上限和清理时机。**

```text
.logsdev/
├── README.md                 # 只有目录索引：现行文档清单与各自状态；不写规则
├── query.md                  # 原文需求（只保留当前节点以来的条目）＋ 状态标记
├── PROJECT.md                # 现行层：当前有效要求与现状（目标 ≤ 400 行）
├── ITERATION.md              # 现行层：正在进行的工作、未决问题、下一步（目标 ≤ 150 行）
├── DECISIONS.md              # 现行层：仍然有效的决定（顶部一张索引表）
├── design/                   # 现行层：每个主题一份现行设计，开头标明状态
├── tasks/                    # 任务层：一个较大需求一张任务卡（取代 interactions/）
├── reviews/                  # 任务层：节点审查（本目录收口后移到这里）
├── verification/             # 证据：被长期文档引用的目录必须入库
├── inputs/                   # 用户附件：query 引用的截图、样例，按 YYYYMMDD-HHMM-名称.png 命名，入库
└── archive/                  # 档案层：按节点存放快照，文本入库；大文件放 archive/_local/（忽略）
    ├── 2026-1017-node/       #   本次收口：ITERATION 历史、query 历史、被取代的设计与决定
    └── _local/               #   不入库的大文件（zip、旧数据）
```

| 层 | 回答什么 | 谁写 | 什么时候清理 |
|---|---|---|---|
| 规则层（AGENTS、DOCUMENTS、rules） | agent 应当怎么工作 | 你确认后修改 | 发现规则与实际不符时 |
| 现行层（PROJECT、ITERATION、DECISIONS、design） | 现在有效的是什么 | 当前任务的负责 agent | 每个审查节点重写一次 |
| 任务层（tasks、reviews） | 某个较大需求怎么做、做到哪了 | 该任务的 agent | 任务完成后，结论并入现行层，卡片移入 archive |
| 档案层（archive） | 过去是什么样 | 只在收口时写入 | 不清理；只读；**不作为需求来源** |

关键点：

1. **ITERATION 只保留“正在进行”的内容。** 一次就完成的 query 不写 ITERATION，它的记录就是“提交信息 + query 回链”。只有跨会话的任务才在 ITERATION 里占一行，并链接到任务卡。
2. **PROJECT 只写现行要求，不按 query 分节。** query 带来的要求变化直接改写对应条目，旧版本靠 Git 和 archive 追溯。
3. **DECISIONS 只保留现行决定。** 被取代的条目在收口时移到 `archive/<节点>/DECISIONS-superseded.md`，现行文件里只留一行“取代了什么”。
4. **设计文档必须有状态头**，例如 `状态：已采纳 / 部分实施 / 草案 / 已被 X 取代（日期）`。同一主题只有一份现行设计，新方案要么修改它，要么写明取代它。
5. **archive 是快照，不是垃圾桶。** 用户附件放 `inputs/`，过期的交接材料和临时脚本直接删除（Git 保留历史），只有被取代、但仍有追溯价值的文本才进 archive。

## 三、日常流程：一条 query 的生命周期

```text
你：在 query.md 末尾写条目  ## 2026-MMDD HHMM 〔待处理〕
     │  （截图放 inputs/，在条目里链接）
     ▼
agent：读 CLAUDE/AGENTS → README 索引 → ITERATION（短）→ 相关 design / 任务卡
     │  大需求：先复述目标，等你确认；小需求：直接做
     ▼
agent：实施 → 按 verification.md 做最小检查
     ▼
agent：提交（不推送），提交信息写明 query 时间、改了什么、检查结果
     │  如果要求有变化 → 同一次提交里改写 PROJECT / design 的对应条目
     │  如果形成长期决定 → 同一次提交里写 DECISIONS
     ▼
agent：在 query 条目下改状态为 〔已实施 → 提交 abc1234〕，一行说明
     ▼
你：看界面。满意 → 在条目下写“接受”（这一版成为基线）；不满意 → 写新条目
```

审查节点（建议每 15–20 条 query 或每周一次，例如今天）时多做一步**收口**：
1. 把已完成的 query 条目整段移到 `archive/<节点>/query.md`，现行 query 只留未完成和“未接受”的条目。
2. ITERATION 的历史移到 archive，现行文件重写成当前状态。
3. 根据最后一版的事实重写 PROJECT 的现行要求，把提案和变更记录移到 archive。
4. 把被取代的 DECISIONS 和设计文档移到 archive，并更新 README 的现行文档清单。
5. 检查长期文档的链接都指向已入库的文件。

这样，`PROJECT / ITERATION / DECISIONS` 每个节点都会被重写一次，始终是“现在”，这正是你说的“需要更新”。历史有固定的去处，archive 也就真正派上了用场。

## 四、coding agent 的使用建议

你现在的用法里，有效的部分要保留：query 保存原文、大需求先复述再做、先固定一条真实任务再做纵向切片（10-16 的做法）。下面几条是改进建议。

1. **把零散意见先攒起来，再一次提出。** 同一页面一小时三轮修改，每轮 agent 都要重新读上下文，还可能推翻上一轮。建议看界面时把意见先记在一条 query 里，看完再一起交给 agent。也可以让 agent 先给 2–3 个可点击的方案让你比较，这是重构建议第七节阶段 B 的做法。审美偏好通过比较原型来定，不要靠逐条指令。
2. **一个会话只做一张任务卡。** `autoCompactThreshold` 设为 400000，说明会话很长。长会话压缩后容易丢失早先的约束。建议大需求先写任务卡（目标旅程 / 必须保留 / 可删除 / 验收 / 未决，10-16 的“工作任务-资料整理到对比报告”就是好例子），一个会话完成一张卡；换会话时由卡片交接，不依赖对话记忆。
3. **明确“接受”这个动作。** 你在 query 里写“接受”或“基线”，agent 就知道哪一版不能随意推翻。这比在 PROJECT 里堆描述更有效。
4. **多个 agent 时指定一个最终写入者。** 例如 Claude 负责实施和写现行层，Codex 只做审查，把意见写到 `reviews/` 或任务卡的“审查意见”一节，不写 PROJECT/ITERATION，也不新建总体方案。DOCUMENTS 已经有这条规则，但没有落实。
5. **让 agent 用提交来记账。** 每条 query 提交一次，提交信息即实施记录。如果你同意 Q3，ITERATION 就不需要再写“未提交”这类很快过期的状态。
6. **数据处理成本。** 你的个人记忆中已有“数据处理交给 Haiku 子代理”的偏好。凡是需要批量调用模型的任务（重新生成场景层级、谱系、提取），应当在任务卡里写明使用哪个模型、预计调用多少次，由你确认后再执行。
7. **节点审查固定下来。** 像今天这样，每 15–20 条 query 做一次“流程 + 工程”审查，并在审查后执行收口。审查时可以用一个没有读过实现的独立会话，或者用 `/code-review` 检查这一段的差异，避免自己审自己。
