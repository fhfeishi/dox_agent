## 2. 推进顺序

1. Q3核对当前改动、保留他人未完成内容，形成可回退基线；Q1明确检查入口和冒烟集。
2. Q2收口现行文档；D-doc明确运行、迁移和接口差异，不再等待重复的D/C答复。
3. 独立的界面线：U1最小令牌＋U2导航＋U3名称 → U4a领导首页核对与收束 → U4b管理员首页 → F3/F3b统一预览。
4. 工程线：B3迁移机制 → B1先接报告/审查，再接其余长任务；B2逐域拆路由；F1/F2对齐实际接口逐批迁移。
5. U5随相关页面迁移处理细节；A1在代码集成后做G2验收，D-doc产出的现行设计（`design/系统.md`、`design/界面.md`）在此之前完成。

D0不冻结细节：缺陷与误导随时修，纯审美按页面集中。C1–C4已有可接受实现，B4只核对/收敛数据契约，不重新制作首页图表。
界面线与工程线只有在不修改同一文件/契约时才可并行；这是一条执行约束，不是强制派发多agent。B2与B1同域串行，避免执行模型和接口同时漂移。

## 3. 缺陷与变更规则

- 新发现的问题按 01 的分级登记。S1 立即处理，并暂停其他批次的合并。
- 默认按一个可独立解释、验证和回退的变更单元本地提交（不推送），可对应一张或多张相关任务卡；不强制每条query一提交。提交信息写明任务卡编号、query 时间和 `check.sh` 的结果。ITERATION 不再为单次实施新增小节。
- 删除旧代码时登记 cleanup-log（沿用 10-18 的格式：删了什么、在哪里、为什么、如何恢复）。
