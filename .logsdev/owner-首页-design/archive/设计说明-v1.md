# 首页「资料库概览」改版 · demo 说明

> 产物：`library-overview-demo.html`（单文件，无依赖，双击可看）
> 数据：`.knowledge` 下 11 个资料库的**真实** `lineage.json` / `target/*.json` / `source/`
> 状态：待审核版式，未改动 `LeaderHome.tsx`

## 一、这一版做了什么

把 02「资料库概览」原来的「各领域项目数条形 + 应用方向雷达」，换成一张**积累分布图**：

```
横轴：技术条目数（对数）       → 摊子铺得多宽
纵轴：平均成熟度 0–5           → 沉到多深
圆面积：覆盖项目数             → 规模
```

右侧详情随点选切换：技术条目 / 高成熟占比 / 技术体系 / 成熟度阶梯 / 四维覆盖 / 缺口提示。

## 二、为什么换这两根轴

| 原设计 | 问题 | 新设计 |
|---|---|---|
| 左侧横条 = 项目数 | 与 banner 第 1 屏「领域项目分布」同数据同编码，重复 | 横轴改为技术条目数，banner 没讲过 |
| 右侧雷达 = 应用方向 | 代码注释自认「方向由模型归纳，需人工核对」「一个项目可计入多个方向」 | 换成成熟度，有明确 6 档定义 |
| 无纵轴 | 只能看规模，看不出沉淀 | 纵轴用 `items[].maturity`，真实可算 |

成熟度 6 档定义取自 `src/prompts/lineage_assign.md`，不是自拟：

`0 未判定 · 1 理论与方法 · 2 算法与模型验证 · 3 原型与样机 · 4 系统集成与场景试验 · 5 示范应用与转化`

## 三、真实数据读出来的四件事

| 结论 | 数据 |
|---|---|
| 两个库吃掉大半，但沉得最浅 | 医疗 1,336 条 + 机器人 1,025 条 = 87.7%；机器人 80.8% 停在 0–1 级 |
| 「量深兼备」是空象限 | 没有一个库同时超过 100 条且高成熟占比 > 20% |
| 精细的是小库 | 社会治理 16 条、50% 高成熟；信息智能 17 条、35% |
| 结构缺口比数量缺口更硬 | 机器人「问题」维只有 246/510 份文档有归纳（48%） |

## 四、与现有首页的差异

**删掉**
- 「各领域项目数」横向条形列表（与 banner 重复）
- 「应用方向分布」雷达图（口径不可靠）
- 底部 6 列小资料库卡片（与散点重复，点已可选）

**新增**
- 积累分布图 + 点选详情
- 底部三条读数（全库成熟度 / 体量与沉淀 / 最需注意）
- 「只看待补」筛选：高成熟 < 20% 或任一维覆盖 < 95%

**保留**
- banner（改为静态展示，条改为「底轨 + 填充 + 右对齐数值」，小库也能看出位置）
- 工作台、我的工作

## 五、交互（首页级，刻意克制）

| 操作 | 行为 |
|---|---|
| 悬停 | 浮层：条目 / 项目 / 均成熟 / 高成熟占比 / 体系数 |
| 单击 | 选中，右侧详情切换（键盘 Enter / Space 同效） |
| 只看待补 | 淡化非缺口库，其余保留轮廓 |
| 打开资料库 → | 接现有 inspector |

**没有做**：缩放、平移、右键菜单、双击下钻、首次引导。这些是「领域分析」板块的动作，首页只负责「看懂 + 分流」。

## 六、接入 React 的落点

| demo 里 | `LeaderHome.tsx` 里 |
|---|---|
| `LIB` 数组 | `useQuery(libraryOverviewQuery())` 的 `rows`，需补 `lineage.items[].maturity` 聚合（后端目前只给 `lineage.items` 计数，**要加一个 maturity 汇总字段**） |
| `--paper/--ink/--g1` | 现有 `--page-cool / --heading / --primary` 等变量 |
| `@media (max-width:980px)` | 现有页面用 `@container`，接的时候改 container query，否则右侧 inspector 打开时不折行 |
| `#btnOpen` | `showInspector({ kind: "corpus", corpusId })` |

**后端只需补一个字段**：每个库的 `maturity` 分布（6 个数）或至少 `hi4` 计数与 `avg`。其余全部现成。

## 七、待你确认

1. **纵轴用均成熟度还是高成熟占比？** demo 用了均值（0–5 刻度直观），但它受长尾影响，大库天然偏低；改用「成熟度 ≥4 的占比」象限归属几乎不变，且不惩罚大库。
2. **9 个小库挤在左半边**是否可接受？现在是真实断层（4–20 项目 vs 510），对数轴已经是最优解；若不接受，只能把医疗/机器人单独置顶。
3. **「只看待补」的判定**（高成熟 < 20% 或任一维 < 95%）会把医疗也算进去 —— 因为医疗成果维 91%。这个阈值要不要调？
