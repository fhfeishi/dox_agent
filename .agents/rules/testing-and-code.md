# 业务代码与测试规范 (Testing & Implementation)

## 1. 行为优先与 BDD 流程
- **先行验收**：必须先定义验收场景再写实现。严禁先写代码再照着实现补写“自证正确”的测试。
- **命名规范**：测试用例统一以 `user ...` 开头，场景结构严格遵循 `Given / When / Then`。
- **测试行为而非实现**：
  - 断言业务结果（状态变化、接口返回值、数据持久化、对外事件），禁止断言私有方法调用、内部调用次数或内部临时变量。
  - 测试必须具备重构韧性：业务需求不变的前提下，重构内部实现测试不得变红。

## 2. 依赖真实性与 Mock 禁令
- **真实基建**：针对 PostgreSQL、Redis、MQ，优先使用真实测试容器或轻量本地真实实例，严禁对 Client 实例随手打补丁 Mock。
- **契约 Fake**：无法直连的外部第三方服务，仅允许使用受契约约束的 Fake Service 注入，并确保与真实 Schema 一致。
- **禁止异步等待与 Sleep**：涉及定时、轮询、超时等时间逻辑，强制使用测试框架的虚拟时钟（Fake Timers），严禁硬编码 `sleep`。

## 3. 端到端优先与精准测试
- **E2E 优先**：业务逻辑优先从用户入口走到可见结果（E2E / 集成）。仅对纯算法、复数分支计算等逻辑独立提取单元测试。
- **文件级精准测试**：本地自测优先通过改动文件反查受影响的测试用例（文件级依赖映射），严禁改动微小代码却默认全量跑全工程。
- **分级测试标记**：核心链路用例标记为 `.core.spec.ts`，其余普通链路标记为 `.spec.ts`。

## 4. 有效覆盖率 (Branch Coverage)
- **90% 覆盖率底线**：分支覆盖率基准设为 90%，但严禁为了凑数写无业务价值的虚假测试。
- **负向路径必测**：未覆盖的 10% 仅限不可达的底层系统级兜底；所有业务异常、超时重试失败、边界冲突等失败分支必须有明确测试覆盖。
