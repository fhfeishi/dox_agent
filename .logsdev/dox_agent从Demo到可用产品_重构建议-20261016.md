# dox_agent 从 Demo 到可用产品：重构困境与实质建议

日期：2026-10-16  
用途：帮助产品负责人改变与 agent 协作的方式，推动资料管理、资料分析的完整体验升级。本文不是新一轮业务代码实施授权，也不替代既有需求原文。

## 一、我的判断：现在缺的不是更多修改指令

你的困境是合理的。你能判断一个系统“不顺手、不完整、看起来不像目标产品”，却很难逐项说明应该改成什么。这种整体判断本来就不容易拆成按钮级需求，不应全部由你承担。

但目前的协作方式使你同时承担了产品负责人、交互设计师、测试人员和实施监督者四种工作。agent 每次完成一条可验证的小修改，系统便多一个局部改进，却未必更接近你心中的完整产品。

从最新工程记录看，基础能力已经不少：资料管理、证据检索、任务模板、分析报告、独立审查、谱系、成果、角色首页均有实现。因此不能再把问题简单归为“功能不足”。也不建议第一步推倒重写后端。

建议改为：**选一条最重要的真实工作流程，重新设计并替换它在现有系统中的全过程，以任务结果而不是页面数量验收。**

## 二、为什么持续小修难以达到目的

本节是基于需求记录和设计文档的分析，不是对当前版本全部功能重新实测。

### 1. 修改单位是界面部件，用户完成的却是一段工作

近几轮需求多为卡片高度、图表位置、按钮去留、导航收缩等。这些都值得改，但解决不了“拿到资料后怎么整理、怎么找、怎么形成可交付报告”的流程问题。

例如，把“与资料对话”搬到右侧，只改善了打开位置。如果选中文件的范围没有带入问题、回答不能继续成为报告、关闭面板后丢失工作上下文，核心困难仍然存在。

### 2. 系统按能力组织，用户按目的工作

“资料库、技术谱系、存量分析、对话、情报分析、成果”是系统能力和对象，用户通常想的是：
- 收到一批材料，整理好并让别人找到。
- 查清一个方向已经做过什么。
- 比较两条技术路线，写一份有依据的分析。
- 检查申请书哪里有问题，把结果交给相关人员。
- 看近期形成了哪些值得关注的结论。

这些目的可能跨多个现有模块。只优化每个模块内部，跨模块的割裂仍会留下。

### 3. “简洁”多次被理解为少显示，而不是少决策

把说明和操作藏起来有时有用，但如果用户不知道默认模板、实际资料范围和结果去向，就要反复打开确认。界面更空了，使用并不更简单。

真正应该减少的是：重复选任务、重复选库、重复填范围、重复寻找结果；不是把所有必要信息都藏起来。

### 4. 多份设计文本没有形成一份明确的现行取舍

已有《总体交互与展示设计》《机关界面设计语言》《UI与易用性复核报告》和大量 query。它们包含有价值的原则，但也保留了不同阶段的角色分工和入口安排。例如旧文本中的领导只读与后续“领导也要进入工作台”不能同时作为当前约束。

agent 容易各取一段，在局部实现上自洽，却在整体上混搭。问题不是再缺一份更长方案，而是需要明确：哪些决定有效、哪些已替代、哪个体验目标优先。

### 5. 技术测试容易通过，产品任务却没有验收

构建成功、按钮可点击、截图没有溢出，都不能证明资料管理员知道下一步，或领导能正确理解结论。

你一直在承担最后这层验收，且往往在代码做完以后才看到完整效果，所以只能继续发修补指令。

### 6. agent 的完成标准偏向“这次改了什么”

我之前的一些建议也存在这个问题：逐条分析很完整，却继续扩展方案和术语，没有先把一个真实业务任务做成可体验、可否决的完整结果。

后续应要求 agent 主动承担整段流程设计、取舍和证据说明，不能把“你再告诉我哪里不好”作为默认工作方式。

## 三、重构怎么选：推荐按工作流程替换

| 路径 | 收益 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 继续逐页面打磨 | 风险低、见效快 | 容易保留跨模块割裂，反复返工 | 用于明确的小缺陷，不作为主线 |
| 按真实工作流程重构 | 能直接改善实际工作，复用已有后端 | 要同时整理入口、状态和结果去向 | 推荐 |
| 全量重写系统 | 可以重新规划技术结构 | 已有引用、版本、解析与审查经验容易丢失，不能保证产品更好 | 暂不推荐 |

推荐方案的前提：现有业务接口大体可复用。若某个底层契约确实阻止流程成立，就针对它做结构性调整并说明影响，不能用前端特例遮住问题。

## 四、先重构哪条流程

建议第一条选择：

**收到一批项目资料 → 整理进库 → 定位相关材料 → 做一次对比分析 → 保存可交付报告 → 他人查阅依据。**

它能同时检验你最关心的资料管理、资料分析和展示，又不会一开始牵动全部审查规则。

可用现有机器人资料和虚构测试材料，不需要先收集大量新数据。建议准备一个固定验收资料包，包含：
- 两个不同项目和同一项目的两份文件；
- 一份重复上传资料；
- 一份年份或经费不明确的资料；
- 一份读取失败或缺少正文的材料；
- 一个确实需要比较两个项目才能回答的问题。

真实项目内容未经允许不新增外发；原有模型与资料使用边界继续遵守。

### 这条流程应达到的体验

| 环节 | 用户看见什么 | 系统应自动承接什么 | 不应要求用户做什么 |
| --- | --- | --- | --- |
| 接收资料 | 明显的上传入口、目标库和读取结果 | 文件状态、重复提示、已知元数据 | 理解索引、向量库、解析器 |
| 整理资料 | 可搜索的文件/项目列表、少量待核对问题 | 已确认项目身份、来源和已有分类 | 每次手填全部字段 |
| 找到资料 | 搜索、项目名称、简要摘要和原文 | 当前库、筛选和选中范围 | 来回跳几个模块找同一材料 |
| 开始分析 | “比较所选资料”等明确动作 | 选中文件、任务类型和默认模板 | 再次选择同一个库和项目 |
| 调整问题 | 预置问题或可编辑草稿 | 已有范围、引用约束和任务上下文 | 写一段复杂提示词 |
| 获取结果 | 先结论、再差异、再依据 | 任务状态、报告版本和来源 | 猜结果保存在聊天还是成果里 |
| 交付与查阅 | 保存/导出/发布的明确动作 | 已有成果对象和发布语义 | 复制文本重新建一个失去引用的文档 |

“资料读取完成”“可检索”“分析归纳已更新”是不同状态。可做检索的材料不必等待全部图谱生成，失败材料也不能被一张绿色“就绪”卡掩盖。

## 五、建议先统一五个对象，再安排页面

无需新建复杂平台。先明确现有对象在流程中的职责：

1. **资料库**：明确的资料范围与组织容器。
2. **资料/项目**：文件是来源，项目是业务对象；同项目多文件不是多项目。
3. **分析任务**：本次问题、输入范围、模板、状态和结果的绑定。
4. **成果报告**：可继续编辑、导出、发布及回读来源的输出。
5. **证据**：连接上述对象的原文与版本，不是另外一堆用户需要管理的文件。

资料清单、对话、图谱和报告都应围绕这些对象共享选择与状态。若必须在每个页面重新理解同一对象，说明流程仍没有统一。

建议采用“三个阅读层次”：
- **选择范围**：我在处理哪个库、哪些资料？
- **完成工作**：我现在在查阅、比较、审查还是写报告？
- **查看依据**：这条结论来自哪里？

这里的三层不是要求新增三个页面；可在当前工作区和右侧预览中完成。

## 六、你需要提供的不是完整设计，而是几件高价值材料

### 1. 一段真实工作描述

例如：

“我收到几份机器人项目材料，需要确认有没有重复、归到对应库，再比较两条路线，给领导一份两页左右的分析说明。过程中不想重新选资料，也不想把结果复制到其他地方。”

它比“资料库要更简洁、更高级”更能约束设计。

### 2. 一个看完就能判断好坏的任务

固定输入、固定目标，不必固定模型每个字。你要能回答：
- 有没有完成我要做的事？
- 有没有遗漏必要材料？
- 我是否知道当前在处理哪些资料？
- 结果是否能交给别人？

### 3. 参考产品中的具体行为

不必找一个整体长得完全相同的产品。可以分别指定：
- 喜欢某个文件列表的预览与返回；
- 喜欢某个分析工具保留已选范围；
- 喜欢某个报告页面先给摘要再给依据。

说清喜欢的行为，比要求“参考某软件整体风格”更有效。agent 可以调查并提出借鉴，但必须解释迁移到本系统后解决了哪个问题。

### 4. 你不愿接受的体验

例如：
- 选完资料之后又要选一遍；
- 一个普通任务要理解四套模板；
- 看原文回来后找不到原位置；
- 页面空白但不知道下一步；
- 漂亮图表不能解释真实数字；
- 报告生成后不知道在哪里找。

这些禁止项能够直接成为验收条件。

不应要求你先写几十页PRD。agent 应把这些输入整理成具体方案，只有真正影响业务取舍的问题才交给你判断。

## 七、要求 agent 交付“可以体验的替代方案”

下一轮建议这样工作：

### 阶段A：诊断，不急着改

agent 走一遍固定业务任务，交付：
- 当前流程图：用户实际点了什么、哪些步骤重复；
- 最重要的三处卡点及证据；
- 一个推荐的新流程，说明保留、合并、删除什么；
- 需要改的前后端契约和风险。

禁止只列“配色优化、响应式优化、性能优化”等泛泛事项。

### 阶段B：先做完整交互原型

使用固定资料和现有视觉组件，做一条能点通的完整流程。允许暂用静态结果，但必须标明；不能把静态报告当模型验证。

原型至少包括正常路径、读取失败、返回恢复和处理中离开。先不改真实数据库或批量重生成图谱。

最多给两个有实质区别的方案，例如：
- 文件列表为主、右侧承接分析；
- 资料与分析双区并排。

agent 必须推荐其中一个并说清取舍，不把所有决策推回给你。你只需判断哪个更接近实际工作，避免先争论所有像素。

### 阶段C：按已选流程实现一条纵向切片

一次交付包含入口、输入、处理中、结果、证据和返回；不能只说“页面已完成，后台下轮再接”。

复用已有解析、检索、成果、审查能力。旧入口被新流程替代时同步移除，不能继续叠加“新版/旧版”“简洁/高级”两套并行路径；只在确有业务差异时保留高级选项。

### 阶段D：先验证会用，再扩到别的角色

找少量真实用户或熟悉该岗位的人，给任务，不口头教学。记录卡在哪里，而不是问“好不好看”。

这一条流程通过后，再扩展批量资料、周期总结和复杂图谱。领导和管理员视图复用已经可靠的成果与统计，不先让它们成为新的庞大驾驶舱。

## 八、用什么标准拒绝“表面完成”

建议每轮用下面七项验收，不必先设一个综合分数：

1. **目的可完成**：固定任务得到可交付结果，不需补到别的工具里才成立。
2. **范围可理解**：用户随时知道当前库、选中文件和分析范围。
3. **上下文可延续**：查看原文、切视角、离开再回来，不重复选择或丢失输入。
4. **结果可解释**：统计分母、材料缺口和结论依据能直接找到。
5. **失败可处理**：错误说明具体，输入保留，用户知道重试或补什么。
6. **维护成本可接受**：没有新增重复对象、无必要配置项和过时兼容分支。
7. **视觉服务工作**：主要动作清楚，常用笔记本尺寸下可读，键盘与返回可用。

记录完成时间、求助次数、重复输入和无效往返；先测当前基线，再决定改善目标。不要凭空承诺“三次点击完成所有任务”。

构建、自动化测试和截图检查仍需要，但它们只能支持具体技术主张，不能替代上述产品验收。

## 九、三类角色该如何参与重构

- **普通用户**：首先验证能收资料、找资料、做分析、交付报告。当前最新要求允许普通用户管理库和文件，后续设计不得照搬旧版“只允许管理员维护”的约束。
- **管理员/小组长**：关注资料异常、缺失、分析范围、共享模板和结果质量。不是在普通用户页面上再加几十个技术字段。
- **领导**：先读有依据的结论与领域结构，再按需展开技术和报告；领导也需要开始业务任务，不能又恢复成完全不能操作的只读站点。

三种身份是不同默认关注点，不是三套独立业务系统。报告公开范围、发布状态与账号权限另有已确认约定，不能仅为界面漂亮自行改变。

约千人容量和正式涉密部署是后续工程阶段。它们需要独立验证，但不应把现在的产品重构变成一场提前设计所有组织制度的项目。

## 十、分析质量与界面必须一起验收

“界面不满意”有时是内容没有提供有用判断，换卡片不会解决：
- 谱系只有分类名称，没有解释项目为什么属于这里；
- 关系图只展示相似度，没有说明共同点；
- 图表数字来自不同集合，用户无法比较；
- 报告结论像摘要拼接，没有回答实际工作问题；
- 审查列很多建议，却漏掉明确错误。

建议同一个固定任务同时审查界面和内容。每个模块至少回答：
“用户能据此采取什么下一步？依据在哪里？哪些内容现在还不能判断？”

对分析质量不使用一个模糊总分。用少数真实案例检查事实遗漏、错误归属、引用定位、范围一致与结论是否回答问题；没有依据就减少结论，不补通用套话。

## 十一、减少设计文档增殖与跨 agent 分歧

当前已有总体设计，不需要再创建一份并列的“大而全终极方案”。建议：
- query 继续保存需求原文；
- 现有总体设计只维护当前有效取舍及替代关系；
- 每次重构用一份短的工作任务：目标旅程、输入、必须保留、可删除、验收、未决事项；
- 实施记录只写真实变化与证据，不反复把方案宣称为已完成。

角色分工可以是：一个 agent 负责把方案与实现做完整，另一个在明确受托时审查。若你继续用 Claude 与 Codex 交替工作，让两者审核同一任务与证据，不分别发明新的总体设计。

发现方案不同，要求说清“业务目标冲突、数据语义冲突，还是个人审美偏好”。审美偏好通过原型比较，代码正确性通过证据，业务取舍由你确定。不要把每次评价都变成全量推翻前一方案。

## 十二、可以直接交给 agent 的下一轮任务文本

> 本轮重构 dox_agent 的“资料整理到对比报告”完整工作流程。
>
> 目标用户是普通资料管理员。任务是：收到若干机器人项目文件，整理到资料库，找到两个待比较项目，提出对比问题，生成报告，并能逐条打开原文依据。
>
> 请先读取当前有效需求与代码，保留已有原始文件、项目身份、引用版本、成果与发布规则。不局限于现有页面排布；可以合并重复操作、替换旧入口，并提出必要的接口调整，但不得仅靠隐藏按钮假装流程简化。
>
> 首先交付当前旅程的三处主要卡点、一个推荐替代流程和可点击原型。用同一组代表资料演示正常路径、失败反馈、离开后恢复及结果交付；静态结果明确标注。不要先修改真实资料库或批量调用模型。
>
> 我关注的是：不用重复选资料、不需要理解内部配置、一直知道分析范围、结果有用且能追溯、阅读过程中不丢位置。请自行解决普通布局和文案问题，只提出真正影响业务取舍的少量问题。
>
> 交付时说明哪些旧操作被替代、哪些接口可复用、哪些能力还未验证。原型确认后再实施完整链路，并用浏览器旅程与真实人员试用验证；不能用“构建通过”替代“工作能独立完成”。

这段任务将“先设计与原型”和“后续正式实施”区分开。它是建议的下一轮委托文本，不表示本轮已经执行或自动获得全库迁移授权。

## 十三、我建议你现在做的决定

不再先问“整个系统还应加什么功能”。先决定：
1. 哪一条真实工作最重要，值得作为本轮重构对象；
2. 哪一份输入与输出能让你当场判断它是否成功。
