# 资料归纳与通用模板审查：设计—实施方案

日期：2026-10-08。状态：汇总设计稿，已落实六项审核意见，待实施；本轮仅更新文档。
需求依据：query.md「2026-0930 1734」「2026-0930 2351」「2026-1008 1026」，以及用户本轮汇总要求。

## 1. 本版决定与替代关系

1. 保留五入口：对话、资料库、存量分析、资料审查、情报分析。分析成果和回收站继续归于存量分析。
2. 资料审查保留形式、专业两个独立入口和执行任务；删除“自然科学基金申请／企业合作投标”两张领域卡片及其新任务必选条件。
3. 两入口采用同一操作框架：选模板 → 上传/选择申请书 → 核对准备信息 → 运行 → 分层报告。各页只展示一张对应类型的模板主卡，旁边是一张上传申请书卡。不会再创建一套领域选择。
4. 模板支持内置示例、网页新建编辑、上传文字提取、预览、保存与版本；模板规定检查要求，不代替用户申请书。
5. 保留 grant-review 丰富的结果层次，审查前操作简化、审查后依据充分。所有额外信息块都要有真实数据或明确未检查状态。

本版统一后续实施顺序，替代《工程设计复核与审查界面优化方案》中以基金/投标场景选择为前提的工作台部分，以及原需求中两领域预设。该复核文档的代码证据、逐卡证据、预算计量、覆盖状态等设计继续作为参考；后续如有冲突，以本版通用模板流程为准。

“一个卡片”在本方案中落实为每个审查入口一张模板主卡；形式与专业入口分别显示自己的模板，避免同时让用户选择领域和任务。此为交互细化，保留用户明确要求的两种审查。

## 3. 两张主卡与页面结构

### 3.1 入口文案

**形式审查模板**

按所选要求检查申请书的章节完整性、字数、金额、日期和文字规范，定位需要修改或核对的位置。

辅助说明：错别字提供校对建议；字体、版式等仅对已支持的格式检查，不把无法读取当成通过。

**专业审查模板**

围绕研究目标与技术方案，评议合理性、开展必要性、可行性和论证充分性；结合所选资料比较已有工作，给出有依据的修改建议。

**上传申请书**

上传待审正文，自动整理内容与基本信息。需要时补充信息表；原文件保留，可随时查看。

### 3.2 布局

    资料审查                  形式审查 | 专业审查       审查记录

    ┌ 审查模板 ─────────────────┐  ┌ 上传申请书 ───────────────┐
    │ 当前模板名称 · 版本       │  │ 拖入文件或点击上传        │
    │ 本次重点 / 已启用要求数   │  │ 文件名 / 读取状态 / 查看   │
    │ [预览模板] [更换]          │  │ [上传申请书] [选择已上传]  │
    └───────────────────────────┘  └───────────────────────────┘

    准备核对：模板已保存 · 正文可读 · 待核对字段 · 补充信息表
    专业审查：对照资料范围 / 可选政策与文献 / 评价时点
                                                [开始审查]

卡片采用一致尺寸、圆角和留白。模板用浅紫强调、上传用浅蓝强调；按钮文字、图标、焦点边框同时区分功能，不能只靠颜色。开始审查保持唯一最高强调按钮。窄屏上下排列。

卡片点击进入模板预览页/面板，明确返回入口；模板列表、创建与导入收在“更换模板”内。页面保留材料选择与未保存编辑，避免往返丢失。沿用平台检查器查看原文，不叠加多套抽屉。

## 4. 模板预览、网页编辑与上传

### 4.1 预览

顶部：模板名称、类型、版本、来源、草稿/已保存、适用说明。
正文：章节目录 + 分组要求；每项用“对象、要求、检查方式、计数/单位口径、来源”展示。可点击查看详情，不把字段 JSON 给资料管理员。
底部操作：使用此版本、复制编辑；自定义模板可进入编辑。内置模板只读，修改从副本开始。

示例展示：

    项目摘要                          程序计数
    不超过 300 个字符（含 300）
    统计项目摘要正文，不含标题与空白字符。 [查看计数说明]

    项目进度计划                      日期区间
    项目计划应在 2026-10-01 至 2028-09-30 内（含首尾日）
    核对整体起止日期及已明确列出的阶段日期。

### 4.2 网页编辑

提供“新增章节/检查项、修改标题和说明、调整顺序、启停或删除条目”。数值规则用易懂控件：检查对象、上限或下限、单位、章节选择、起止日期。专业条目编辑评价问题、需要对照的资料与期望解释，不要求用户编写提示词或表达式。

保存校验：空名称、非法数值、反向日期区间、重复章节导致歧义要就地提示。草稿允许保留未解决事项；采用模板前必须保存并确认启用项目。可执行条目参数缺失不得当成普通文字后假装已完成检查。

未保存时切换/离开提供保存、舍弃、继续编辑；保存失败保留输入。执行绑定服务端已保存版本。用户明确发布“需人工核查”的条目可执行整份审核，但该条只能列待核查。

### 4.3 上传文字模板

首批建议支持 UTF-8 TXT、Markdown、DOCX 和可提取文字的 PDF；DOC 沿用已有可靠转换能力，有依赖缺失时说明。模板文件、申请书文件使用不同上传语义，不互相替代。

过程：上传 → 读取文字 → 提取章节与要求 → 生成草稿 → 原文/结构对照 → 网页修改 → 保存使用。
保留原文件、提取文本和各条来源位置。提取错误、空文档或扫描件无正文不生成虚假条款；失败后材料及已有模板仍在。

“300以内”“不超过300”“≤300”可对齐包含边界的上限；无法明确的金额类型、章节边界、日期口径标待确认。模型负责结构化建议，程序校验数值与单位，用户确认后才成为执行规则。
导入文本中所有内容视为材料，不允许要求绕过核查或执行工具的文字成为系统指令。

## 5. 六项形式模板示例与执行口径

以下数值来源于 1008 纪要，可提供为可复制的“通用形式审查示例”。这是本次示例模板配置，不是全部基金或企业通用政策。界面使用时明确展示数值；不隐藏启用。

| 项目 | 示例要求 | 执行定义与反例 |
| --- | --- | --- |
| 申报单位 | 不超过 3 家，含 3 | 按明确的申报/联合申报单位名单计数；同名单重复项去重，不按全文机构提及次数计数。单位别名/附属机构归属不明时待核对 |
| 项目摘要 | 不超过 300 字符，含 300 | 仅统计确认的摘要正文。300 通过、301 超限；全文长度不参与本条 |
| 项目背景 | 不超过 200 字符，含 200 | 定位该章节；重复同名章节需确认，不任取首次出现 |
| 项目方案 | 不超过 2000 字符，含 2000 | 覆盖该章节及所属子节；不能只取标题后一个段落 |
| 项目预算 | 不超过 300 万元，含 300 | 示例默认按“项目总预算”解释，预览写明并允许改为申请资助额/直接费用；执行只取匹配字段。缺单位或多个冲突总额待核对 |
| 项目进度计划 | 2026-10-01 至 2028-09-30 内 | 整体开始不早于下界、结束不晚于上界、开始≤结束；已明确阶段不得越界或超整体区间。日期粒度不足、字段冲突时待核对 |

字符计数首版固定采用：正文去空白，中文、标点、字母、数字分别按 Unicode 码点计一字符；Markdown 统计解析后的可见文本，DOCX/PDF 统计可确认章节的提取文本，排除标题、页眉页脚。表格单元格正文计入，图片内文字未可靠读取时标覆盖不足。模板版本固定保存算法标识与口径说明；首版仅支持这一种算法，预览和编辑页只读展示，不提供不能执行的自由切换。不能将字符数称为中文词数。


### 5.1 覆盖与结论联动

判“通过”必须同时满足：检查对象定位可靠、相关内容读取完整、计量口径和输入值已确认、计算满足要求。解析成功或人工确认章节范围本身不等于文字读取完整。

- 摘要已读取 280 字，但含未读取的图片文字：显示“已读取 280 字，完整字符数未能核对”，状态待核实，不显示通过。
- 已可靠定位的摘要文本本身就有 301 字，即使另有未读文字，也可报告已确定超出 300 的问题，并保留覆盖不足提示。
- 上述超限判断仅适用于证据足以确定违反要求的情况；字段范围不确定、重复计入或单位不明时不能据此判违规。部分科目金额不代表总预算，部分阶段合法不代表全部进度合法。
- 每项结果保存定位、读取覆盖、已核对范围和限制；网页与导出一致。没有被发现的问题不等于通过。人工确认范围不能消除仍存在的未读图片或文本缺口。


日期只比较日期，不套用申报时间的时区条件，不用上传日期、填表日期、发表截止日或文件修改时间替代。文件名若明确给出项目区间，可作为候选来源并显示精度；“2026—2028”不足以判断本例月日边界，不自动补 1 月 1 日。具体年月日明确时可按规则核对。删去旧的统一必填日期设计，不增加兼容开关。

找不到章节分两种：文本覆盖可靠、标题/对应关系核对后确实缺失，报告“缺少章节”；解析失败或映射不确定，报告“未能核对”。不能把所有未命中都当申请书违规。

错别字与文字规范是形式审查中的默认校对建议组：给原句、位置、建议改法和必要解释，专业术语/缩写不确定时提示核对，不能批量自动改文或当资格不合格。六项示例之外不自动添加未获依据的数值门槛。

## 6. 专业模板与独立执行

专业模板默认提供六组可编辑评价问题：目标与合理性、相近工作差异、必要性、可行性与资源依赖、技术先进性与验证、风险及薄弱点。政策符合性只有选择政策材料时开展；专业合理性不等于政策符合性。

每组意见输出：原文主张、分析判断、支持/反对证据、尚缺材料、具体建议。专题未覆盖须明确显示，不能为了填满六块生成泛泛意见。

专业模板必须驱动执行：每条问题有模板内稳定 ID，编辑保留 ID 并产生新模板版本，新增问题产生新 ID。执行读取绑定版本中实际启用的问题、说明和证据需求；固定六组仅是初始模板，不是提示词中的隐藏必执行清单。

结果携带对应条目 ID 与本次证据 ID。服务端逐项核对启用清单与结果：遗漏条目单列“未完成评价”，停用条目不计入本次覆盖；未知或停用 ID 的结果不能计为有效完成。覆盖状态与技术判断状态分别保存，不能用总卡片数量代替覆盖数。全部停用拒绝启动，单项未完成保留其余有效结果及限制。

修改一项、停用一项后运行，必须能从请求快照、关联结果和报告看到新要求确实生效；旧报告继续使用旧版本。

专业任务可在没有外部对照时做“申请书内部论证审查”，启动前写明范围；比较已有项目、领域先进性、政策一致性需相应证据。取消现有“必须至少选择一库”对内部审查的阻止；不得悄悄替用户选择资料库。
文献空选就是无附加文献，不能取旧库存补齐；资料库检索范围由用户选择。历史评价的日期不明证据不能证明当时先进性，项目区间不当论文发表时间。

形式任务不自动执行技术评议；专业任务不执行单位数、字数或预算合规清单。材料包可以共享，两个结果独立保存。

## 7. 丰富审查结果，保留 grant-review 的层次

共同首屏：项目与材料版本、模板版本、运行状态、摘要、问题/建议/待核实/通过计数，单独列最终复核未完成数量。不适用可筛选；completed 仅表示生成完成。

形式报告页签：

- 审核概览：主要问题、需要补充的材料、处理顺序。
- 正文与大纲：依模板章节展示，要求/实际值/差异/文字校对。
- 信息表与单位：字段、名单计数、正文与表单冲突及来源。
- 预算与进度：金额口径、构成、总额/合计/差额/公式；时间区间与越界节点。
- 依据与覆盖：启用条款、已检查/待核实/未支持、未读页块、来源与复核。

专业报告页签：

- 审核概览；技术专题；相近项目；政策与文献；修改建议。
- 每条技术意见展示实际 evidence_ids 对应来源和 basis，不只是全局文献清单。
- 相近项目按可靠身份去重，文件份数另列；当前主张/已有事实/差异/缺证据双端对照。
- 无匹配是允许的结果，不能得出原创。预期成果不当已取得成果。
- 修改建议按申请书章节组织，保持原文只读；重审上传新版本，不覆盖原报告。

沿用前一复核方案中的预算可信绘图、状态筛选、独立运行记录和导出规范。页面只渲染有依据的结论；字体版式不支持时显示未检查。不引入总分、获批概率、自动整改或审批流。

## 8. 最小工程契约与旧设计删除

### 8.1 模板唯一对象

继续演进现有 RulePack/GuideCheck 存储和版本，不新建第二套模板服务。审查模板与情报报告的“输出模板”用途不同，不能仅因同名就混用数据契约。

新增/调整最小语义：

- 模板审查类型 formal/professional；名称、说明、版本、条目顺序与启停。
- 模板整体来源 builtin/manual/upload 仅描述建立方式；条目独立保存原始出处（文件版本、位置、原始引文）、当前生效要求及执行参数、人工修订标识。人工新建条目明确标“用户编写”，不伪造 guideline_id、页码或引文。
- 上传原文为 300 字、人工改为 500 字时，预览与导出显示“原文要求 300／本模板人工修订为 500”，执行 500；原文件仅证明原始 300，不能被列为 500 的直接依据。原始出处不可覆盖，修订进入新版本。纯顺序/展示变更与要求修订区分，不凭模型自行消除修订标识。
- 数值条目保存检查对象（章节/字段）、运算、数值、单位、计数口径；日期区间保存上下界及包含边界。
- 专业条目保存评价专题、问题、证据需求；不把自然语言任意编译为可执行代码。
- 新模板不再必须填写 fund、year、scenario；可选的适用说明不参与硬性领域分支。模板版本号和发布时间独立于业务年度。

删除新任务 scenario 字段及 fund/tender 路由校验、筛选和界面卡片。旧报告按保存快照回读，原场景名称可作为历史描述；历史保留不意味着继续运行旧场景分支。旧模板在实施时清点：能明确归类的作一次性迁移，无法判定类型的要求用户选择后另存；不得清空已有模板或悄悄默认全为形式模板。

请求继续复用 /api/review/runs，绑定 task kind、template id/version、不可变材料版本和明确证据选择。具体模板 API 优先扩展既有 rules/guidelines 接口，命名整理随实现决定，不另建同义端点。

### 8.2 材料与执行

一个不可变正文版本+可选信息表；信息表由模板需要和用户选择决定，不是所有通用模板的必备项。由正文可获取的单位名单/金额可核对；两处冲突并列，不固定只信信息表。

准备核对区新增“章节对应核对”：每行展示目标章节 → 识别位置（文件、页/块、标题路径）→ 纳入文本预览 → 定位与读取覆盖状态。模板中的“项目摘要”定义检查对象，这里的对应关系才定义本次申请书实际参与计数的内容。

用户可选择重复标题的正确候选、调整起止文本块、纳入或排除子节/表格、查看跨页连续文本，并保存确认。不做全文编辑器，不允许在此悄悄改原文。重叠选区按块 ID 去重，保留原顺序；不确定和未读取部分明确展示。未保存映射不能执行为已确认版本，但可以以待核对范围运行并返回对应待核实项。

映射绑定材料版本、模板条目 ID 和映射修订号，运行保存快照；材料替换或条目目标范围改变后须重新识别/核对。仅修改字符上限且材料及目标未变化时可复用范围，避免无意义重复确认。历史运行保留原映射。

程序依据有效映射和可计量事实执行计数、比较；模型负责提取候选、文字校对和技术论证。人工确认的字段保留版本和来源，不能被后台提取覆盖。
保存运行使用的模板快照、材料版本、范围与逐条依据；规则更新后旧结果不变。未保存编辑先保存或撤销，不能界面/后端使用不同规则。
通用形式审查不要求技术文献截止日期；专业选择历史模式才明确评价时点。不是新加一组统一日期门槛。

## 9. 全工程主线保持与后续衔接

资料库：继续四维概览→主题→项目→证据→预设分析；项目身份、金额口径、分母和来源有效性沿用原正式需求。
存量分析：按已选主题/项目范围执行，不静默截断；统计取项目索引，解释只基于实际阅读证据。
情报分析：外部材料+库内证据+输出模板，报告入统一成果；替换材料不破坏旧引用。
成果管理：现有预览编辑、版本、导出和回收生命周期保持。审查报告仍保留独立记录；是否新增统一成果入口另需具体需求，不在本轮悄悄搬库。
四维归纳作为独立工作线 G1–G2，人工确认映射与来源提取分开；更新只使相关主题归纳失效。审查真实样例或模型连接受阻，不阻止这条工作线继续。

## 11. 验收载体与反例

优先扩展 tests/test_review_flows.py、tests/browser_review_flows.py 的现有上传—模板—运行—查看—导出旅程；模板迁移依托真实临时存储检验，不用静态字段断言冒充迁移成功。

关键反例：

- 摘要完整读取 280 字、全文 5000 字：摘要检查通过；另有未读图片文字则待核实；可靠摘要范围已读 301 字可明确超限。摘要缺失与未读出正文分别提示。
- 摘要/背景标题重复、章节跨页、含子节/表格：通过准备区选择正确范围并保存，核验计数对应实际预览；重叠块不重复计入；替换材料后旧映射不得沿用为已确认。
- 正文总预算 300 万、信息表 320 万：显示冲突，不任取较小值通过；直接费用不能代替总预算。
- 开始日等于 2026-10-01、结束日等于 2028-09-30 通过；早/晚一天或阶段越界不通过；仅有年份待核对。
- 单位名重复、简称疑似同机构：明确去重结果及未确认项，不无证据合并。
- 模板导入歧义、手工编辑未保存、全部条目停用、保存失败、旧模板归档：不能误用旧版本或空模板生成完整审查。
- 无信息表但正文已有事实可检查；无资料库可执行内部技术论证，不能宣称已完成外部先进性对比。
- 技术证据零条、旧库存非空、日期未知、模型中断、原文定位失败：准确呈现，不补假证据。
- 上传条款 300 改 500：程序按 500 执行，网页/Word 同时显示人工修订和原始 300；旧报告仍按旧版本。
- 专业模板修改一个评价问题、停用另一个：请求绑定启用 ID，结果关联新要求，停用项不执行，遗漏项单列；旧报告内容和版本不变。
- 专业/形式独立运行，模板版本更新不改历史结果，Word 导出与网页结论一致。
- 390px/常用桌面宽度、键盘焦点、分点文本、小数金额、原文返回位置和状态文字可读。

## 12. 交付边界与待补输入

## 13. 四维层级结构与成果相关分析（2026-10-07 需求，2026-10-08 追加）

需求依据：query.md「2026-1007 1241」，正式要求见 [需求文档-资料管理与分析审查](需求文档-资料管理与分析审查.md) §17。本节只定义层级实体、生成位置与界面落点；G1/G2 与 S0–S4 的顺序、退出条件不变，本节接入 G1–G2 工作线，不新增并行项目索引。实施状态：库级综合、资料库场景层级页与报告/情报报告中的层级章节已实现（证据见 ITERATION §16.56、§16.58）；G1 人工归并/改名/撤销已实现（§16.54），G2 主题归纳已实现（§16.57），S4 真实材料验收已完成（§16.59）。仍未做：层级综合与主题归纳的真实质量样例审核。

### 13.1 现有基础与缺口

`src/targets.py:20` 的 `DIMENSIONS`（场景/问题/技术/成果）已按文件级提取出 `items`（含 `id/name/desc/status` 与证据），`src/project_index.py` 聚合为项目级 facets 并按主题汇总 `dimensions`。缺的是维度之下的层级：主题之间没有从属关系、没有“已解决/待解决”的状态、没有技术路线条目，也没有成果侧的方面完成度。当前 `ProjectOverview.tsx` 只展示维度→主题→项目，没有场景→问题→技术路线这一层。

因此本节不新建提取目的，也不改 `DIMENSIONS`；层级在 G1 的主题归属之上建立。

### 13.2 层级实体与字段

四类对象共用现有证据字段（`doc_id` + `version`），保证点击可回读同一版本原文：

| 实体 | 关键字段 | 来源 |
| --- | --- | --- |
| `Scene` | `id`、`name`、`summary`、`project_ids`、`evidence_ids`、`derived_from` | 场景维度主题（红） |
| `Issue` | `id`、`scene_id`、`name`、`state`(`solved`/`open`)、`summary`、`evidence_ids` | 问题维度主题（蓝）归属到场景 |
| `TechRoute` | `id`、`issue_id`、`title`、`summary`、`project_count`、`evidence_ids` | 技术维度主题（绿）归属到问题 |
| `Achievement` | `id`、`scene_id`、`title`、`summary`、`marker_basis`、`evidence_ids` | 成果维度主题（黄）归属到场景 |
| `AspectFinding` | `scene_id`、`aspect`(八项枚举)、`stage`(已取得/在研/仅预期/原文未提及)、`note`、`evidence_ids` | 由成果证据派生，随场景整体失效 |

`marker_basis` 记录标志性依据（覆盖项目数、代表项目、是否已验证），由项目索引计算，不由模型估计。`stage` 复用 R-LIB-05 的口径，不新增第四种状态。

### 13.3 生成与失效

层级由**库级一次模型综合**产生，不做逐文档第二次提取：

1. 输入为项目索引 `coverage.dimensions` 的四维主题清单（主题名＋覆盖项目数＋条目 ID），按维度分组，注明每条主题的项目去重数量。
2. 模型输出只允许引用清单中已存在的条目名。程序逐条校验：场景名必须命中场景主题，问题名必须命中问题主题，技术路线标题必须命中技术主题，成果名必须命中成果主题；无法回指的条目整条丢弃并计入 `gaps`，不补造名称。
3. 方面完成度只能引用该成果条目已有的证据 ID；引用不到任何证据的方面回落为“原文未提及”，模型未给出的方面同样标为“原文未提及”并在覆盖说明中区分。
4. 每个问题固定要求 2 个“已解决”＋1 个“待解决”；供给不足时按实际保留，并在 `coverage.gaps` 记录缺口。
5. 记录保存主题指纹（各维度主题名与其项目集合的 SHA-256）。指纹变化即标“需更新”，只提示受影响范围，不自动重算；页面打开不触发模型调用。
6. 生成失败保留既有版本，状态标“未完成”并附错误原因；不因失败清空已有层级。
7. 人工合并、改名与归属覆盖留给 G1，本节不先建半套人工归属界面。
