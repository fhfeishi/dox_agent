# dox_agent 系统、界面与交互设计：从上层逻辑到下层规范

日期：2026-10-16  
状态：设计建议，待通过完整交互原型确认；本轮不修改业务代码。  
定位：补充《从 Demo 到可用产品：重构建议》的执行细节，说明系统逻辑如何落实到页面、组件和操作。不是另一份并行的现行需求，确认后的取舍应回写现有总体设计。

## 一、首先定义“好用”，不要先选风格

对于本系统，好用至少包含五件事：
1. 用户能直接开始工作，不必先学习系统内部结构。
2. 当前处理对象、范围和状态始终清楚。
3. 常用工作可以连续完成，不重复选择和输入。
4. 结果有用、有依据，能保存、修改、交付。
5. 出错、离开、返回、撤销都有明确结果。

美观要支持这些目标：让重要信息突出、相关信息聚在一起、操作位置稳定、长中文内容易读。深蓝、卡片、动效都只是手段，不是“机关审美”的充分条件。

当前工程已有深蓝灰主色和顶部导航，本轮不建议再换色或更换组件库。优先改变信息组织、上下文承接和工作流程。

## 二、把设计分成五层，按顺序做决定

| 层次 | 需要回答 | 交付给实现者的内容 | 常见失败 |
| --- | --- | --- | --- |
| 业务目标 | 用户要完成什么工作？ | 固定任务、输入和可交付结果 | 只列模块和功能 |
| 对象与规则 | 在处理什么？什么时候算完成？ | 资料、项目、任务、成果、证据的边界 | 同名对象含义不同，状态混算 |
| 信息架构 | 去哪里开始，下一步在哪里？ | 页面职责、默认入口、主辅关系 | 每页都像控制台，重复菜单 |
| 交互行为 | 点下去发生什么，回来怎样？ | 范围传递、状态、错误、返回、保存规则 | 按钮能点，但流程断裂 |
| 视觉表达 | 哪个信息先被看见？ | 字级、间距、色彩、密度、组件状态 | 漂亮静态图，实际长内容难用 |

顺序不能倒置。某个页面总要添加提示和开关才能解释清楚，先检查前两层，而不是继续美化按钮。

## 三、上层系统设计：统一事实对象与工作上下文

### 3.1 五个核心对象的职责

| 对象 | 负责什么 | 不应混淆 |
| --- | --- | --- |
| 资料库 | 组织资料、描述范围、支持检索和分析 | 不是一次分析任务 |
| 原始资料/项目 | 文件提供证据，项目关联多份文件 | 文件数不是项目数 |
| 工作任务 | 一次问题、输入范围、模板、执行状态和输出 | 页面停留位置不是任务状态 |
| 成果报告 | 正文、版本、来源、导出和发布 | 聊天中的说明文字不是正式报告 |
| 证据 | 把判断连接到实际文件与位置 | 相似度不是证明，摘要不是全文 |

沿用现有对象与存储，不为这张表另建通用业务平台。只有现有契约确实无法表达必须行为时才调整。

### 3.2 统一“本次工作上下文”

用户选定的库、项目/资料及当前任务目的，应由各入口传递到同一执行流程。

例：在资料列表选中A、B，点“对比所选资料”，系统应自动带入A、B及对比任务。用户只需要选择或编辑问题；不能进入对话后又按默认库检索，实际换了范围。

最少需要保持：
- 当前浏览的资料库；
- 本次分析的库/文档范围及范围来源（自动选择或人工指定）；
- 分析类型、问题文本和所用模板版本；
- 执行状态、结果和来源。

当前浏览库与本次分析范围必须明确区分。用户看过某库，不等于授权所有后续任务都用该库。已经明确指定资料时，自动选库不得擅自覆盖。

临时页面状态如面板宽度、列表滚动和图谱缩放可本地保存；已经提交的工作与输入范围必须由服务端保存。避免只保存在浏览器，刷新后任务失联。

### 3.3 让对象状态各司其职

- 文件：已上传、读取中、可阅读、读取失败。
- 检索：待更新、可检索、部分资料不可检索。
- 归纳：未生成、处理中、可查看、来源变化需更新。
- 任务：待提交、排队、执行中、完成、失败；中断必须明确。
- 成果：草稿/定稿、发布状态、回收状态分别表达。

不要把这些状态压成一个“就绪”。用户界面按当前操作显示有关状态，不要求把完整状态表铺出来。
文件可检索时即可问答，不应强制等待全部谱系和成果归纳；阅读原文也不需要模型服务在线。

## 四、信息架构：一个入口开始，一处承接，一处交付

先保留已确认的顶栏模块，不立即重命名全部导航。用每页的职责约束解决重复：

| 页面/区域 | 用户来此的目的 | 主操作 | 应下沉的内容 |
| --- | --- | --- | --- |
| 角色首页 | 开始或接续工作 | 继续具体任务/选工作入口 | 大量配置、全量历史 |
| 资料库列表 | 找库、整理库 | 打开库/管理资料 | 每个库的全部分析 |
| 库内资料文件 | 找到、预览、选择材料 | 与所选资料对话或分析 | 模型参数、完整图谱 |
| 库内技术研判 | 理解已有知识结构 | 点选方向并看依据 | 上传维护、报告编辑 |
| 年度/项目关系 | 比较分布、定位项目 | 点图看明细 | 重复的零散关联项目清单 |
| 存量分析 | 选择已有资料的分析目的 | 开始一个分析任务 | 模板生命周期解释 |
| 资料审查 | 上传并检查申请书 | 开始审查 | 默认展开的元数据表和全部规则 |
| 情报分析 | 分析用户提供的外部内容 | 生成分析报告 | 默认要求入库 |
| 成果页 | 找到、修改、交付报告 | 打开/导出/发布 | 原始执行日志 |

按最新query保留独立成果页和周期总结位置，不恢复旧“成果只能从检查器进入”设计。右侧面板继续承担详情与原文，不需要包揽所有工作。

### 三种角色是一套系统的三种默认关注点

- 领导：开始今天的工作、资料库概览、自己的工作；重点读领域结构和可交付结论，也可进入业务任务。
- 管理员/小组长：资料异常、关键路线、缺失证据、共享模板及分析质量；提供维护能力，但不是调试后台。
- 普通用户：整理资料、查阅、提问、比较、审查与报告；按最新要求保留资料库与文件维护能力。

不为角色复制三套资料库页面；共用组件、统计与原文。用户能力和可见范围按当前已确认权限规则执行，不能从“领导”二字推导所有资料可见，也不能从“普通用户”推导只能读不能整理。

## 五、完整任务链：比“少跳页面”更重要

推荐统一的工作链：

    选定资料 → 选择工作目的 → 补充问题 → 提交任务
                                      ↓
    返回继续 ← 打开原文依据 ← 查看结果 ← 排队/执行
                                      ↓
                           保存成果 → 修改 → 导出/发布

不同入口预填不同步骤：
- 资料列表：已选范围，只需选择目的和问题。
- 存量分析：已选目的，补充资料范围和问题。
- 自由对话：问题优先，系统推荐范围。
- 原文阅读：绑定当前资料，可提问或加入对比。
- 成果阅读：可以继续修改或基于明确的新范围再分析，但不覆盖旧版本。

能复用的选择自动传递，能明确默认的不要再次问。不能自动判断的才请用户核对。

“少跳转”不等于禁止路由或把所有内容塞进抽屉。重要工作切换可以进入独立页面，前提是输入、范围、状态和返回位置都能恢复。

## 六、下层布局：固定功能位置，控制默认密度

### 6.1 工作区骨架

    顶栏：稳定的全局业务入口、任务与成果入口、账号
    上沿：当前库/任务、范围摘要、一个主操作
    左侧：当前模块必要目录，可收起
    主区：当前列表、分析内容或报告正文
    右侧：原文、项目或模板详情，按需打开
    底部：仅在编辑任务时显示输入/保存，不长期堆全局工具

列表页、图谱页、编辑页不必完全同构，但同一个功能应遵循相同位置与命名规则。

### 6.2 三种密度，而不是三套模式开关

- 概览卡片：一句主题、关键数字和下一步入口。
- 工作列表：名称、必要字段、状态与操作。
- 阅读详情：摘要、正文和来源，允许长内容。

密度由内容类型决定，不给用户增加“简洁版/专家版/高级版”的学习负担。

### 6.3 卡片并不适合所有内容

卡片适合选库、选任务和展示主题概览。大量文件、审查项、报告记录优先列表或表格。不要为了整齐把一段复杂证据拆成多张难以连续阅读的卡片。

同组卡片字段顺序固定：名称 → 一句说明/核心结果 → 必要数字或状态 → 操作。可以对齐底栏，但不以截掉重要正文换取等高；长文在详情阅读。

## 七、交互语言：把动作、结果和范围说清

### 7.1 按钮命名

按钮采用“动作＋对象”，同一动作处处同名：

| 不够明确的表达 | 推荐表达 | 使用条件 |
| --- | --- | --- |
| 处理、执行 | 开始审查 / 生成报告 | 指向具体任务 |
| 产出 | 查看成果 / 保存为报告 | 区分打开与创建 |
| 更多 | 更多操作 | 展开后明确列操作 |
| 检查器 | 查看原文 / 查看详情 | 业务入口直指内容；内部组件名不必面向用户 |
| 刷新 | 更新资料索引 / 刷新列表 | 分清有成本的处理与普通读取 |
| 完成 | 报告已生成 / 文件已读取 | 不把流程完成当内容合格 |

按钮禁用时说明缺什么；不能只变灰。破坏性动作的确认说清对象和后果，不反复确认可撤销的小操作。

### 7.2 常用反馈文案

- “已上传5份，4份可阅读，1份需要处理。查看原因”
- “本次对比：2个项目、3份资料。更改范围”
- “任务已提交，可以离开。完成后从成果页打开”
- “部分内容未读出，本项暂不能核对。查看对应位置”
- “资料已更新，本结论使用的是上一版本。查看来源版本”
- “未能自动确定资料库。请选择候选库，或明确使用当前范围”

数字必须来自当前实际数据。普通用户错误提示不包含堆栈、配置变量或HTTP代码；管理员可展开诊断信息。

### 7.3 结果语言

正文优先：结论、关键差异、建议下一步、依据与限制。
“已解决”保留项目自述边界，“相近”不写成“重复”，“没有找到”不写成“不存在”。
同一结果不要同时出现红色警告、黄色待核实和绿色完成却不说明各自对象。

## 八、右侧面板与图谱：控制层级而不是一味侧滑

右侧适合短时查阅：原文、资料摘要、项目详情、模板预览。长报告持续编辑、复杂模板维护可以使用主工作区；不要把所有功能塞进窄面板。

规则：
- 一次只打开一个主要对象，顶部有对象名称与来源。
- 从年份清单打开文件后，返回回到该清单，保留位置。
- 切换资料库时，关闭旧库临时详情，或明确标出旧来源；不留下无提示的错配上下文。
- 关闭面板回到原触发位置；键盘可进入、返回和关闭。
- 临时预览不改变当前分析任务的资料范围。

图谱专注模式：
- 收起非必要目录、说明和重复统计，不改业务状态。
- 保留当前库名、退出与缩放复位；双窗格比例可调。
- 同层节点保留，单支下钻，选中技术与详情一致。
- 图上没有原文依据的类别说明与实际项目事实区分。
- 视觉面积扩大后仍需检查节点字号、连线和点击范围，不能只把画布放大。

## 九、视觉设计：用一套少而稳定的规则

建议在现有 globals.css 语义变量上整理，不引入新主题引擎。以下数值是设计起点，需真实屏幕验证，不宣称已达标。

- 主色：沿用现有深蓝灰；主要动作使用同一强调色。分类色、状态色与选中色分清。
- 字体：中文系统字体优先；正文14–16px，分组标题16–18px，页标题22–26px。重要信息不依赖极浅灰小字。
- 间距：统一使用少量间距层级，例如8/12/16/24；分组间距大于组内间距。
- 控件：常用操作有足够点击区，建议36–40px高；文字与图标组合优先于难识别的单图标。
- 边界：用留白和轻边框区分区域，避免每个短句都套一层卡片。
- 状态：始终有文字；无数据、未生成、加载失败三种空态不同。
- 动效：短而可打断，支持减少动态效果；不能让动画延迟连续操作。
- 轮播：最新已要求自动与手动切换，保留此方向；增加暂停/恢复，悬停和键盘聚焦时暂停，不能切走用户正在读的内容。核心任务入口不能只存在于某一张轮播里。
- 响应式：按内容真实可用宽度收束导航，先收辅助项，不在普通笔记本上过早隐藏常用入口；150%缩放单独测试。

不要用“机关风格”作为重装饰的理由。正式感主要来自稳定结构、清楚文字、可靠数字和一致动作。

## 十、分析可视化：一张图只回答一个明确问题

| 用户问题 | 首选表达 | 必须说明 |
| --- | --- | --- |
| 哪些领域资料多？ | 排序条形图 | 文件数还是项目数，是否跨库去重 |
| 不同年份项目如何分布？ | 年度柱图 | 当前需求采用项目数，按立项年归属，年份未知另列 |
| 同年经费差异怎样？ | 散点＋年度平均 | 金额口径、已知金额项目数、缺失与冲突 |
| 技术体系怎样关联？ | 可折叠树/按需路网 | 分类关系、相似关联和配套关系分别解释 |
| 当前分析聚焦什么？ | 条形图或已有雷达图 | 轴的含义、统一零起点、实际刻度和未判定数 |
| 一份报告说明了什么？ | 短摘要＋比较表 | 来源、适用条件和未能回答的部分 |

最新2026-1016 0919已把年度数量改为项目数，不沿用旧“报告份数”说明。工程各处使用同一统计契约，图、标题和点击清单一致。

雷达图保留用户已要求的形式，但不能把每个维度各自归一化成满格；同一个数在不同图中不能使用不明分母。没有多个有意义维度时宁可只给事实句或表格。

指标和分析结论不足时，减少结论而不是增加图表填满画面。

## 十一、默认值与AI主动性

适合自动完成：推荐资料库、带入选中文档、选择已确认默认模板、补问题草稿、恢复上次工作位置。
需要用户明确决定：发送问题、提交审查、发布报告、改变已指定范围、覆盖编辑、删除资料。

AI问题草稿和正式执行之间保留清楚的“发送/开始”。用户已经输入完整问题时不强制先走关键词生成。
模糊问题可给少量候选；路由失败不能悄悄沿用旧库。自动选择优先服从明确人工范围。

模型不可用时，原文查阅、历史成果、模板预览和数据管理仍应可用。不能因为分析服务故障让整个工作区变成不可操作。

## 十二、两个必须打通的具体流程

### 流程A：资料整理到对比报告

上传 → 看到每份处理结果 → 选两个项目 → 对比所选 → 草稿问题已带范围 →
发送 → 离开处理页 → 回到任务/成果 → 阅读差异 → 点引用看原文 →
返回结果 → 保存或编辑报告 → 导出/发布。

用户只决定材料、问题和是否交付。系统承接项目身份、范围、版本、来源和进度。

### 流程B：申请书审查

默认模板可见 → 上传申请书 → 明确字段自动识别，歧义集中提示 →
开始审查 → 离开仍执行 → 结果先列问题 → 点某项看要求与原文 →
导出或修改材料后再次审查。

不同模板可以产生不同结果；不能把所有字段都变成全局必填。新一次审查保留旧结果，不覆盖其输入版本。

两条流程均应包含失败恢复与范围变化反例。实现不能只覆盖“第一次点进来”的顺利路径。

## 十三、工程实现应如何支撑这些体验

这些是行为约束，不要求为每项新建抽象层：

1. 入口复用既有任务创建与范围绑定，不在每个页面分别实现相似流程。
2. 任务状态由服务端维护，面板关闭不取消；只有页面仍需观察进行中任务时刷新。
3. 报告有一个正文与版本来源，聊天卡片、成果页和导出读取同一对象。
4. 已发布内容与当前编辑内容的关系明确，不让旧引用无提示指向新正文。
5. 默认只读取所需摘要，详情点开再取；失败不能降为空列表。
6. 提交期间禁重复点击，后端处理重复请求；重试失败任务时说明是否会再次调用模型。
7. 删除或替换资料考虑已生成成果的引用，按现行生命周期处理，不在UI中绕开契约。
8. 重构选择整条旧路径替换，删除无调用旧组件；不长期保留两套入口与状态。

架构重构的优先单位是“范围传递、任务状态、结果复用”这些实际重复问题，而不是先拆微服务、换数据库或建立通用设计平台。

## 十四、先做什么：一个可执行的最小升级批次

### 第一步：固定流程与信息契约

选择流程A作为第一条；准备固定资料包。写明文件/项目计数、选中范围、任务结果归属及返回规则。以最新query修订已过时的页面分工。

### 第二步：可点击原型

使用现有组件和真实长度的中文内容，演示从选资料到交付结果；失败、空数据和返回恢复也能体验。先验证工作是否连贯，不改真实库。

### 第三步：完整接通并替换旧路径

接通现有API、来源、队列和成果；删除被替代的重复步骤。报告原始功能不因UI精简被削掉。

### 第四步：用任务验收而非截图投票

观察用户是否独立完成、哪里求助、哪里重复输入、哪里误解范围；自动化检查状态与数据，人工检查结论和阅读。只针对具体失败继续迭代。

首批不同时改角色体系、全部导航、所有图谱分类和资料迁移。界面中的专业名称与统计口径若确需变更，先在小样本原型中确定，再扩至全库。

## 十五、给 agent 的设计交付清单

每次应交付以下五项，内容可以简短，但必须互相对应：
1. 一条具体用户旅程及输入/结果。
2. 页面职责与需要保留、合并、删除的旧操作。
3. 范围、状态、返回、异常的交互契约。
4. 有真实长度内容的可点击原型与主要状态截图。
5. 测试证据及仍未验证的业务质量。

验收时追问：
- 你减少了用户哪一个判断或重复操作？
- 哪些选择被自动承接，在哪里可以看见和修改？
- 失败后用户能继续什么？
- 报告能否直接交付，依据能否打开？
- 这个图/卡片/字段帮助用户做什么决定？
- 旧流程是否真的删除，还是又新增了一层？

如果只能回答“更美观、按钮更少、组件可复用”，说明交付仍停留在局部装修。
