# 权限系统 · 上层设计

本文只解决一件事：**在一个资料库 + 知识推理系统里，谁能读哪份资料、谁能改哪条规则**。它不覆盖密级、不等保测评、不做通用 IAM。

三条设计约束来自对话：

- 资料可见性只有一条规则（人的组 ∩ 资料的组），不做密级、不做分级继承。
- 管理侧按三员分立：系统管理员提案、授权管理员生效、安全审计员审计；无超级管理员，管理账户无业务权限。
- 不再为每个资料库设权限管理员。审批落在**科室负责人**这个业务岗位上，属于岗位职责，不新增角色。

## 1. 三个正交概念

现在把 `admin / leader / user` 一个字段揉了三件事，所以怎么改都别扭。拆成三个互不推导的维度：

```
账户
 |-- ① 类别：业务 / 管理            决定"有没有数据范围"
 |-- ② 归属（仅业务）：库 + 组       决定"能看什么"
 |-- ③ 岗位（仅业务）：组员 / 组长 / 科室负责人 / 宣传员 / 资料管理员 / 院领导
 |                                   决定"能做什么"
 `-- ④ 管理角色（仅管理）：sys / aut / saf
                                     决定"能改什么"
```

四者关系是**相乘**：

- 管理账户：②③为空，④有值 → 什么资料都看不到，只能改配置。
- 业务账户：②③有值，④为空 → 能看到什么由①决定，能做什么由③决定。
- 一个人不能同时是两类账户（见不变量 I2）。

这条拆分是整个设计的地基。之前的"超级管理员"问题，本质是把①②③④塞进同一个 `admin`。

## 2. 主体模型

```
自然人
  └─ 账户（一人一账户，不共享）
       ├─ 类别：业务
       │    ├─ 归属：库(AI与机器人自动化) + 主组(感知与视觉) + 兼组(可选)
       │    ├─ 岗位：组员
       │    └─ 个人资料库（仅本人可见，不参与组匹配）
       │
       └─ 类别：管理
            ├─ 归属：无
            └─ 管理角色：sys / aut / saf（三选一，互斥）
```

关键取舍：**归属与岗位分开**。同一个人调到另一个组，只改归属，岗位不变；升任组长，只改岗位，历史归属记录不变。现在的模型把"能看什么"和"能做什么"都塞进 role，任何一次调岗都得改角色，审计上说不清。

## 3. 权限组重构（回答"要不要重新设计"）

要。现在的三个组 `admin / leader / user` 建议整体废除，换成"类别 + 岗位"：

| 现在 | 新模型 | 说明 |
|---|---|---|
| `admin` | `admin-sys` + `admin-aut` + `admin-saf` | 三个独立账户，三选一，互斥 |
| `admin` 的资料库维护职能 | 业务岗 `资料管理员`（科室级） | 属于业务，不是管理员 |
| `admin` 的模板/模型设置 | `sys` 提案 + `aut` 生效 | 配置变更，不是内容操作 |
| `leader` | 业务岗 `院领导` / `科室负责人` | 范围收窄到院/科室，不再全局 |
| `user` | 业务岗 `组员` | 可见性由组归属决定 |

三条理由：

1. `admin` 现在同时能建账户、改资料、看所有报告——这恰好是"超级管理员"的定义，合规上过不去。
2. `leader` 是"看汇总"的岗位，不是权限等级；把它做成 role 会让"领导能不能看正文"永远说不清。
3. `user` 太粗：组员、组长、科室负责人、宣传员的能力完全不同，却共用一个值。

新岗位表（业务侧只有这六个，不再增加）：

| 岗位 | 数据范围 | 核心能力 |
|---|---|---|
| 组员 | 本组 | 读本组、发起申请、建个人库 |
| 组长 | 本组 | 组员 + 审批本组阅读申请 |
| 科室负责人 | 本科室 4 组 | 组长 + 审批跨组、提组划分、管本科室资料 |
| 宣传员 | 本科室 4 组（只读） | 跨组读、禁导出 |
| 资料管理员 | 本科室 4 组 | 导入/删除资料、改元数据（不含定组） |
| 院领导 | 全院汇总 | 看统计与趋势，正文按组 |

## 5. 三员分立

```
时间轴 →
sys   [建号草案]────────[停用提案]────────[改组提案]──────
aut        [生效]──────────────[追认]──────────[生效]─────
saf   ──[记录]──────[记录]──────[记录]──────[记录]──[告警]
```

职责边界：

- `sys` 能提案一切配置，但**不能生效任何一条**，包括自己的账户。
- `aut` 能生效，但**不能提案**，也不能生效自己经手的、不能改自己的账户。
- `saf` 只能读日志，不能改配置、不能改日志、不能看正文。

### 不变量（实现时逐条写成测试）

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| I1 | 管理账户的数据范围为 ∅，系统拒绝给管理账户授可见性 | 出现"能看一切的管理员" |
| I2 | 一个账户只能是业务或管理之一，不能原地转换 | 兼岗绕过三员互斥 |
| I3 | 任何配置变更，提案人 ≠ 生效人 | 一人分饰两角 |
| I4 | `aut` 不得生效自己提的、不得变更自己账户 | 自批自审 |
| I5 | 三员账户增删改必须"上级批文 + sys 执行 + saf 见证"，无批文号拒绝 | sys 自建一个假审计员 |
| I6 | 审计日志 append-only，sys 也无删除权 | 事后抹痕 |
| I7 | 不存在同时具备"提案 + 生效 + 改日志"的账户 | 超级管理员 |
| I8 | 业务可见性只能由 (库, 组) 推导，例外只走有时限的阅读授权 | 私下开小口子 |

I7 是"不得设立超级管理员"的可测试写法：只要能把三种能力画成三列、每列只有对应账户打勾，就不存在超级管理员。

### 三员自身怎么换人

这是最容易设计成死循环的地方（谁批准授权管理员的任命）。答案是**把起点放在系统外**：

1. 上级保密委出书面批文（纸质/签章）。
2. 部署时用离线脚本创建首批三员，Web 界面不提供"创建第一个管理员"。
3. 之后的任免：`sys` 录入批文号 → `saf` 核对签字 → 系统执行。`aut` 不参与，因为被换的可能正是 `aut`。

## 6. 账户生命周期

```
待激活 --首登改密--> 启用 --停用--> 已停用 --90 天--> 归档
                     |  ^
                 锁定 |  | 解锁（sys 提案 + aut 生效）
                     v  |
                   已锁定
```

规则：

- **不物理删除**。停用即失效，会话立即作废；90 天后归档，保留 id 供审计回溯。
- 停用是唯一允许 `sys` 单步执行的动作（安全阀），但须 24 小时内由 `aut` 追认，否则升级告警给 `saf`。
- 调岗：停用旧归属 + 新建归属，两条记录，不覆盖。旧组的历史授权立即失效。
- 口令：`sys` 只能发一次性重置码，永不可见明文；首次登录强制改密；三员账户加二次确认。

## 7. 三条主流程

### 7.1 账户变更

```
科室负责人 申请 ──► sys 建草案 ──► aut 生效 ──► 账户可用
                        │              │
                        └─ 驳回 ◄──────┘
```

### 7.2 阅读申请（上一轮已细化）

```
用户点锁定行 ──► 申请（资料 + 期限 + 理由）──► 科室负责人批 ──► 立即生效
                                                    │
                                              跨库时加 aut 一道
```

### 7.3 定组 / 改组划分

```
科室负责人 提案 ──► sys 复核影响面 ──► aut 生效 ──► 全库可见性重算
```

影响面必须显示：多少份资料换组、多少人的可见集合变化。改的是全库可见性，不是单份。

## 8. 审计

记什么：

- 登录、登出、失败、锁定；
- 账户与归属的每次变更（前后值）；
- 阅读申请、审批、生效、到期；
- 全文打开、导出（doc_id + 账户 + 时间）；
- 配置变更（策略、组划分、模型参数）。

不记什么：

- 正文内容。日志只存 `doc_id` 与内容哈希，审计员看得到"谁看了第 7 号文档"，看不到文档写了什么。

保留：在线 ≥ 6 个月，归档 ≥ 3 年；每日哈希链锚定，跨日不可改写。

## 9. 数据模型

```
accounts(id, username, class, post, admin_role, status, pwd_hash, must_change, created_by, created_at)
memberships(account_id, library_id, group_id, kind, valid_from, valid_to)
doc_groups(doc_id, library_id, group_id, weight, is_primary)
grants(account_id, doc_id, granted_by, approved_by, from, until, reason, state)
requests(id, kind, payload, requester, state, created_at, decided_by, decided_at, expire_at, note)
audit_events(seq, ts, actor, action, object_type, object_id, decision, detail_hash, prev_hash)
policies(key, value, version, proposed_by, approved_by, effective_at)
```

`class` 与 `post/admin_role` 分开存，并加约束：`class='admin'` 时 `post IS NULL`，`class='business'` 时 `admin_role IS NULL`。

## 10. 界面

顶部右侧，头像左边：

```
[系统管理 3] [授权管理 2] [安全审计]   通知 ●3   李×× ▾
```

- 每个管理账户只看到自己那一个入口（另两个不渲染，不是禁用）。
- 业务账户一个都看不到。
- 徽标是待办数：系统管理 = 待提交草案 + 被驳回项；授权管理 = 待生效 + 待追认；安全审计 = 未读告警。
- 三个台共用一套壳：左侧分区、右侧详情，列表行统一"状态 + 提交人 + 时间"。

现有 `admin` 的资料库维护界面不消失，只是换到业务岗 `资料管理员` 名下。

## 11. 迁移与分期

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 账户类别 + 三员账户 + 顶部入口隔离 + 登录后按类别分流 | 三员互斥、管理账户看不到任何资料 |
| P1 | 库/组归属 + 列表、检索、引用、导出的统一过滤 | 任意账户的可见集合可复算 |
| P2 | 阅读申请与审批 | 一条申请从提交到到期全链路留痕 |
| P3 | 审计中心 | 能复现任意一次配置变更的前后值 |
| P4 | 组划分工单 + 影响面预演 | 改组前能看到多少人受影响 |

P0 是纯账户层，不动资料数据，可以先做；P1 才动可见性，风险最大。

现状差距：

- `src/auth.py` 的 `Role = Literal["admin","leader","user"]` 与单 `admin` 判定要整体替换，不做兼容分支。
- `scripts/permission_matrix.py` 的 `ROLES` 与能力表要按本文重写，它现在是唯一能自动发现"漏判"的东西。
- `api/reports.py`、`review/routes.py`、`api/web.py`、`chat.py` 各自写的"作者或管理员"要收敛到一个判定函数。

## 12. 未决

1. 院领导能不能看正文？现在设计是"只看汇总，正文按组"，若要看需走阅读申请。
2. 原 `admin` 名下的历史报告归谁？建议归 `sys` 仅元数据，或建一个"系统归档"账户。
3. 科室负责人是否兼任资料管理员（小科室可能一人两岗）？允许兼任，但要在账户上显式记录。
4. 三员是否要求独立终端/独立登录入口？现在是同一登录页 + 登录后分流。
