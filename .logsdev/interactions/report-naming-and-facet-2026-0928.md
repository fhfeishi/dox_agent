## 2. 报告文件名规范

### 2.1 命名模型

`<库名>_<主题>_<类型>_<年窗>_<日期>`，例：

```
AI与医疗_AI辅助癫痫致痫网络识别_成果报告_2023-2026_20260928.docx
AI与机器人自动化_无人机集群自组网_对比分析_2021-2025_20260928.md
```

| 段 | 来源 | 缺失时 |
|---|---|---|
| 库名 | `CorpusInfo.name`（`corpus_id` → 查表） | 省略该段 |
| 主题 | `params.domain`，过长时截断到 20 字 | 用 `params.focus` / `params.purpose`；仍无则省略 |
| 类型 | 报告 → `TEMPLATE_NAMES[template_id]`（"成果报告"）；对话成果 → `TASKS[task_id].name`（"对比分析"） | `fallback`（`report` / `answer`） |
| 年窗 | `year_from`–`year_to`（相等时为单年） | 省略 |
| 日期 | `created_at` 的 `YYYYMMDD` | 省略 |

### 2.2 清洗规则（必须实现，勿依赖调用方）

- 替换 `\ / : * ? " < > |` 与控制字符为 `_`；折叠连续空白与 `_`。
- 段内**去掉**分隔符 `_`（避免破坏段边界），首尾去 `.` 与空白。
- **总量上限 120 字符**（含扩展名）：依次从尾部裁掉 日期→年窗→类型，最后截断主题，任一段为空则跳过该段而不是留空段。
- 结果不得为空、不得为 `.`/`..`；命中则整串退回 `fallback-<8位短id>`。
- 同一目录重名由浏览器/系统决定，**服务端不做去重**（同名不同版本是正常的）。

### 2.3 RFC 5987（关键，容易漏）

中文文件名必须同时给 ASCII 兜底与 UTF-8 编码名，否则各浏览器行为不一致：

```
Content-Disposition: attachment; filename="report-1a2b3c4d.docx"; filename*=UTF-8''%E5%9F%BA...%2Edocx
```

- `filename` 用 **纯 ASCII** 兜底（沿用现有 `report-<8hex>`，避免老客户端拿到空名）。
- `filename*` = `UTF-8''` + `urllib.parse.quote(name)`（注意 **`quote` 默认不转义 `/`**，需先按 §2.2 清洗，`safe=""`）。
- 前端 `downloadText`（Blob 下载）**读不到响应头**，需由后端把规范名一并返回（见 §2.5）。

### 2.4 实施位置：三方案比较

| | A 后端单一函数 + 随资源返回 | B 前端各自构造 | C 前端改用 URL 直开 |
|---|---|---|---|
| 做法 | 新增 `src/naming.py::export_filename()`；`GET /api/artifacts/{id}` 与 report 详情增加 `export_filename` 字段；三处导出端点复用同一函数 | 在 `exportFormat.ts` 复制一份 JS 实现 | 前端不再用 Blob 下载，统一 `window.open(exportUrl)` 让浏览器吃响应头 |
| 收益 | 单一口径，中文正确，前端零逻辑 | 改动最小 | 改动最小 |
| 代价 | 加一个字段 + 一个模块 | **双端漂移**：规则一改必不一致 | md 无图场景可用，但做不到"复制为文件"、失败无提示、被弹窗拦截 |
| 主要失败方式 | 忘记同步 `export_filename` 到前端 → 前端仍用旧名 | 一段规则在两边表述不同 | 用户开了弹窗拦截则完全不可用 |

**推荐 A**。C 作为 A 落地前的临时手段不必做（避免两套并存）。

## 3. 四维提示词：分层，不替代

### 3.1 为什么不能直接替换

`src/targets.py` 的调用契约：

- **分段**调用（`review_segments` 切段，逐段一次模型调用，段号与字符区间进 Human 消息）
- 严格解析 JSON，逐字引文必须能在**本段**（或全文）中 `find` 到，否则 `ValueError`（`targets.py:189-206`）
- 强制四个 key 齐全、条目 id 段内唯一、`成果` 必须有 `status` 枚举
- 跨段按 `name` 归一化合并，`PROMPT_VERSION` 变化会把已有结果判为 `stale`

用户版本的表述是"整篇一次提炼、叙述流畅自然、四段式"，**与分段调用和 JSON 契约冲突**：直接替换会让逐字引文与合并逻辑全部失效。

### 3.2 分层结构

| 层 | 文件 | 用途 | 谁读 |
|---|---|---|---|
| 契约层 | `src/prompts/target_extract.md`（**改**） | 分段抽取的机器契约：JSON 骨架 + 引文 + status；**吸收子维度作为思考路径** | `targets.py::target_instruction()` |
| 阅读层 | `src/prompts/target_facet_guide.md`（**新增**） | 人类阅读框架：四维各自回答什么、行文与证据要求 | task2/task3/task4 提示词引用，以及后续"四维对比" |

### 3.3 契约层修订稿（`target_extract.md`，可整份替换）

```markdown
你负责从一段科研报告原文中提取四维事实，供后续横向对比、研判与报告生成使用。
只依据给定原文，不补充常识，不把推测写成事实。

四维的阅读逻辑（按理解一项技术成果的顺序递进，仅作抽取时的思考路径，不是输出字段）：
- 场景：在什么业务/工程背景下做——应用领域与业务想定、作业工况与边界条件。
- 问题：遇到哪些核心瓶颈——系统/机理级矛盾、算法与感知决策受限。
- 技术：用了什么关键方法与方案——架构与机理建模、智能算法与协议策略。
- 成果：取得哪些可核对的产出——平台与软硬件、量化指标、转化应用与学术指标。

必须只返回一个 JSON 对象，不要 Markdown 代码围栏。结构固定为：

{
  "facets": [
    {"key":"场景","items":[{"id":"本段唯一id","name":"简短名称","desc":"原文限定下的说明","evidence":[{"quote":"原文逐字引文"}]}]},
    {"key":"问题","items":[]},
    {"key":"技术","items":[]},
    {"key":"成果","items":[{"id":"本段唯一id","name":"简短名称","desc":"说明","status":"已取得|预期|原文未明确","evidence":[{"quote":"原文逐字引文"}]}]}
  ],
  "relations": [
    {"from":{"dimension":"场景","item_id":"某条目的id"},"to":{"dimension":"问题","item_id":"某条目的id"},"basis":"原文明示"}
  ]
}

规则：
1. facets 必须且只能包含“场景、问题、技术、成果”四项；原文未提及某维度时保留该项并返回空 items。
2. 每个条目至少附一条原文逐字引文；quote 必须能在本段原文中精确找到，不得改写、拼接或概括。
3. 成果条目必须标注“已取得”“预期”“原文未明确”之一。计划、目标、拟开展工作不得标成“已取得”。
4. relations 只记录原文明示的关联。仅在同一段同时出现两个条目，不足以证明它们有关联。
5. 不输出置信度、完成百分比、评分或原文没有的数据。
6. name 用 6–20 字的名词短语（如“非视距强对抗组网”“外部感知神经环路调控”），不要整句；desc 写原文限定下的说明，不写评价性措辞。
7. 量化指标（提升百分比、时延、准确率、投递率等）必须原样保留在 name 或 desc 中，不得改写成“显著提升”一类形容词；原文没有量化数据时不补。
8. 本段没有可抽取内容的维度返回空 items，不要为凑齐四项而编造条目。
```

与现有版本的差异：新增第 3.3 节开头的四维"思考路径"、新增规则 6–8（名称粒度、量化保真、空维度不凑数）。**其余原样保留**。

### 3.4 阅读层新增（`target_facet_guide.md`，即用户提供的框架精修）

```markdown
# 四维信息阅读框架（场景 / 问题 / 技术 / 成果）

用于对比分析、趋势推测与报告生成时组织内容。四维是同一份材料的四个切面，**不是分类目录**：
同一项工作会在四维里各出现一次，彼此多对多交叉。

## 一、业务与应用场景（Scenario）
- 工程/业务载体：技术落地的具体环境与业务想定（如低空智联通信、临床康复训练场景）。
- 运行环境与约束：现实边界、外部干扰或特殊物理限制（如非视距遮挡、强电磁对抗、个体差异适配）。

## 二、核心挑战与瓶颈问题（Problem）
- 机理与系统瓶颈：物理特性、资源配比、网络拓扑或人机交互上的本质矛盾。
- 算法与决策难点：环境不确定性、数据稀缺、高动态性导致的感知与决策难题。

## 三、关键技术与创新方案（Technology）
- 架构与理论模型：理论基石、系统架构体系、仿生/认知机理。
- 核心算法与策略：用于感知、优化、控制、预测的关键算法、协议机制或新型软硬件器件。

## 四、落地成效与综合成果（Achievement）
- 平台与软硬件：原型样机、半实物仿真平台、核心软件模组。
- 性能与指标量化：可量化的提升（时延降低、准确率提升、吞吐量增加等具体数值）。
- 转化与学术指标：工程应用验证、论文/专利/奖励。

## 写作与引用要求
1. 行文符合专业工程与学术阅读习惯，语言精炼客观，层级清晰；不写评价性形容词。

3. 保持“场景 → 问题 → 技术 → 成果”的稳定顺序，便于跨材料对照。
4. 某维在原文中缺失时写明“原文未提及”，不要用常识补齐。
```
