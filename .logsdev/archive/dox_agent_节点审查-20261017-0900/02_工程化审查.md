## 二、阶段判断：从 1-demo 到 2-product-demo

你的阶段划分是 1-demo → 2-product-demo → 3-product-v0 → 4-product-v0.1，判断现在处于 1-demo。我同意。准确地说，现在是**功能广度已经超过 demo，骨架还停留在 demo**：
- 功能广度：问答、四维归纳、谱系、审查、情报、周期总结都有，用的是真实资料，测试有 255 + 47 项；
- 骨架：系统设计、模块边界、交互语言这三层基本没有落到代码里。

功能越多、骨架越弱，每次细节修改的波及面就越难预料，修改也就只能越改越小。这与你说的“只能小修小改”是同一个原因。

### 2.2 进入 2-product-demo 的出口标准（建议，需要你确认）

满足以下六条，才算进入 2-product-demo：

1. **一份现行的系统设计**（`design/系统.md`），包括：
   - 核心对象、各自的 ID 与生命周期，以及对应的代码模块和存储（一个对象只对应一处）；
   - 三类角色的权限矩阵；
   - 两条主流程：资料整理到对比报告、申请书审查。
2. **两条主流程端到端可用**：用固定的真实资料包，由你按任务验收（能不能把事办完），不靠看截图打分；对应的浏览器脚本能够自动运行。
3. **模块边界**：
   - 后端按领域拆成 router（资料库、分析运行、成果、审查、账户与设置）；
   - 前端按功能分目录（library、analysis、results、review、home），公共层不导入业务页；
   - 前后端类型由 OpenAPI 生成，或者至少有覆盖主流程的契约测试。
4. **交互语言变成代码**：按钮、状态标签、空状态、错误提示、“本次范围”提示做成共用组件，加一张文案表。新页面只能使用这些组件，细节调整改一处就全局生效。
5. **工程基线**：`check.sh`、固定的 lint 规则、提交策略、文档收口（见 03）。
6. **明确不做**：性能与并发、部署打包、多部门数据隔离。这些属于 3-product-v0。

### 2.3 推进顺序

1. **暂停细节修改。** 除缺陷之外，按钮、卡片、文字类的意见先记入 query，标为〔搁置·细节池〕，等第 4 步交互语言组件化之后集中处理。这样做不是不处理这些意见，而是避免在没有共用组件的情况下逐页返工。
2. **系统设计（先现状，后目标）。** 让 agent 先从代码中整理出“现状对象图”：现在有哪些对象、存在哪里、哪些接口在读写、哪里重复。然后对照上下层设计规范 §3 给出目标模型和差异，由你确认。这一步只产出文档，并且先于任何重构。
3. **工程基线**：第三节的 E1、E2、E6。
4. **按对象重构**：每次只做一个对象。比如“成果”：统一模型和存储，拆出它的 router 和前端目录，删除被替代的旧路径（遵循“新旧冲突整体替换”），每次做完运行 `check.sh full`。这一步就是 09 方案中 M2、M3 的具体执行方式。
5. **交互语言组件化**：在第 4 步拆前端目录时一并完成，然后再处理细节池。
6. **主流程验收**：按出口标准第 2 条，由你按任务完成。通过后进入 2-product-demo。

### 2.4 给 agent 的任务写法

修改单位要从“控件”换成“对象”和“流程”。例如：

```text
按 design/系统.md 的“成果”对象重构：
目标：成果只有一个模型和一个存储；报告、问答快照、审查结果都是它的类型。
必须保留：现有成果的 ID、版本、导出、回收站；历史引用可以读回。
可删除：被替代的旧接口和组件（列出清单，等我确认）。
验收：check.sh full 通过；固定任务中“保存回答 → 生成报告 → 在成果页重开”这条流程不变。
不做：界面样式调整。
```

## 三、工程基础问题与建议

### E1 没有统一检查入口，浏览器脚本处于失修状态（影响最大）

- 事实：
  - `tests/` 下有 26 个 `browser_*.py`，都是独立的 `asyncio main()` 脚本。它们需要先手动启动服务（默认地址 `127.0.0.1:8011`），不会被 pytest 收集，也没有统一的运行方式。
  - 仓库里没有 CI（不存在 `.github/`），也没有 `scripts/check` 这类入口。
  - `browser_task_templates` 在“创建自定义任务”的接口步骤失败，`browser_review_flows` 因为没有登录而停在登录页。两个失败都被记为“与本次无关，未处理”（ITERATION §16.121、“GitHub 产品调研”一节）。10-13 加入登录后，早期写的脚本大多没有登录步骤（推断，没有逐个运行确认）。
- 影响：verification.md 把端到端测试定为默认机制，但端到端脚本只能靠 agent 记得、并且手动启动才能运行。每轮只跑“与本次相关的几个”，其余的悄悄失效。真正要做大重构（M3 拆分 `main.py`）时，没有一套可以信任的回归保护。
- 最小修正：
  1. 写一个 `scripts/check.sh`，分两档：
     - `quick`：pytest、npm test、tsc；
     - `full`：在 `quick` 基础上，用临时状态目录启动服务，依次运行“冒烟集”浏览器脚本，最后自动关闭服务。
  2. 盘点 26 个脚本：用户旅程仍然存在的，补上共用的登录步骤；旅程已经删除的，删除脚本。冒烟集控制在 6–8 个，覆盖固定任务（资料整理到对比报告）、审查、成果、登录与角色。
  3. 每个审查节点运行一次 `full`，把结果写入 `verification/<节点>/` 并入库。
- 暂不建议立即接入 GitHub Actions：浏览器脚本依赖本地资料和模型替身，先把本地入口做稳。

### E2 lint 规则没有固定

- 事实：`pyproject.toml` 中的 `[tool.ruff]` 只设置了 `line-length` 和 `target-version`，没有 `select`。dev 依赖写的是 `ruff>=0.8`。所以规则集跟着 ruff 版本的默认值走，本机 0.16.9 报 67 项。ITERATION 中提到 ruff 26 次，但当时用的版本和规则无法还原。
- 影响：“ruff 通过”这类表述无法复现。新版 ruff 的默认规则一变，就会无缘无故出现一批报错。
- 最小修正：在 `[tool.ruff.lint]` 中写明 `select`（建议从 `E,F,I,B,UP` 开始），用 `uv.lock` 锁定 ruff 版本。修掉其中的 F/B 类问题，并放进 `check.sh quick`。TRY/BLE/DTZ 这些风格类规则不必纳入。

### E3 仓库体积主要来自历史

- 事实：
  - `.git` 有 2.8 GB，pack 有 2.49 GiB。当前入库的 `.knowledge` 有 6845 个文件、约 667 MB，包括 11 个 `knowledge.sqlite3`。
  - SQLite 文件在历史中只被提交过 2 次，所以体积不是频繁提交数据造成的，而是早期提交过、后来又删除的数据留在了历史里。例如 `4eb2bb5` 删除了 10560 行。
  - `git count-objects` 提示 pack 目录里有残留的 `.mtimes` 文件。
- 影响：clone 和备份很慢，但不影响日常开发。改写历史（如 `git filter-repo`）难以撤销，并且会改变所有提交号，而 ITERATION 和 DECISIONS 里引用了大量提交号。
- 建议：现在不动。等需要把仓库分发给他人时，再在“改用 Git LFS”和“数据另建仓库，主仓库只放清单与校验和”之间做决定（README 中的 Q4）。在那之前，避免提交大的二进制文件：`.gitignore` 已经忽略 `.logsdev/archive/` 和 PNG，这一点要和 01 提出的 `inputs/` 入库规则一起调整。

### E4 后端单文件过大（已有计划，同意计划中的顺序）

- 事实：`src/main.py` 有 2823 行、99 个 `@app` 路由，其余模块大多不超过 750 行；前端 `store.tsx` 有 1375 行。`DeepResearch-products/09` 已经给出 M2（拆分 store 的业务上下文和界面状态）和 M3（`main.py` 按领域拆成 APIRouter）的方案和验收规则。
- 意见：同意 09 的方向和其中“不以拆目录、减少行数代替职责收敛”的验收规则。补充两点：
  1. **M3 必须排在 E1 之后。** 拆分路由前，先用冒烟集和 `test_app.py` 固定接口行为，否则回归无法定位。
  2. 权限目前靠 `src/auth.py` 中间件里的 `ADMIN_WRITES` 路径正则实现。拆分路由时，路径一改，正则就可能悄悄失效。建议拆分时把管理员限制改成路由级依赖（`Depends`），并为“非管理员写入被拒绝”保留一条接口测试。

### E5 数据可见范围仍是全员共享（产品决定，部署前要再确认）

- 事实：10-14 的决定是“所有角色看到同样的报告”（`main.py:2160` 注释，DECISIONS 中的“三类账户按角色进入不同界面，暂不做接口级权限”）。10-13 的节点审查曾把这一点列为 B1、Q1，提醒在接入真实资料前解决。
- 意见：这是已经确认的产品决定，不算缺陷。但在面向机关单位部署之前，应当重新确认一次。建议把这一项写进 ITERATION 的“未决问题”，不要只存在于历史审查里。

## 四、工程基础的处理顺序（对应 2.3 第 3 步）

1. 提交当前工作区，作为基线。
2. E6 清理工作区，E2 固定 lint 规则。这两项不改动业务。
3. E1：写 `check.sh`，修复或删除失效的浏览器脚本，确定冒烟集。
4. 节点收口时运行一次 `full`，证据入库。
5. 然后进入 2.3 第 4 步，按对象重构（即 09 方案中的 M2、M3），每做完一个对象运行一次 `full`。
