# 03 规则文档修改建议

以下是建议，**尚未修改任何规则文件**，需要你确认 README 中的 Q1–Q5 之后再执行。原则：

- 只修改与实际不符、或导致 01 中各项问题的地方；
- 不为凑完整而增加规则；
- 项目特有的事实（文件名、命令、目录）写进 DOCUMENTS 和 `.logsdev/README`；
- 通用方法保留在 rules 中。

## 二、DOCUMENTS.md

### 2.1 把载体表改成项目实际使用的文件（Q1 选择保留现名时）

用下表替换现在的“信息放在哪里”表，并删除“下表路径是模板默认载体……”这一段，因为映射已经直接写进了表里：

| 信息 | 载体 | 边界与上限 |
|---|---|---|
| 工程当前能力和使用方法 | 根目录 `README.md`、组件文档、接口契约 | 只写当前实现及证据支持的事实 |
| Agent 通用原则和阅读路由 | `AGENTS.md`（`CLAUDE.md` 引用它） | 只放无条件适用的原则 |
| 反复使用的方法 | `.agents/rules/` | 不写项目进度和一次性结论 |
| 原始需求 | `.logsdev/query.md` | 保留原文；每条带状态标记；节点收口时把已完成条目移入 archive |
| 用户附件（截图、样例） | `.logsdev/inputs/` | 入库；命名为 `YYYYMMDD-HHMM-简述.ext`；单个文件不超过 1 MB |
| 当前有效要求与现状 | `.logsdev/PROJECT.md` | 只写现行内容，不按 query 分节，不放提案；目标不超过 400 行 |
| 正在进行的工作 | `.logsdev/ITERATION.md` | 只写进行中的任务、未决问题、下一步；目标不超过 150 行；跨会话任务链接任务卡 |
| 现行决定 | `.logsdev/DECISIONS.md` | 顶部是现行决定索引；被取代的条目在收口时移入 archive |
| 现行设计 | `.logsdev/design/<主题>.md` | 每个主题一份；开头写明状态；新方案修改或取代旧方案，不并列新建 |
| 较大需求的任务卡 | `.logsdev/tasks/<YYYYMMDD>-<主题>.md` | 目标旅程、必须保留、可删除、验收、未决；完成后结论并入现行层，卡片移入 archive |
| 节点审查 | `.logsdev/reviews/<YYYYMMDD-HHMM>/` | 审查结论；采纳的意见转入现行层或任务卡 |
| 验证证据 | `.logsdev/verification/<主题-日期>/` | 被长期文档引用的目录必须入库；大文件（录屏等）放 `_local/` 并在 README 写明 |
| 历史快照 | `.logsdev/archive/<YYYY-MMDD>-node/` | 只在收口时写入；只读；**不作为需求来源**；大于 1 MB 的二进制文件放 `archive/_local/`（忽略） |
| 普通历史 | Git | 不按轮次复制 |

### 2.2 新增一节“节点收口”

```markdown
## 节点收口

用户发起审查节点时，或现行层超出上限时执行。一次收口单独提交一次。

1. 确认工作区已提交，或说明有哪些未提交内容。
2. query：已实施且已被接受的条目整段移到 `archive/<节点>/query.md`；现行文件只留待处理、进行中、未接受的条目。
3. ITERATION：整份旧文件移到 `archive/<节点>/ITERATION.md`；现行文件按当前事实重写。
4. PROJECT：按最后一版实现与有效要求重写现行条目；提案和按 query 分节的记录移入 archive。
5. DECISIONS 与 design：被取代的条目移入 archive；更新索引和状态头。
6. 检查：长期文档中的链接都指向已入库的文件；`.logsdev/README.md` 的现行文档清单与目录一致。
7. 在 query 的节点条目下回链本次收口的提交。

收口只改变文档的位置和表述，不改变要求。发现要求冲突时，按通用原则列出冲突，等用户裁决。
```

### 2.3 新增 query 条目格式

```markdown
## 2026-MMDD HHMM 〔待处理〕
（用户原文；附件链接 inputs/…）

→ 〔已实施 abc1234〕一句话结果；涉及要求变化时注明“已改 PROJECT §x”
→ 〔接受〕（用户写）
```

状态只有五种：待处理、进行中、已实施、接受、搁置。agent 只写前三种和“搁置（原因）”，“接受”由你来写。

### 2.4 修改“何时更新”中的一句

- 原文：“工作确需中断接续、交接或并行协调时更新当前工作载体……简单且当次完成的任务可只在交付回复中说明。”
- 改为：“……简单且当次完成的任务**以提交信息和 query 回链为记录，不写 ITERATION**。”

现在的规则本来就允许这样做，但没有被执行。原因是“只在交付回复中说明”没有持久的位置，agent 于是选择写 ITERATION。改成提交信息之后，记录就有了持久的位置。

### 2.5 “清理前保留什么”补一条

“`interactions/`、`.workbuddy/` 这类交接和临时目录，在任务完成后由该任务的 agent 删除。需要保留的结论先并入现行层。”

## 五、不建议做的事

- 不建议把 ITERATION 改成按日期拆分的多个文件，那只是把流水账拆成了更多份。真正需要的是“现行”和“历史”分开。
- 不建议在 rules 里写死角色流程（规划 → 实现 → 审查 → 观察）。现在单人工作为主，按 DOCUMENTS 第 5 节“有并行时才启用”即可。
- 不建议在本次收口中删除 archive 里的大文件。是否保留 `grant-review.zip` 和 `target-v1/` 由你决定，移到 `_local/` 即可。
