# 信息抽取重构：默认模板、两段流程与档案记录

## 1. 背景与目标

1101 要求“不同类型资料的信息提取模板”并增加预览/编辑入口；1110 进一步指出：四维是甲方明确要求、覆盖至少一半资料类型，但只提取四维不够；`project_index.py` 只适合 NSFC 验收报告；`retrieval.py` 依赖文件名不可靠；`experts.py` 待完善。

本轮先把**默认抽取契约**固定下来，不急着做多模板和专家审计 UI：

- 默认模板先把“关键技术项目报告”（NSFC、横向、纵向等提出技术解决场景问题并形成成果的报告）跑稳；
- 元数据、资金从四维中拆出，单独成层；
- 资料入库内部分为“解析”和“抽取”两段，外部仍是一条流程；
- 文档记录统一存 `archive/<doc_id>.json`，版本固定引用，过时按哈希/版本判断。

## 2. 已确认的需求

1. **默认模板 = 四维**：场景、问题、技术、成果；沿用现有契约，保留 `relations`、`outputs`、`events`、技术角色、成果状态。
2. **四维不够，但不替代四维**：项目身份、单位、负责人、时间、资金等事实单独成层；四维仍是甲方要求的核心切面。
3. **解析/抽取两段**：解析是确定性的，抽取是模板驱动的；内部两段、外部一条流程。
4. **解析结果可查看/修改**：保留入口，不强制；系统库管理员改，个人库本人改，其他账户只读。
5. **元数据独立**：9 个词条；正文优先、文件名兜底、人工最高；项目身份 = 项目体系 + 项目编号。
6. **资金独立**：4 个 NSFC 默认词条；绘图只用“总经费”，缺失留空，不跨口径合计。
7. **文件结构简化**：不新增 `metadata/`；`parsed/` 放解析产物，`archive/` 放文档记录；`source/datadb/vectordb/hierarchy.json/lineage.json` 保持不变。
8. **版本严谨**：资产版本 + 记录固定引用 + 发布不可改 + 不自动重跑；过时由源哈希、校正哈希、版本比较判断。
9. **一次性迁移**：实施时 `target/` → `archive/`，之后只保留 `archive/`。

## 3. 默认抽取模板

名称：`项目报告-四维`（暂定 id：`project-report-four-facets`）。
适用：NSFC、横向、纵向等“提出技术解决某场景问题并形成成果”的项目报告。
不适用：论文、专利、政策、笔记（后续另立模板）。

输出结构沿用现有四维契约：

```json
{
  "facets": [
    {"key": "场景", "items": [{"id": "...", "name": "...", "desc": "...", "evidence": [...]}]},
    {"key": "问题", "items": []},
    {"key": "技术", "items": [{"id": "...", "name": "...", "role": "关键创新|配套-…|未标明", "evidence": [...]}]},
    {"key": "成果", "items": [{"id": "...", "name": "...", "status": "已取得|在研|预期|原文未明确", "status_raw": "...", "self_reported": false, "evidence": [...]}]}
  ],
  "relations": [{"from": {...}, "to": {...}, "type": "场景-问题|针对|配套|验证", "basis": "原文明示", "evidence": [...]}],
  "outputs": [{"id": "...", "kind": "期刊论文|会议论文|专利|软件/数据|样机/系统|平台/基地|标准/许可|人才/团队|转化/应用|指标|奖励/专著", "attribution": "本项目|前期成果|参考文献|待核对", "status": "...", "title": "...", "evidence": [...]}],
  "events": [{"id": "...", "type": "试验|样机|部署|论文发表|专利申请|专利授权|其他", "date": "...", "status": "...", "desc": "...", "evidence": [...]}]
}
```

冻结规则：

- 四个 facets 的 key 固定；技术角色、成果状态、成果类别、事件类型固定。
- 每条事实必须有原文引文；找不到引文的值拒收，进 `rejected`。
- 关系只记录原文明示；同段共现不算关系。
- `outputs/events` 保留为“成果细化”，不删除。
- 文件名不参与四维事实。
- 旧记录继续有效，不批量重跑。

## 4. 解析与抽取

### 4.1 边界

| 阶段 | 输入 | 输出 | 失败 |
|---|---|---|---|
| 文档解析 | 原文件 | 正文、页码、图片、表格、解析质量、解析版本 | 保留文件与原因，可重试 |
| 信息抽取 | 解析正文 + 模板/字典 | 四维记录、元数据、资金、证据、拒收项 | 单段/单字段失败，保留部分结果 |

- 解析不调用语义模型；抽取是模板驱动的。
- 抽取记录绑定“解析版本 + 校正哈希”；解析/校正变化，抽取标“需更新”。
- 模板/字典出新版，只标“有新版本”，不自动重跑。

### 4.2 用户看到的状态

内部解析/抽取分开，外部只给四个状态：

| 用户状态 | 内部含义 | 用户动作 |
|---|---|---|
| 处理中 | 解析中 / 抽取中 | 等待，可看进度 |
| 待核对 | 完成但有警告：缺关键字段、字段冲突、解析质量低、有拒收项 | 查看并确认 |
| 已入库 | 解析 + 抽取完成且无阻塞问题 | 查看解析/抽取 |
| 失败 | 解析失败或抽取失败 | 看原因 / 重试 |

- 正常情况自动到“已入库”；只有异常才“待核对”，不强制逐步确认。
- 详情页签：原文 / 解析 / 抽取 / 元数据 / 资金。
- “查看/修改解析结果”只在详情里，不在主流程。
- 系统库管理员可随时查看、重抽；默认自动入库，不额外加审批。

### 4.3 权限

- 系统资料库：管理员修改解析结果。
- 个人资料库：本人修改。
- 其他账户：只读。
- 若以后要允许普通用户修改系统库解析，需另加审核/留痕规则；默认不做。

## 5. 元数据与资金

### 5.1 元数据字典 v0

| 词条 | key | 别名（先列这些） |
|---|---|---|
| 项目名称 | `project_name` | 项目名称、课题名称、合同名称、项目名 |
| 项目编号 | `project_no` | 批准号、项目批准号、项目编号、课题编号、合同编号、项目编码 |
| 项目体系 | `project_scheme` | 国家自然科学基金、自然科学基金、横向、纵向、其他 |
| 项目类别 | `project_category` | 资助类别、项目类别、专项、计划类别、项目类型 |
| 承担单位 | `lead_unit` | 依托单位、承担单位、牵头单位、受托单位、项目单位 |
| 参与单位 | `participant_units` | 合作单位、参与单位、协作单位 |
| 负责人 | `principal_investigator` | 负责人、项目负责人、课题负责人、首席科学家 |
| 开始时间 | `start_date` | 执行年限、研究期限、项目起止、合同期限、起止时间 |
| 结束时间 | `end_date` | 同上 |

规则：

- 取值顺序：人工确认 → 正文结构化字段/表格 → 正文叙述 → 文件名（legacy，标 low）→ 未知。
- 每个值带 `source / confidence / evidence`；日期多一个 `precision`。
- 冲突进 `candidates`，不自动选。
- 项目身份 = 项目体系 + 项目编号；没有编号就“待识别”，不用标题/负责人合并。
- 项目体系只认正文明确写出或人工确认，不从标题猜。
- 单位区分主承担/参与，不混。

### 5.2 资金字典 v0（NSFC 默认）

| 词条 | key | 别名 | 用途 |
|---|---|---|---|
| 总经费 | `total` | 项目总经费、总经费、经费总额、项目总金额 | 唯一绘图口径 |
| 批准资助金额 | `awarded` | 批准资助、资助金额、批准金额、资助经费 | 展示/核对，不绘图 |
| 直接费用 | `direct` | 直接费用、直接经费 | 展示/核对，不绘图 |
| 间接费用 | `indirect` | 间接费用、间接经费 | 展示/核对，不绘图 |

资金事实：

```json
{
  "term": "total",
  "term_raw": "项目总经费",
  "amount": "297.0000",
  "unit": "万元",
  "currency": "CNY",
  "tax": "未说明",
  "evidence": [{"quote": "项目总经费:297.0000（万元）", "locator": {"page": 1}}],
  "source": "content",
  "status": "stated"
}
```

规则：

- 只取原文明确金额；不推算、不换算、不补零。
- 同一词条多个值并列冲突；不同词条不合计。
- 绘图只取 `total`；缺失留空；冲突排除并列出。
- 现有资料里很多只写“直接费用”，按总经费口径会显示缺失；这是口径选择的结果，不补零、不替代。

## 6. 文件结构与档案记录

```text
<corpus>/
  source/
  datadb/knowledge.sqlite3
  vectordb/
  parsed/<相对路径>/
      markdown.md
      middle_json.json
      images/
      cache.json
      corrections.json
  archive/<doc_id>.json
  hierarchy.json
  lineage.json
```

- `parsed/` 按源文件相对路径组织：解析产物大、与文件内容绑定、方便人工对照。
- `archive/` 按 `doc_id` 组织：文档改名/移动后 id 稳定，记录不跟着路径跑。
- `archive` 语义是“资料档案”，不是“过时归档”；过时由 `versions` 比较判断。
- 一份文档只保留当前记录；旧版本不另存。以后需要审计历史，再加 `archive/<doc_id>.<version>.json`，不新开目录。

## 7. 版本与过时

读取时比较，不写死状态：

- `source.sha256` 与当前原文件不一致 → `parse` 过时；`metadata`、`extraction` 都过时。
- `parse.text_sha256` 与当前校正后正文不一致 → `metadata`、`extraction` 过时。
- `versions.metadata_*` 低于当前发布版本 → 标“有新版本”，不自动重跑。
- `versions.extraction_*` 低于当前发布版本 → 标“有新版本”，不自动重跑。
- 只有解析/校正变化才强制标过时；模板/字典出新版只是“可选重抽”。

版本维护：

- 发布后的资产版本不可改，只能出新版；旧版本保留，可 diff、可回滚。
- 记录固定引用当时使用的版本；不因后台改模板而悄悄改变结果。

## 8. 迁移

- 实施时一次性把 `target/` 迁到 `archive/`，之后只保留 `archive/`，不并行两个目录。
- 旧记录没有 `metadata/parse/versions` 时按 legacy 读：有 `facets` 就按四维记录，缺的段视为“未抽取”。
- 迁移不批量重跑模型；旧记录保留原版本，按需重抽。
