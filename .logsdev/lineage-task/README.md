# 技术谱系（lineage）生成任务说明

供其他模型执行。每个资料库独立处理，分三步：① 搭框架（一次调用）；② 分批归类并判定阶段（每批 25 条）；③ 对第②步没归入主题的条目再归类一次。三步产出交回后，由本系统按现有规则校验并组装成 `lineage.json`。

## 输入文件（`.logsdev/lineage-task/inputs/`）

- `<库名>.step1.txt`：第①步的用户消息，已按系统格式生成，可直接使用。
- `<库名>.items.json`：`corpus_id`、`scenes`（场景归纳的 6 个场景名，即“应用领域”）、`items`（全部技术条目）。每个条目：`id`（`项目号|条目号`，唯一键）、`name`、`desc`、`project_id`、`start`/`end`（项目起止年，可能为空）、`outcomes`（该项目已取得的成果，最多 4 条）。

条目数：医疗 1336、机器人自动化 1025、金融经济 66、农业 48、材料 46、生物识别 40、隐私保护 36、生物医药 32、大数据 31、信息智能 17、社会治理 16。

## 第①步：框架

- system 消息：下面“提示词一”全文。
- user 消息：`<库名>.step1.txt` 全文。
- 产出：一个 JSON（格式见提示词一末尾）。`fields` 必须与输入给定的应用领域逐字一致、顺序一致。

## 第②步：归类与阶段（每批 25 条）

- system 消息：下面“提示词二”全文。
- user 消息按以下格式拼接（编号由第①步结果生成）：

```text
技术主题（编号 体系 › 方向 › 主题）：
K1 <体系> › <方向> › <主题>
K2 …（按第①步 categories → children → themes 的顺序依次编号，从 K1 起，全库统一编号）

应用领域（编号 名称）：
F1 <fields[0].name>
F2 …

业务环节（编号 名称）：
S1 <stages[0].name>
S2 …

技术条目（编号｜名称｜说明｜项目起止年｜该项目已取得的成果）：
T1｜<name>｜<desc 前 80 字>｜<start 或 ?>–<end 或 ?>｜<outcomes 用“；”连接，没有写“无”>
T2｜…（每批最多 25 条，T 从 1 编起）
```

- 产出：每批一个 JSON `{"items": [{"ref": "T1", "theme": "K12", "field": "F2", "stage": "S3", "maturity": 2, "basis": "…"}]}`。交回时请注明每批对应的条目 `id`（例如保存为 `[{"id": "<条目 id>", …该条目的输出…}]`），避免批内编号错位。

## 第③步：未归入条目再归类一次

- 收集第②步中 `theme` 为 `K0` 或不在编号表内的条目，按第②步同样格式再发一次，只是 user 消息最前面加一行：

```text
这些条目上一轮没有归入任何主题。除非是组织管理、研讨交流等非技术条目，请选最接近的主题，不要因为应用对象不同而填 K0。
```

- 这一步只用来补“主题”（以及第②步留空的领域/环节）；阶段 `maturity` 与依据 `basis` 以第②步为准，不覆盖。

## 系统会做的校验（交回前可自查）

- 体系最多 8 个、每体系方向最多 6 个、每方向主题最多 6 个；名称去重，体系不超过 20 字、方向/主题不超过 24 字，超长截断。
- `theme` 不在编号表内 → 该条目列入“未归入体系的条目”；`field`/`stage` 编号越界或为 F0/S0 → 记为“未判定”。
- `maturity` 只接受整数 0–5，其他值一律记为 0（未判定）；`basis` 截到 60 字。
- 每个条目只归一处；条目名称、项目、年份不允许改写（由系统从输入回填）。

## 交回内容

每个库一个文件夹：`framework.json`（第①步输出）、`assign.json`（第②步全部条目的结果，带条目 `id`）、`retry.json`（第③步结果，带条目 `id`）。我会用现有代码校验、组装并写入各库 `lineage.json`，再在界面核对。

## 提示词一（第①步 system）

# 技术谱系框架

为一个资料库的全部技术条目搭建技术谱系的上三级：技术体系 › 技术方向 › 技术主题，供不熟悉新技术的领导和资料管理员理解“这些技术属于什么体系”。系统随后会把每个技术条目放到某个主题下，成为第五级（领域是第一级）。

## 要求

- 技术体系按**技术方法本身所属的体系**划分，不按应用场景划分：用较传统、熟悉的说法（参照学科与申请代码习惯，例如“控制理论与方法”“机器学习”“计算机视觉”“传感与检测”“机构与驱动”“优化与决策”“建模与仿真”），不超过 10 字；目标 4–8 个。
- 技术方向是体系下更具体的方向，不超过 12 字；每个体系 2–5 个。
- 技术主题是方向下一类做法，不超过 12 字；每个方向 2–5 个。主题要能各自容纳多个条目，不要为单个条目单设主题。
- **分类标准**：体系 = 方法所属的学科；方向 = 该学科内按方法原理的细分；主题 = 方向内的一类具体做法。每个主题必须是所在方向的下位概念（例如“多模型比较与集成”不是“特征选择与降维”的下位，应放到合适的方向或另立方向）。一种做法同时涉及多个体系时，按其主要方法原理只归一处，不要为凑满层级强行嵌套。
- 名称中不要出现应用对象或场景词（如康复、自动驾驶、水下、医疗、制造、作物）。
- 三级合起来要能容纳清单中绝大多数条目；`summary` 一句话说明该体系在本领域主要解决什么，不引入清单外的数字或机构。
- 读者包括不熟悉新技术的资深专家和管理层：体系与方向各给一句 `plain`（不超过 40 字），用本领域经典学科说法讲清“它做什么、解决什么”，把新术语说成熟悉做法的延伸（如“注意力网络”说成“自动聚焦关键区域的识别模型”），不用“颠覆”“革命性”等词，不夸大。
- 技术方向若是跨应用场景共用的**共性支撑**（数据采集与治理、数据与样本库建设、隐私保护与可信计算、跨机构协同、模型可解释与安全、通用平台与工具），标 `"foundation": true`；具体解决某类业务任务的方法标 `false`。

- 另给出本领域的**业务环节** `stages`（4–6 个，每个不超过 10 字，附一句 `plain`）：按该领域经典的业务或诊疗全流程划分，读者一看就能对号入座。例如医学可用“风险预测与早筛、诊断与分型、治疗决策与介入、疗效评估与预后、机制与转化研究”，机器人可用“感知与建模、决策与规划、控制与执行、系统集成与应用”。环节是技术**服务于哪一步**，与技术方法分类相互独立。
- 若输入给定了应用领域，`fields` 原样照抄；未给定时给出 4–8 个应用领域（按服务对象划分，不超过 12 字）。

## 输出

只输出 JSON：

```json
{"branch": "本库领域分支名（不超过 12 字）",
 "fields": [{"name": "应用领域"}],
 "stages": [{"name": "业务环节", "plain": "通俗说明"}],
 "categories": [{"name": "技术体系", "summary": "一句话", "plain": "通俗说明",
                 "children": [{"name": "技术方向", "plain": "通俗说明", "foundation": false,
                               "themes": ["技术主题", "技术主题"]}]}]}
```

## 提示词二（第②③步 system）

# 技术条目归类与成熟度

把每个技术条目放到给定的一个“技术主题”下（用主题编号），并判断该项目对这项技术做到的成熟度。

## 归类

- `theme` 只能填给定列表中的主题编号（如 K12），选最贴近的一个；确实都不贴近时填 `K0`。

- 给出了应用领域和业务环节时：`field` 填该条目服务对象所属的应用领域编号（如 F2）；通用方法按其所在项目的主要对象判断，确实无法判断填 `F0`。`stage` 填该技术在业务流程中起作用的环节编号（如 S3），无法判断填 `S0`。

## 成熟度（只依据给出的条目说明和该项目已取得的成果，不用常识补全）

- 1 理论与方法研究：提出理论、模型或方法，尚无实验验证描述。
- 2 算法与模型验证：在仿真、公开数据集或离线数据上验证。
- 3 原型与样机验证：做出原型系统、样机、装置，并有实验室实验。
- 4 系统集成与场景试验：系统集成后在真实场景、临床、现场或多中心开展试验。
- 5 示范应用与转化：已有示范应用、推广、转化或产品化。
- 0 未判定：给出的文字不足以判断。

组织管理机制、研讨与交流方式等非技术条目填 0。只算已取得的程度，计划或预期的工作不算；`basis` 用不超过 20 字说明依据（引用给出的说法）。

## 输出

只输出 JSON，每个输入编号一条：

```json
{"items": [{"ref": "T1", "theme": "K12", "field": "F2", "stage": "S3", "maturity": 2, "basis": "一句依据"}]}
```
